## The problem we're solving

A list of resources escapes its allocated panel and pushes the next section far below its expected location. The goal is a predictable local repair, not a decorative mockup. The HTML fixture is fully offline and has an intentionally failing starter plus an instructor solution.

## Build the mental model

overflow: auto creates scrolling only when content overflows; max-block-size constrains the scrollport. Keyboard-only users need a reachable scroll container, and visible focus should remain obvious. overflow: hidden clips content and can affect sticky positioning; do not add it reflexively.

**Predict before running:** The resources panel scrolls internally and remains reachable by the keyboard.

## Guided implementation

<LessonStep number={1} title="Reproduce the actual defect" file="labs/css-overflow/starter/index.html" expected={"overflow: visible allows the list to paint outside its intended scrollport."}>

Use the original CSS from the starter. Resist the temptation to add `!important` until you know which computed property is causing the failure.

```css
.resources { max-block-size: 8rem; overflow: visible; }
```

**Predict before running:** overflow: visible allows the list to paint outside its intended scrollport.

**Why it fails:** overflow: auto creates scrolling only when content overflows; max-block-size constrains the scrollport. Keyboard-only users need a reachable scroll container, and visible focus should remain obvious. overflow: hidden clips content and can affect sticky positioning; do not add it reflexively.

**Proof:** Inspect overflowY, scrollHeight, clientHeight, tabindex and the keyboard focus ring. Record the value in the starter before moving on.

</LessonStep>

<LessonStep number={2} title="Repair the rule, not the screenshot" file="labs/css-overflow/starter/index.html" expected={"The resources panel scrolls internally and remains reachable by the keyboard."}>

Replace the defective declaration with this rule from the instructor implementation. Do not change the semantic markup or hide overflow simply to mask a layout defect.

```css
.resources { max-block-size: 8rem; overflow: auto; overscroll-behavior: contain; outline-offset: 3px; } .resources:focus-visible { outline: 3px solid #ba4c08; }
```

**Predict before running:** The resources panel scrolls internally and remains reachable by the keyboard.

**Why it works:** overflow: auto creates scrolling only when content overflows; max-block-size constrains the scrollport. Keyboard-only users need a reachable scroll container, and visible focus should remain obvious. overflow: hidden clips content and can affect sticky positioning; do not add it reflexively.

**Proof:** Compare the properties and geometry with `labs/css-overflow/solution/index.html`, using DevTools, not merely text-searching the CSS source.

</LessonStep>

<LessonStep number={3} title="Measure and regression-check the behavior" file="labs/css-overflow/starter/index.html" expected="Narrow and wide states remain usable, with no unexpected horizontal overflow.">

Open Responsive Design Mode at 320px and 1100px. For applicable lessons, scroll, inspect an accessible scrolling region or constrain the query container while keeping the viewport fixed.

```js
const root = document.documentElement;
const surface = document.querySelector('#demo');
console.log({
  fitsViewport: root.scrollWidth <= innerWidth,
  display: getComputedStyle(surface).display,
  inlineSize: surface.getBoundingClientRect().width
});
```

**Predict before running:** A specific layout value changes as expected, and the repaired surface stays within its available width.

**Why it works:** Browser computed styles and bounding boxes reflect selector matching, layout algorithm and containing-block constraints.

**Proof:** Inspect overflowY, scrollHeight, clientHeight, tabindex and the keyboard focus ring.

</LessonStep>
