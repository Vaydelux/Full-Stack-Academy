## The problem we're solving

A password form has password and confirmation fields. Each field meets individual rules, but inconsistent values must still be rejected with an issue on the confirmation control.

**Broken behavior:** The starter validates lengths but never compares confirmation to the original password.

## Build the mental model

Use refine for a single boolean invariant and superRefine for multiple custom, path-aware issues. In Zod 4, superRefine remains supported but is deprecated in favor of check.

**Predict before coding:** Reject mismatched confirmation and attach the custom issue to confirmPassword.

**Important boundary:** TypeScript types are erased at runtime. These exercises import Zod 4 from the repository's locked dependencies and run actual `safeParse` or `parse` assertions, not simulated validation. Runtime validation does not authenticate a caller, authorize object access, or persist data.

```ts
import * as z from 'zod';
export const Passwords=z.strictObject({
 password:z.string().min(8),
 confirmPassword:z.string().min(8),
}).superRefine((values,ctx)=>{
 if(values.password!==values.confirmPassword)ctx.addIssue({
  code:'custom',path:['confirmPassword'],message:'Passwords do not match',
 });
});
```

**Why this works:** Use refine for a single boolean invariant and superRefine for multiple custom, path-aware issues. In Zod 4, superRefine remains supported but is deprecated in favor of check.

</LessonStep>
