## The problem we're solving

A preview inserts user text into innerHTML and unexpectedly creates clickable elements and script-capable markup. Browser Interaction topics require both executable JavaScript logic and a real local HTML document. The fixture uses synthetic content with no external scripts, endpoints or data uploads.

## Build the mental model

innerHTML interprets markup; it is an injection sink and needs a trusted sanitization model if markup is truly required. For ordinary user text, textContent treats markup characters as literal text. Avoid security claims based solely on a regex or strip-tags helper.

**Predict before running:** Typing <strong>hello</strong> displays literal brackets and never creates a strong node.

<LessonStep number={2} title="Implement the browser-safe interaction" file="labs/js-safe-dom/starter/index.html" expected={"Typing <strong>hello</strong> displays literal brackets and never creates a strong node."}>

Replace the defective handler without discarding native elements or semantics. For untrusted content use `textContent`, not an unsafe HTML sink.

```js
document.querySelector('#preview').addEventListener('click',()=>{const value=document.querySelector('#text').value;document.querySelector('#status').textContent=value;});
```

**Predict before running:** Typing <strong>hello</strong> displays literal brackets and never creates a strong node.

**Why the repair works:** innerHTML interprets markup; it is an injection sink and needs a trusted sanitization model if markup is truly required. For ordinary user text, textContent treats markup characters as literal text. Avoid security claims based solely on a regex or strip-tags helper.

**Proof:** Compare the resulting DOM and accessibility state to the instructor `solution/index.html` using the same input.

</LessonStep>
