## The problem we're solving

The starter always chooses v1 even when the caller explicitly requests a known v2 or unknown v3 media type. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

Version negotiation needs a documented, bounded contract; unsupported vendor media versions must not silently fall back and change behavior.

**Expected outcome:** Default JSON requests use v1, explicit academy v2 selects v2, and unknown versioned media fails.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. A real versioned deployment should explicitly publish support/deprecation policy and API contract regression tests; this simple negotiator is intentionally not full Accept q-value parsing.

<LessonStep number={2} title="Build the valid OpenAPI 3.1 integration" file="labs/openapi-version-strategy/starter/solution.mjs" expected="Default JSON requests use v1, explicit academy v2 selects v2, and unknown versioned media fails.">

```js
export function selectApiVersion(accept='application/json'){
 if(typeof accept!=='string')throw new TypeError('Invalid Accept');
 const value=accept.trim().toLowerCase();
 if(value==='application/json'||value==='*/*')return 'v1';
 if(value==='application/vnd.academy.v1+json')return 'v1';
 if(value==='application/vnd.academy.v2+json')return 'v2';
 throw new RangeError('Unsupported API version');
}
```

**Why this corrects the contract:** Version negotiation needs a documented, bounded contract; unsupported vendor media versions must not silently fall back and change behavior.

</LessonStep>
