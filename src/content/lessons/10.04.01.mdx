## The problem we're solving

The starter invents a version and ignores missing document metadata. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

An OpenAPI 3.1 document declares an exact version, info metadata, paths and reusable components; it is a source contract, not an HTTP server.

**Expected outcome:** A valid OpenAPI 3.1.1 document summarizes the correct title and static operation count, and an incomplete one is rejected.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. OpenAPI 3.1 Schema Objects align with JSON Schema 2020-12. This course model is not a full JSON Schema validator.

<LessonStep number={2} title="Build the valid OpenAPI 3.1 integration" file="labs/openapi-document-layout/starter/solution.mjs" expected="A valid OpenAPI 3.1.1 document summarizes the correct title and static operation count, and an incomplete one is rejected.">

```js
export function summarizeDocument(document){
 if(!document||!/^3\.1\.\d+$/.test(document.openapi??'')||!document.info?.title||!document.info?.version||!document.paths)throw new TypeError('Invalid OpenAPI 3.1 document');
 let operationCount=0;
 for(const value of Object.values(document.paths))for(const method of Object.keys(value))if(['get','post','put','patch','delete'].includes(method))operationCount++;
 return {version:document.openapi,title:document.info.title,operationCount};
}
```

**Why this corrects the contract:** An OpenAPI 3.1 document declares an exact version, info metadata, paths and reusable components; it is a source contract, not an HTTP server.

</LessonStep>
