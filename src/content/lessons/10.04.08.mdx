## The problem we're solving

The starter reports an invented OpenAPI version and contains no usable client generator or server contract. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

End-to-end verify that a real OpenAPI 3.1 document can produce a functional SDK that calls a loopback secured HTTP API, including successful and denied requests.

**Expected outcome:** The generated client calls GET health, GET notes and POST notes, injects bearer only on protected operations, and rejects unauthorized requests.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. The example is intentionally localhost-only, single process, in-memory and uses an opaque demo token. It does not satisfy production authentication, compliance, multi-tenant authorization or durable persistence.
