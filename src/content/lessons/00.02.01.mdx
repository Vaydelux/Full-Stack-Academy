## The problem we're solving

A teammate opens your repository and immediately gets inconsistent formatting and broken tasks. Your settings live only on your machine. Putting a minimal project-owned configuration in version control makes the experience repeatable without forcing personal preferences on everyone.

## Build the mental model

A VS Code workspace is the folder or multi-root workspace currently opened. User settings apply across your editor; workspace settings usually override them for the project. A folder's .vscode/settings.json records shared settings, extensions.json recommends extensions without silently installing them, and tasks.json describes local tasks. Extensions and tasks can execute code, so inspect unfamiliar projects in Restricted Mode before trusting them. Do not commit machine-specific absolute paths or secrets. Editor settings are convenience; lint and tests must also work in a terminal and CI.

<LessonStep number={2} title={"Set shared editing rules"} file="labs/vscode-workspace/starter/.vscode/settings.json" expected={"Files save using UTF-8 and LF, with two-space indentation."}>

Create .vscode/settings.json inside the starter workspace. JSON without comments is used here so the verifier can parse it. Personal choices such as font size remain user settings.

```json
{
  "editor.tabSize": 2,
  "editor.insertSpaces": true,
  "files.encoding": "utf8",
  "files.eol": "\n",
  "editor.formatOnSave": false
}
```

</LessonStep>

<LessonStep number={3} title={"Recommend focused extensions"} file="labs/vscode-workspace/starter/.vscode/settings.json" expected={"The workspace recommends the ESLint and Prettier extensions, but does not auto-install them."}>

Create .vscode/extensions.json. Verify the marketplace publisher and permissions before installing. ESLint checks rules; Prettier formats text. Do not enable both tools as competing formatters without configuring them.

```json
{
  "recommendations": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
}
```

</LessonStep>

<Misconception claim={"Installing more extensions automatically makes a development environment better."} correction={"Each extension adds maintenance, resource and trust costs. Select only the tools needed by the project."} />

## Bug Hunt: diagnose before you change code

An extension setting points to a machine-specific path such as `C:\Users\someone\node.exe`. It works on one PC and fails everywhere else. Remove the machine-specific path, install Node using your documented runtime setup, and keep executable discovery on PATH.
