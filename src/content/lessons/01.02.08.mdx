## The problem we're solving

A contact form looks good with a mouse but fails for keyboard and screen-reader visitors: missing labels, unlabeled radio choices, no validation, invisible focus and a submit action that silently does nothing.

## Build the mental model

An accessible form begins with persistent labels and a coherent control order. Fieldsets group related choices; hints and errors should have clear programmatic relationships. Native constraint validation handles common input errors and can focus invalid controls. For an inline summary, listen to invalid events in the capture phase (they do not bubble normally) without suppressing browser validation. Display a visible alert for invalid input and a status message only after a valid local demo submission. This example intentionally **does not save or transmit** contact data. The production backend would still need validation, abuse protection, privacy handling and a real acceptance response.

**Predict before running:** If an email is invalid, the submit handler ordinarily will not run, but an invalid listener in the capture phase can provide an extra accessible error summary.

<LessonStep number={1} title={"Repair labels and grouped contact preferences"} file="labs/forms-accessibility-capstone/starter/index.html" expected={"Assistive technology exposes field names and a named radio group."}>

Create associated labels and a native fieldset/legend for exclusive choices.

```html
<label for="contact-name">Display name</label>
<input id="contact-name" name="displayName" autocomplete="nickname" required>
<label for="contact-email">Contact email</label>
<input id="contact-email" name="email" type="email" autocomplete="email" required>
<fieldset><legend>Contact preference</legend>
  <label><input type="radio" name="preference" value="email" required> Email</label>
  <label><input type="radio" name="preference" value="none"> No follow-up</label>
</fieldset>
```

</LessonStep>

<LessonStep number={2} title={"Describe required message length and preserve browser validation"} file="labs/forms-accessibility-capstone/starter/index.html" expected={"Short or empty messages are rejected through native constraints."}>

Use aria-describedby for a hint, required and minlength on the message.

```html
<label for="message">Workshop question</label>
<p id="message-hint">At least 10 characters. No real messages are sent.</p>
<textarea id="message" name="message" rows="5" required minlength="10" aria-describedby="message-hint"></textarea>
```

</LessonStep>

<LessonStep number={3} title={"Give valid submission an honest live-region status"} file="labs/forms-accessibility-capstone/starter/index.html" expected={"Invalid fields remain focusable; valid submission produces a truthful status."}>

Avoid fake success responses. Capture invalid events without canceling native feedback.

```js
form.addEventListener('invalid',event=>{
  error.textContent='Check the highlighted field: '+(event.target.labels?.[0]?.textContent||'Required information');
},true);
form.addEventListener('submit',event=>{
  event.preventDefault();
  error.textContent='';
  status.textContent='Local form preview complete. Nothing sent or saved.';
});
```

</LessonStep>

<LessonStep number={4} title={"Verify visible focus and mobile readability"} file="labs/forms-accessibility-capstone/starter/index.html" expected={"The form has visible focus and no horizontal overflow at a 390px viewport."}>

Apply a high-contrast keyboard focus outline and responsive content width; then tab through the entire form.

```css
input:focus-visible,textarea:focus-visible,button:focus-visible{outline:3px solid #e67b18;outline-offset:3px}
*{box-sizing:border-box}
main{width:min(100%,48rem)}
```

</LessonStep>
