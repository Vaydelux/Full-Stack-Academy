## The problem we're solving

An API always returns status 200, including validation errors. Clients cache, retry or render success incorrectly. An HTTP contract must describe both success and failure using methods, statuses and body formats.

## Build the mental model

A request contains a method, target, headers and optional body. GET is intended to be safe and idempotent; POST requests processing and is not generally idempotent; PUT replaces a representation and is idempotent by semantics; PATCH describes partial changes and is not necessarily idempotent; DELETE is idempotent by semantics even if subsequent response codes differ. Headers communicate metadata, such as Content-Type describing a sent body and Accept describing desired formats. Status classes: 2xx success, 3xx redirection, 4xx client-related errors, 5xx server errors. A 204 has no response body. The local exercise uses Fetch Request and Response objects as an in-process contract test; production servers still need streaming body limits, authentication and persistent storage.

**Predict first:** If a client sends text/plain to a JSON-only endpoint, should the handler blindly parse JSON? No. Reject unsupported media types first.

<LessonStep number={2} title={"Route by path and method"} file="labs/http-contract/starter/exercise.mjs" expected={"GET /api/tasks works; unknown paths and unsupported verbs return 404 and 405."}>

Implement the first branches of handle. The Allow header describes supported methods. In this exercise POST returns a synthetic record rather than saving to a database.

```js
export async function handle(request) {
  const path = new URL(request.url).pathname;
  if (path !== '/api/tasks') return json({error:'Not found'},404);
  if (request.method === 'GET') return json({tasks:[]});
  if (request.method !== 'POST') return json({error:'Method not allowed'},405,{Allow:'GET, POST'});
  return createTask(request);
}
```

</LessonStep>

<LessonStep number={3} title={"Validate content type and body"} file="labs/http-contract/starter/exercise.mjs" expected={"Malformed JSON gets 400, unsupported media gets 415, valid content gets 201."}>

Check the media type, then parse and validate an object with a non-empty bounded title. This fixture is in-process; an actual web endpoint must enforce a body-size limit before reading the entire body.

```js
async function createTask(request) {
  const media = request.headers.get('content-type')?.split(';')[0].trim().toLowerCase();
  if (media !== 'application/json') return json({error:'JSON required'},415);
  let body;
  try { body = await request.json(); } catch { return json({error:'Malformed JSON'},400); }
  if (!body || typeof body.title !== 'string' || !body.title.trim() || body.title.length > 120) return json({error:'Invalid title'},400);
  return json({id:'demo',title:body.title.trim()},201);
}
```

</LessonStep>

## Explore it yourself

Inspect a GET and POST response in your own browser's Network panel using the previous local server. Compare Request Headers with Response Headers. In production use a stable error envelope and choose deliberately between 400 and 422 according to your API contract. Do not confuse an idempotent operation with a guarantee that it executes exactly once.

<Misconception claim={"All successful HTTP responses must contain JSON."} correction={"HTTP allows multiple media types. A 204 response must not contain a body."} />

## Bug Hunt: diagnose before you change code

The handler parses every POST request before checking Content-Type. An HTML form or malformed request throws and the API returns a 500. Check media type, catch malformed JSON, and validate the input shape before use.
