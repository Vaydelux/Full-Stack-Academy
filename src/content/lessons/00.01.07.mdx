## The problem we're solving

A developer saves a role in localStorage and trusts that value for an admin API. Anyone controlling their browser can change it. Browser storage is convenient for preferences, but authentication requires server-verified evidence.

## Build the mental model

Cookies are scoped by host/domain, path and other attributes and may be sent automatically to matching requests. HttpOnly restricts script access; Secure restricts transmission to secure contexts (browsers have localhost exceptions); SameSite restricts some cross-site attachment, not every CSRF risk. localStorage persists by origin until cleared; sessionStorage is also scoped to a browser tab's page session. Both are accessible to script and are unsuitable as a trusted authorization store. An opaque session ID is a lookup key for server-owned session data, not a user ID or password. Real apps use mature authentication libraries, session rotation, CSRF controls, revocation and durable shared storage, not this isolated in-memory teaching fixture.

**Predict first:** If a visitor changes localStorage.role to admin, should a server grant admin access? Never. Server permissions must come from trusted state.

<LessonStep number={1} title={"Create an isolated session store"} file="labs/cookies-sessions/starter/exercise.mjs" expected={"A random opaque ID refers to an expiring server-side record."}>

Use randomUUID rather than a predictable user identifier. The create function assumes authentication already happened; it is not a login endpoint. Inject a clock to test expiry without waiting.

```js
import {randomUUID} from 'node:crypto';
export function createSessions(now = Date.now) {
  const sessions=new Map();
  return {
    create(userId,ttlMs=60000) {
      if(!Number.isSafeInteger(ttlMs)||ttlMs<=0)throw new Error('Invalid TTL');
      const id=randomUUID(); sessions.set(id,{userId,expires:now()+ttlMs}); return id;
    },
    get(id) {
      const entry=sessions.get(id);
      if(!entry||entry.expires<=now()){sessions.delete(id);return null;}
      return entry.userId;
    },
    revoke(id){sessions.delete(id);}
  };
}
```

</LessonStep>

<LessonStep number={2} title={"Issue a cookie with explicit attributes"} file="labs/cookies-sessions/starter/exercise.mjs" expected={"A host-only cookie header contains HttpOnly, Secure, SameSite=Lax and Path=/; no Domain is supplied."}>

The __Host- prefix requires Secure, Path=/ and no Domain in supporting browsers. Use the opaque ID and encode it; do not put a private user record in the cookie. Expiry is enforced server-side even if the browser still sends the cookie.

```js
export function sessionCookie(id) {
  return '__Host-academy_session='+encodeURIComponent(id)+'; Path=/; HttpOnly; Secure; SameSite=Lax';
}
```

</LessonStep>

<LessonStep number={3} title={"Resolve a cookie against trusted state"} file="labs/cookies-sessions/starter/exercise.mjs" expected={"Unknown IDs and revoked sessions resolve to null; a valid unexpired session resolves to its user."}>

The simple parser accepts exactly one matching cookie and rejects malformed encodings or duplicates. It is teaching code; use a reviewed cookie parser and session middleware in a production application.

```js
export function readSession(header, sessions) {
  const matches=header.split(';').map(v=>v.trim()).filter(v=>v.startsWith('__Host-academy_session='));
  if(matches.length!==1)return null;
  try{return sessions.get(decodeURIComponent(matches[0].slice('__Host-academy_session='.length)));}
  catch{return null;}
}
```

</LessonStep>

## Explore it yourself

In DevTools Application, inspect Local Storage for the academy's origin: progress is saved locally and is not an account credential. For a trusted HTTPS site inspect cookie attributes, not secret values. Never copy real session tokens into a lab, screenshot, log or AI prompt. HttpOnly reduces token theft through script access, but an XSS script can still perform actions using the browser session.

<Misconception claim={"HttpOnly means a cookie is encrypted and immune to all attacks."} correction={"HttpOnly blocks ordinary JavaScript reads. HTTPS, expiry, CSRF protection and server authorization are separate requirements."} />

## Bug Hunt: diagnose before you change code

A server trusts a userId supplied in a browser cookie. A visitor changes it and acts as another user. Store a random opaque ID, look it up on the server, reject expired IDs, and check authorization for each resource.
