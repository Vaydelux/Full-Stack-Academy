## The problem we're solving

Your frontend expects a product price as a number, but an external API returns a string. TypeScript types disappear at runtime; a type assertion will not repair an invalid response. API boundaries need a defined representation and validation.

## Build the mental model

An API is a contract between consumers and a provider. JSON is a text format covering objects, arrays, strings, finite numbers, booleans and null. It does not preserve functions, undefined, Date types, BigInt or object identity; JSON.stringify can omit object properties with undefined and throws for BigInt by default. Parse text, then check the shape. Zod safeParse returns a discriminated success/failure result instead of throwing for ordinary validation failures. A public data transfer object explicitly selects fields rather than serializing a database row with private properties.

**Predict first:** Does JSON.parse guarantee that a product has a valid numeric price? No. It guarantees only that the syntax parses.

<LessonStep number={1} title={"Serialize and parse a message"} file="labs/api-json/starter/exercise.mjs" expected={"JSON text becomes data and malformed text is rejected."}>

Define a safe boundary for syntax errors. The returned data is untrusted until validated; never use eval to decode JSON.

```js
export function decode(text) {
  try { return {ok:true,value:JSON.parse(text)}; }
  catch { return {ok:false,error:'invalid-json'}; }
}
```

</LessonStep>

<LessonStep number={2} title={"Define a runtime schema"} file="labs/api-json/starter/exercise.mjs" expected={"Valid product data passes. Strings in a numeric field and unknown keys fail."}>

Use Zod 4 strictObject to make the inbound contract explicit. Prices use integer centavos to avoid floating-point currency rounding in this exercise.

```js
import * as z from 'zod';
const Product = z.strictObject({
  id:z.string().min(1),
  name:z.string().trim().min(1).max(120),
  priceCentavos:z.number().int().nonnegative().max(Number.MAX_SAFE_INTEGER)
});
export function parseProduct(text) {
  const parsed=decode(text);
  if(!parsed.ok) return parsed;
  const result=Product.safeParse(parsed.value);
  return result.success ? {ok:true,value:result.data} : {ok:false,error:'invalid-product'};
}
```

</LessonStep>

<LessonStep number={3} title={"Shape a public response"} file="labs/api-json/starter/exercise.mjs" expected={"Only id, name and priceCentavos are included; acquisition cost and other fields are absent."}>

A public response is an allowlist, not a blacklist that must know every future private field. This helper assumes an already trusted validated row; in production combine it with authorization.

```js
export function publicProduct(row) {
  return {id:row.id,name:row.name,priceCentavos:row.priceCentavos};
}
```

</LessonStep>

## Bug Hunt: diagnose before you change code

A developer uses a type assertion for the response, then calculates a price from the string '1200'. This may concatenate or produce incorrect arithmetic. Define an integer schema, reject an invalid type, and map explicit response fields.
