## The problem we're solving

Serialized event data contains a malformed date but is cast as a domain event and converted to ISO without validation. In a full-stack application, this boundary can lead to incorrect data or information disclosure even if the TypeScript project compiles successfully.

## Build the mental model

JSON has strings/numbers/objects but no native Date; serialization boundaries must parse dates and numbers explicitly. Date.parse can accept some noncanonical input, so enforce the contract's ISO format before conversion. JSON.parse itself does not validate application fields.

**Predict before running:** Only canonical valid UTC dates cross into the domain; malformed dates return null.

Use unknown at the boundary, a runtime predicate or strict schema and a public result type. Handle expected invalid data explicitly.

```ts
export function solve(raw:unknown):string|null{if(!raw||typeof raw!=='object'||!('createdAt' in raw)||typeof raw.createdAt!=='string'||!/\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d\.\d{3}Z$/.test(raw.createdAt))return null;const date=new Date(raw.createdAt);if(!Number.isFinite(date.getTime())||date.toISOString()!==raw.createdAt)return null;return date.toISOString();}
```

**Why the repair works:** JSON has strings/numbers/objects but no native Date; serialization boundaries must parse dates and numbers explicitly. Date.parse can accept some noncanonical input, so enforce the contract's ISO format before conversion. JSON.parse itself does not validate application fields.

## Explore and verify

Use boundary-oriented reasoning: the outer layer receives unknown, the parser enforces shape and units, and only then may a domain function use a trusted type. Separate validation from authorization; a successful schema parse never proves the actor has permission.
