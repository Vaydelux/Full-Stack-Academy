## The problem we're solving

A request indicator needs clear ready, loading and failed states for screen-reader users. Using one generic label for every state hides failures from the learner. This lesson uses local React 19 / TypeScript 5 fixtures; the website does not execute learner-provided code.

## Build the mental model

Represent each UI state explicitly; never confuse a missing status with a successful one. A failed request is a distinct user-facing state and needs an accurate accessible announcement. A React element is a description of UI; server rendering verifies initial markup but cannot, by itself, prove a browser interaction, reconciliation, or a DOM commit.

**Predict before you run:** Loading is announced as status, failure as alert, and ready as an ordinary message.

<LessonStep number={2} title="Implement the smallest correct React contract" file="labs/react-conditional/starter/solution.tsx" expected="Loading is announced as status, failure as alert, and ready as an ordinary message.">

Replace the starter's implementation with the reviewed approach below. Keep its public exports stable.

```tsx
export type RequestState = 'loading' | 'ready' | 'failed';
export function RequestNotice({state}:{state:RequestState}) {
  if(state==='failed') return <p role="alert">Unable to load the report.</p>;
  if(state==='loading') return <p role="status">Loading report…</p>;
  return <p>Report is ready.</p>;
}
```

**Predict before you run:** Loading is announced as status, failure as alert, and ready as an ordinary message.

**Why the repair works:** Represent each UI state explicitly; never confuse a missing status with a successful one.

</LessonStep>
