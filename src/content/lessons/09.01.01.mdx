## The problem we're solving

An API accepts account settings with any role and silently strips extra keys; a developer assumes TypeScript types validate requests.

**Broken behavior:** The starter uses open z.object and a generic role string, so invalid roles and surplus keys pass.

## Build the mental model

Use a Zod 4 strict object with bounded strings, enum values and explicit booleans to reject unexpected keys and impossible roles.

**Predict before coding:** Trim the display name, reject unknown keys and reject roles outside reader/editor.

**Important boundary:** TypeScript types are erased at runtime. These exercises import Zod 4 from the repository's locked dependencies and run actual `safeParse` or `parse` assertions, not simulated validation. Runtime validation does not authenticate a caller, authorize object access, or persist data.

export const AccountSchema=z.strictObject({
 displayName:z.string().trim().min(2).max(80),
 role:z.enum(['reader','editor']),
 active:z.boolean(),
});
