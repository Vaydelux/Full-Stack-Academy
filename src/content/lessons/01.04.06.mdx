## The problem we're solving

A frontend cannot read a cross-origin API response, so a teammate suggests disabling CORS in the browser. That would bypass a security boundary without fixing the server contract. Instead we will model which response headers allow a browser to expose a response to a requesting page.

## Build the mental model

Same-origin compares scheme, host and port. Browsers may send cross-origin requests, but scripts cannot freely read responses without authorization. CORS is a response-sharing protocol enforced by browsers, not user authentication or a server firewall. Non-simple requests may require OPTIONS preflight. A credentialed response cannot use wildcard Access-Control-Allow-Origin; it requires an explicit matching origin and Access-Control-Allow-Credentials: true. This offline exercise evaluates policy; it does not make cross-origin requests or change browser settings.

**Predict before running:** For credentialed reads, ACAO:* plus ACAC:true is still invalid. An explicit matching origin with credentials allowed can pass.

<LessonStep number={1} title={"Identify the requesting origin"} file="labs/web-cors/starter/index.html" expected={"Changing scheme or port can change origin."}>

Build origin from parsed URL parts, not from a domain-name substring.

```js
const origin = new URL('https://app.example:443/').origin;
// 'https://app.example'
```

**Predict before running:** Changing scheme or port can change origin.

**Why it works:** An origin is not the same as the registrable domain.

**Proof it works:** Compare http://app.example and https://app.example in DevTools mentally.

</LessonStep>


<LessonStep number={2} title={"Evaluate a credentialed CORS response"} file="labs/web-cors/starter/index.html" expected={"Wildcard origin with credentials must be rejected."}>

Match the exact origin and the explicit credentials header.

```js
const permitted = allowOrigin === requestingOrigin &&
  (!credentials || allowCredentials === true);
```

**Predict before running:** Wildcard origin with credentials must be rejected.

**Why it works:** Credentialed CORS has tighter requirements than ordinary noncredentialed responses.

**Proof it works:** Select Wildcard with credentials and click Evaluate CORS.

</LessonStep>


<LessonStep number={3} title={"Explain preflight without bypassing policy"} file="labs/web-cors/starter/index.html" expected={"The actual request proceeds only when the browser accepts relevant preflight response headers."}>

Document the OPTIONS request and server decisions for methods or headers outside the safelist.

```js
// Preflight request sketch:
// OPTIONS /resource
// Origin: https://app.example
// Access-Control-Request-Method: PUT
// Access-Control-Request-Headers: content-type
```

**Predict before running:** The actual request proceeds only when the browser accepts relevant preflight response headers.

**Why it works:** Preflight is a browser negotiation, not a replacement for authorization.

**Proof it works:** Describe which response headers a server needs and why wildcard credentials cannot work.

</LessonStep>
