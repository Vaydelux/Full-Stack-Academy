## The problem we're solving

A generic first-element helper is widened to unknown, and callers lose the concrete element type without a compiler regression test. In a full-stack application, this boundary can lead to incorrect data or information disclosure even if the TypeScript project compiles successfully.

## Build the mental model

Type tests ensure a public API retains its intended compile-time relationship. Tools such as tsd can express this in dedicated packages, but the repository already has strict tsc and @ts-expect-error; use those to prove valid and invalid calls without installing another test dependency. Runtime assertions still cover the emitted code.

**Predict before running:** The public type preserves tuple literal information and rejects impossible assignments during tsc.

## Explore and verify

Use boundary-oriented reasoning: the outer layer receives unknown, the parser enforces shape and units, and only then may a domain function use a trusted type. Separate validation from authorization; a successful schema parse never proves the actor has permission.
