## The problem we're solving

A route receives a request for a lesson, fetches data server-side, creates a React Server Component payload, and hydrates only interactive islands.

**Symptom:** The starter starts hydration before creating server render output, reversing the required logical sequence.

## Build the mental model

Distinguish server data and RSC rendering from client hydration; hydration attaches interactivity to server-rendered UI.

**Predict first:** Server data precedes the RSC payload, HTML precedes hydration, and the list is immutable.

The local fixture tests only an isolated TypeScript/React contract; actual Server Component compilation, network transport, streaming, Server Actions, security isolation and browser hydration require a separate compiled Next.js 16 application and integration tests.

**Framework-oriented example (illustrative; needs real imports and infrastructure):**

```tsx
// Request lifecycle (conceptual, not one universal transport trace)
// 1. Server performs authorized data access and renders Server Component payload.
// 2. Next.js produces initial HTML for a full document request.
// 3. Browser displays HTML and React hydrates Client Components.
// 4. Subsequent navigations can request an RSC payload without full-page reload.
// 5. Client Components own interactive event handlers and local state.
```

**Boundary note:** Real streaming and navigation may interleave payload chunks; this five-step teaching model is intentionally conceptual. Verify the browser network waterfall and hydration rather than assuming all requests behave identically.

</LessonStep>
