## The problem we're solving

A project runs on the author's laptop but fails for a teammate after installing dependencies. A compatible version range can resolve differently over time. Lockfiles capture the chosen dependency graph so installations can be repeated.

## Build the mental model

package.json records scripts, version constraints and direct dependencies. A lockfile records resolved versions and usually integrity metadata. A caret range such as ^1.2.3 allows compatible minor and patch releases until the next major for a nonzero major. npm install may update the lockfile; npm ci requires a matching npm lock and starts from a clean node_modules. pnpm uses its own lockfile and a content-addressed store with linked dependency layouts. Choose one manager per project; the academy uses npm, while our full-stack architecture may use pnpm in a monorepo. Node 24 does not bundle Corepack by default; follow pnpm's official installation options if you use it. Install scripts can run code, so review dependencies before installation.

## Explore it yourself

Change the starter manifest's version temporarily, compare it to the lock root, regenerate the lock intentionally, then restore the lesson contract before testing. In a real project with dependencies, npm ci fails if the dependency declarations and lock disagree. Do not use npm audit fix --force blindly; inspect the proposed version and the breaking-change impact.

<Misconception claim={"A lockfile is a cache that should be ignored by Git."} correction={"Application lockfiles are versioned inputs for repeatable installs. Commit them with intentional manifest changes."} />

## Bug Hunt: diagnose before you change code

A teammate runs pnpm in an npm-managed project and commits a second lockfile. Agree on the manager, remove the accidental lock only after verifying it is unneeded, then use the original manager's frozen-install command.
