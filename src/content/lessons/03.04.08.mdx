## The problem we're solving

A custom tabs widget changes panel text but does not expose selected state or support Left/Right arrow navigation. Browser Interaction topics require both executable JavaScript logic and a real local HTML document. The fixture uses synthetic content with no external scripts, endpoints or data uploads.

## Build the mental model

Native buttons make tabs keyboard-focusable; a tablist needs matching tab/panel IDs, role=tab, aria-selected and correct roving tabindex. Arrow keys should move focus, Home/End may optionally jump, and hidden panels should be excluded from the accessibility tree. Validate focus and semantics in a real browser.

**Predict before running:** Click and arrow keys switch the selected tab, panel visibility and roving focus together.

<LessonStep number={2} title="Implement the browser-safe interaction" file="labs/js-widget/starter/index.html" expected={"Click and arrow keys switch the selected tab, panel visibility and roving focus together."}>

Replace the defective handler without discarding native elements or semantics. For untrusted content use `textContent`, not an unsafe HTML sink.

```js
const tabs=[...document.querySelectorAll('[role=tab]')];function activate(index){tabs.forEach((tab,i)=>{const selected=i===index;tab.setAttribute('aria-selected',String(selected));tab.tabIndex=selected?0:-1;document.getElementById(tab.getAttribute('aria-controls')).hidden=!selected;});tabs[index].focus();document.querySelector('#status').textContent=tabs[index].textContent+' active.';}tabs.forEach((tab,i)=>{tab.addEventListener('click',()=>activate(i));tab.addEventListener('keydown',event=>{if(event.key==='ArrowRight'||event.key==='ArrowLeft'){event.preventDefault();activate((i+(event.key==='ArrowRight'?1:-1)+tabs.length)%tabs.length);}if(event.key==='Home'||event.key==='End'){event.preventDefault();activate(event.key==='Home'?0:tabs.length-1);}});});
```

**Predict before running:** Click and arrow keys switch the selected tab, panel visibility and roving focus together.

**Why the repair works:** Native buttons make tabs keyboard-focusable; a tablist needs matching tab/panel IDs, role=tab, aria-selected and correct roving tabindex. Arrow keys should move focus, Home/End may optionally jump, and hidden panels should be excluded from the accessibility tree. Validate focus and semantics in a real browser.

**Proof:** Compare the resulting DOM and accessibility state to the instructor `solution/index.html` using the same input.

</LessonStep>

<LessonStep number={3} title="Test the state and boundary cases" file="labs/js-widget/solution.test.mjs" expected="Local logic tests and browser behavior checks agree under normal and edge cases.">

The core logic has a separate module with executable assertions, while the HTML fixture validates DOM binding and keyboard interactions.

```js
export function solve(index,delta,count){if(!Number.isInteger(index)||!Number.isInteger(delta)||!Number.isInteger(count)||count<1)throw new TypeError('Integer tab state required');return ((index+delta)%count+count)%count;}
assert.equal(solve(0,1,3),1);assert.equal(solve(2,1,3),0);assert.equal(solve(0,-1,3),2);assert.throws(()=>solve(0,1,0),TypeError);
```

**Predict before running:** Click and arrow keys switch the selected tab, panel visibility and roving focus together.

**Why it matters:** A passing algorithmic unit test does not prove its DOM wiring; use Chromium to exercise the actual handler.

**Proof:** Use ArrowRight on Overview, assert Resources has aria-selected=true and focus; use ArrowLeft to wrap back.

</LessonStep>
