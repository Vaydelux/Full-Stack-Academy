## The problem we're solving

A course index should show a meaningful loading placeholder while a segment streams, and an error notice if rendering fails.

**Failure:** The starter treats an error as a successful ready state and hides it from assistive technology.

## Build the mental model

Use loading.tsx for Suspense fallback, error.tsx as a client-rendered boundary, and explicit accessible status/error content.

**Prediction:** Loading announces progress, errors announce a failure, and ready has normal content.

**Proof boundary:** The local Node/TSX fixture verifies this lesson's deterministic model and initial React markup. It does **not** start Next.js, compile route conventions, simulate streaming, or prove HTTP status codes. A separately built Next application and browser/HTTP test are needed before release qualification.

```tsx
export type PageState='loading'|'ready'|'error';
export function SegmentNotice({state}:{state:PageState}){
 if(state==='loading')return <p role="status">Loading lesson…</p>;
 if(state==='error')return <p role="alert">Lesson could not load.</p>;
 return <p>Lesson ready</p>;
}
```

**Why it works:** Use loading.tsx for Suspense fallback, error.tsx as a client-rendered boundary, and explicit accessible status/error content.

**Real App Router shape:**

```tsx
// app/guides/loading.tsx
export default function Loading() {
  return <p role="status">Loading guide…</p>;
}
// app/guides/error.tsx (must be a Client Component)
'use client';
export default function ErrorView({reset}:{error:Error;reset:()=>void}) {
  return <div role="alert"><p>Could not load guide.</p><button onClick={reset}>Retry</button></div>;
}
```

**Nuance:** Error boundaries cannot catch every class of error (including their own throws). Streaming, status codes and network data are integration concerns; a static notice fixture does not prove Next's actual boundary lifecycle.

</LessonStep>
