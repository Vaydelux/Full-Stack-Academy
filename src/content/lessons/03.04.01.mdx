## The problem we're solving

A click handler updates a variable but never updates the accessible output displayed in the document. Browser Interaction topics require both executable JavaScript logic and a real local HTML document. The fixture uses synthetic content with no external scripts, endpoints or data uploads.

## Build the mental model

querySelector locates a DOM element and addEventListener subscribes to an explicit event. Changing a JavaScript variable does not update the DOM until code assigns a safe property such as textContent. Native buttons already support keyboard activation.

**Predict before running:** Activating the native button announces an incremented numerical status.

## Guided implementation

<LessonStep number={1} title="Reproduce the browser interaction defect" file="labs/js-dom/starter/index.html" expected={"A click handler updates a variable but never updates the accessible output displayed in the document."}>

Observe the starter with keyboard and pointer input, then inspect what actually changes in the DOM. The sample contains the following intentionally defective handler:

```js
let count=0;document.querySelector('#add').addEventListener('click',()=>{count++;});
```

**Predict before running:** A click handler updates a variable but never updates the accessible output displayed in the document.

**Why it fails:** querySelector locates a DOM element and addEventListener subscribes to an explicit event. Changing a JavaScript variable does not update the DOM until code assigns a safe property such as textContent. Native buttons already support keyboard activation.

**Proof:** Click the button twice and inspect output.textContent; verify keyboard activation with Enter.

</LessonStep>

<LessonStep number={2} title="Implement the browser-safe interaction" file="labs/js-dom/starter/index.html" expected={"Activating the native button announces an incremented numerical status."}>

Replace the defective handler without discarding native elements or semantics. For untrusted content use `textContent`, not an unsafe HTML sink.

```js
let count=0;document.querySelector('#add').addEventListener('click',()=>{count++;document.querySelector('#status').textContent=String(count);});
```

**Predict before running:** Activating the native button announces an incremented numerical status.

**Why the repair works:** querySelector locates a DOM element and addEventListener subscribes to an explicit event. Changing a JavaScript variable does not update the DOM until code assigns a safe property such as textContent. Native buttons already support keyboard activation.

**Proof:** Compare the resulting DOM and accessibility state to the instructor `solution/index.html` using the same input.

</LessonStep>

<LessonStep number={3} title="Test the state and boundary cases" file="labs/js-dom/solution.test.mjs" expected="Local logic tests and browser behavior checks agree under normal and edge cases.">

The core logic has a separate module with executable assertions, while the HTML fixture validates DOM binding and keyboard interactions.

```js
export function solve(count){if(!Number.isInteger(count)||count<0)throw new TypeError('Nonnegative count required');return count+1;}
assert.equal(solve(0),1);assert.equal(solve(9),10);assert.throws(()=>solve(-1),TypeError);
```

**Predict before running:** Activating the native button announces an incremented numerical status.

**Why it matters:** A passing algorithmic unit test does not prove its DOM wiring; use Chromium to exercise the actual handler.

**Proof:** Click the button twice and inspect output.textContent; verify keyboard activation with Enter.

</LessonStep>
