## The problem we're solving

An API handler trusts a request body as TypeScript, accepts unknown fields, and returns a domain object even when required values are invalid. In a full-stack application, this boundary can lead to incorrect data or information disclosure even if the TypeScript project compiles successfully.

## Build the mental model

A schema-first boundary validates unknown data before constructing domain types. Zod 4 strictObject rejects unknown keys; safeParse gives a typed discriminated result. An educational local contract does not implement authentication, authorization or production transaction guarantees.

**Predict before running:** Only strict validated API request bodies enter the domain; extra keys and invalid quantities are rejected.

<LessonStep number={2} title="Validate and map a trusted domain value" file="labs/ts-schema-api/starter/solution.ts" expected={"Only strict validated API request bodies enter the domain; extra keys and invalid quantities are rejected."}>

Use unknown at the boundary, a runtime predicate or strict schema and a public result type. Handle expected invalid data explicitly.

```ts
import {z} from 'zod';const Schema=z.strictObject({sku:z.string().min(1).max(40),qty:z.number().int().nonnegative().max(100000)});export type InventoryRequest=z.infer<typeof Schema>;export function solve(raw:unknown):{ok:true;data:InventoryRequest}|{ok:false;error:'invalid-body'}{const parsed=Schema.safeParse(raw);return parsed.success?{ok:true,data:parsed.data}:{ok:false,error:'invalid-body'};}
```

**Predict before running:** Only strict validated API request bodies enter the domain; extra keys and invalid quantities are rejected.

**Why the repair works:** A schema-first boundary validates unknown data before constructing domain types. Zod 4 strictObject rejects unknown keys; safeParse gives a typed discriminated result. An educational local contract does not implement authentication, authorization or production transaction guarantees.

**Proof:** Compare clean and malformed cases against the verified instructor module.

</LessonStep>

assert.deepEqual(solve({sku:'SKU-1',qty:3}),{ok:true,data:{sku:'SKU-1',qty:3}});assert.deepEqual(solve({sku:'SKU-1',qty:-1}),{ok:false,error:'invalid-body'});assert.deepEqual(solve({sku:'SKU-1',qty:3,admin:true}),{ok:false,error:'invalid-body'});assert.deepEqual(solve(null),{ok:false,error:'invalid-body'});

**Predict before running:** Invalid external input never enters the typed domain as though it had passed validation.

**Why this matters:** A compiler's assurances apply to typed source relationships, not arbitrary strings from a network or storage boundary.

## Explore and verify

Use boundary-oriented reasoning: the outer layer receives unknown, the parser enforces shape and units, and only then may a domain function use a trusted type. Separate validation from authorization; a successful schema parse never proves the actor has permission.
