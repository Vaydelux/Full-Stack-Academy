## The problem we're solving

An error handler leaks raw error objects and assumes every caught rejection is an Error instance. In a full-stack application, this boundary can lead to incorrect data or information disclosure even if the TypeScript project compiles successfully.

## Build the mental model

A JavaScript catch value is unknown. Narrow Error safely and map expected failures to a discriminated Result; never echo arbitrary objects or internal stack traces to the client. Unexpected failures may need structured logging at the application boundary.

**Predict before running:** Expected failures produce safe public error codes without leaking sensitive rejection text.

<LessonStep number={2} title="Validate and map a trusted domain value" file="labs/ts-typed-errors/starter/solution.ts" expected={"Expected failures produce safe public error codes without leaking sensitive rejection text."}>

Use unknown at the boundary, a runtime predicate or strict schema and a public result type. Handle expected invalid data explicitly.

```ts
export type Result={ok:true;value:string}|{ok:false;error:string};export function solve(input:unknown):Result{if(typeof input==='string'&&input.trim())return {ok:true,value:input.trim()};if(input instanceof Error)return {ok:false,error:input.name==='TypeError'?'invalid-type':'operation-failed'};return {ok:false,error:'invalid-input'};}
```

**Predict before running:** Expected failures produce safe public error codes without leaking sensitive rejection text.

**Why the repair works:** A JavaScript catch value is unknown. Narrow Error safely and map expected failures to a discriminated Result; never echo arbitrary objects or internal stack traces to the client. Unexpected failures may need structured logging at the application boundary.

**Proof:** Compare clean and malformed cases against the verified instructor module.

</LessonStep>

<LessonStep number={3} title="Exercise the successful and rejected cases" file="labs/ts-typed-errors/solution.test.mjs" expected="The same offline tests distinguish valid and invalid input without hidden network state.">

```ts
assert.deepEqual(solve(' ok '),{ok:true,value:'ok'});assert.deepEqual(solve(new TypeError('password=secret')),{ok:false,error:'invalid-type'});assert.deepEqual(solve({password:'secret'}),{ok:false,error:'invalid-input'});
```

**Predict before running:** Invalid external input never enters the typed domain as though it had passed validation.

**Why this matters:** A compiler's assurances apply to typed source relationships, not arbitrary strings from a network or storage boundary.

## Explore and verify

Use boundary-oriented reasoning: the outer layer receives unknown, the parser enforces shape and units, and only then may a domain function use a trusted type. Separate validation from authorization; a successful schema parse never proves the actor has permission.
