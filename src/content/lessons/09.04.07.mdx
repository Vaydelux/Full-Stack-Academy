## The problem we're solving

A remote task list already belongs in the server query cache, but an engineer copies whole task objects into Zustand and creates inconsistent stale data.

**Broken behavior:** The starter stores and exposes a private copy of remote task data in shared UI state.

## Build the mental model

Store only UI selection or preferences in Zustand; keep authoritative remote records in a server/query cache and derive the chosen record by ID.

**Predict:** Zustand stores just the selected ID and actions; record details come from the authoritative provided collection.

**Evidence boundary:** The local test imports the real Zustand 5 `createStore` API and, where appropriate, the official middleware. The store is created afresh per test; it does not use a global request-scoped server singleton. Passing Node assertions does not prove browser hydration, cross-tab synchronization or HTTP authorization.

```ts
import {createStore} from 'zustand/vanilla';
export type Selection={selectedId:string|null;select:(id:string|null)=>void};
export function makeSelectionStore(){return createStore<Selection>()(set=>({
 selectedId:null,select:selectedId=>set({selectedId}),
}));}
export function selectedTask<T extends {id:string}>(rows:readonly T[],id:string|null):T|null{
 return id?rows.find(row=>row.id===id)??null:null;
}
```

**Reasoning:** Store only UI selection or preferences in Zustand; keep authoritative remote records in a server/query cache and derive the chosen record by ID.

```tsx
// UI state only: selectedTaskId, showDetails, user-visible table density.
// Remote data stays in a validated API response / TanStack Query cache,

// This avoids stale data drift and accidental multi-user record leakage.
```

**Trust boundary:** Never treat a UI role, selected row or persisted browser token as server authorization. Query data and private records still require server-side validation and access controls.
