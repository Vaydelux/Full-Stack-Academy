## The problem we're solving

A 'Show help' button inside a form unexpectedly submits it. A reset button erases filled fields, and a server receives nothing because the controls have IDs but no `name` attributes.

## Build the mental model

Buttons inside forms default to submit unless a type is specified. Choose `type=submit` for submission, `type=button` for local actions and `type=reset` only when intentionally clearing input. Successful form controls submit their `name` and value; disabled fields are omitted. GET encodes form data into the URL and is appropriate for safe search queries, not secrets. POST sends a request body and can change server state; this lesson stays offline. The local example navigates to a bundled static receipt with a query string, demonstrating GET encoding without storing data on a server.

**Predict before running:** What happens when a `<button>` lacks `type` inside a form? It acts as a submit control unless other context changes its association.

## Bug Hunt: identify the root cause

A help button unexpectedly triggers GET navigation because it has no `type`. Change it to `type=button`, test by clicking it, and confirm location remains on the form.
