## The problem we're solving

The starter reports no operation ID errors even after a new endpoint reuses an existing operationId. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

Operation IDs used by SDK generators should be stable, unique and safe identifiers; examples should match their documented schema and not contain credentials.

**Expected outcome:** The canonical contract has no issues; duplicates, missing IDs and unsafe names are detected.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. Operation IDs are an SDK stability contract, not authorization or sanitization for arbitrary user-supplied scripts.

```js
export function operationIdIssues(document){
 const issues=[];const seen=new Set();
 for(const [route,verbs] of Object.entries(document?.paths??{})){
  for(const [method,operation] of Object.entries(verbs)){
   if(!['get','post','put','patch','delete'].includes(method))continue;
   const id=operation?.operationId;
   if(typeof id!=='string'||!/^[A-Za-z_$][\w$]*$/.test(id)||['__proto__','constructor','prototype'].includes(id))issues.push('invalid '+method+' '+route);
   else if(seen.has(id))issues.push('duplicate '+id);
   else seen.add(id);
  }
 }
 return issues;
}
```
