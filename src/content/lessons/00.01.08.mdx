## The problem we're solving

A bug report says the website stopped loading. That is not enough evidence to know what broke. A useful report describes the reproduction, expected result, actual status, request identity, timings and the layer where failure occurred.

## Build the mental model

Combine the module: a URL identifies the origin and path; local resolution and transport connect the client; an HTTP request arrives at a server route; the response contains status, headers and a body; the browser uses the result. A correlation ID allows a developer to match a response to one server event. In production traces span multiple services, and sensitive headers or bodies must not be logged. This lab uses a local Node HTTP server with synthetic records. Its request IDs are generated by the server rather than trusted from the client.

**Predict first:** If DevTools shows 404 and the server logs that request ID, was DNS necessarily broken? No. The request reached a server and got an application response.

<LessonStep number={1} title={"Create a diagnostic response helper"} file="labs/devtools-trace/starter/exercise.mjs" expected={"Every response includes X-Request-Id and an accurate content type."}>

Generate an ID for each request. Do not accept arbitrary client-supplied IDs as trusted log data. Start with a helper that writes the status and header.

```js
import {randomUUID} from 'node:crypto';
function send(res,id,status,body,type='application/json') {
  res.writeHead(status,{'Content-Type':type,'X-Request-Id':id,'Cache-Control':'no-store'});
  res.end(type==='application/json'?JSON.stringify(body):body);
}
```

</LessonStep>

<LessonStep number={2} title={"Implement a page, success route and failure route"} file="labs/devtools-trace/starter/exercise.mjs" expected={"The document loads a button; the API returns 200 or 404 with a matching request ID."}>

Use the full fixture in your starter's createApp function. The page makes same-origin requests; the logger records only the request ID, method, fixed route category and status.

```js
import {createServer} from 'node:http';
export function createApp(log=console.log) {
  return createServer((req,res)=>{
    const id=randomUUID();
    const path=new URL(req.url,'http://127.0.0.1').pathname;
    let status=404;
    if(req.method==='GET'&&path==='/'){
      status=200;
      send(res,id,status,`<!doctype html><meta charset="utf-8"><title>Trace lab</title><h1>Trace lab</h1><button id="good">Load project</button><button id="bad">Missing project</button><pre id="output"></pre><script>
async function load(path){const output=document.querySelector('#output');try{const r=await fetch(path);output.textContent=r.status+' '+r.headers.get('x-request-id')+' '+await r.text();}catch{output.textContent='Network failure';}}
document.querySelector('#good').onclick=()=>load('/api/project');document.querySelector('#bad').onclick=()=>load('/api/missing');
</script>`,'text/html; charset=utf-8');
    }else if(req.method==='GET'&&path==='/api/project'){
      status=200; send(res,id,status,{project:'Platform'});
    }else send(res,id,status,{error:'Not found'});
    log({id,method:req.method,route:path==='/'?'page':path==='/api/project'?'project':'unknown',status});
  });
}
```

</LessonStep>

## Explore it yourself

Write a short debugging report: environment (localhost and browser), reproduction steps, expected behavior, actual HTTP status, request ID, whether a server log exists, and proposed fix. Use only the synthetic request IDs. Do not export an unredacted HAR from a signed-in production website because it may contain credentials or personal data. For this fixture, the missing route is intentional; the correct fix in a real app would be based on whether the route or client URL was wrong.

<Misconception claim={"Every browser network error is a backend exception."} correction={"A failed lookup or connection may never reach the backend. A recorded response and request ID provide evidence that it did."} />

## Bug Hunt: diagnose before you change code

The developer logs every cookie and authorization header to debug slow requests. Remove that data. Use a request ID, method, route template, status and duration, with controlled error details. Reproduce with synthetic data.
