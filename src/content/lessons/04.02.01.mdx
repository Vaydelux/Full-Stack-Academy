## The problem we're solving

A reusable selector returns the first record instead of the record with the requested ID, and the API accepts objects without IDs. This advanced-types lab requires both compile-time evidence and meaningful runtime behavior; TypeScript's erased types alone cannot fix logic bugs.

## Build the mental model

A generic preserves a relationship between input and output types. `T extends {id:string}` constrains the required property while retaining extra fields in the returned item. At runtime, find must still check the requested ID rather than trusting the type parameter.

**Predict before running:** The generic function returns the matching item with all of its original extra properties.

<LessonStep number={2} title="Implement the correct type/runtime relationship" file="labs/ts-generics/starter/solution.ts" expected={"The generic function returns the matching item with all of its original extra properties."}>

Preserve exported `solve` and tighten the behavior without adding an unsound `as any` cast.

```ts
export function solve<T extends {id:string}>(items:readonly T[],id:string):T|undefined{return items.find(item=>item.id===id);}
```

**Predict before running:** The generic function returns the matching item with all of its original extra properties.

**Why the fix works:** A generic preserves a relationship between input and output types. `T extends {id:string}` constrains the required property while retaining extra fields in the returned item. At runtime, find must still check the requested ID rather than trusting the type parameter.

**Proof:** The same Node test now passes; the separate compiler-negative test rejects invalid static usage.

</LessonStep>
