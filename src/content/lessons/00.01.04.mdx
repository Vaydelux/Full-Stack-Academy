## The problem we're solving

A browser shows a certificate warning for your API. The IP address may resolve and a TCP connection may succeed, but the HTTPS connection is not trusted. Treat these as different layers, not one generic network error.

## Build the mental model

TCP establishes an ordered reliable byte stream. TLS negotiates encryption, authenticates the server using a certificate chain and protects data against interception and tampering; it normally checks the intended hostname against certificate identities. HTTPS is HTTP over a secure transport (HTTP/1.1 and HTTP/2 commonly use TLS over TCP; HTTP/3 uses QUIC over UDP). TLS protects data in transit, not authorization, server integrity or data at rest. Certificates also require a trusted chain, validity period, and other checks; checking a name alone is not full TLS verification.

**Predict first:** If a certificate is valid for api.example.com, can it automatically be trusted for admin.example.com? No. The hostname must match an identity covered by the certificate.

<LessonStep number={2} title={"Inspect a target URL"} file="labs/tcp-tls-https/starter/exercise.mjs" expected={"HTTPS defaults to port 443 and HTTP to port 80; explicit ports override defaults."}>

This helper describes the URL; it does not prove connectivity or encryption. A successful TCP test is not an HTTPS certificate verification.

```js
export function transportInfo(input) {
  const url = new URL(input);
  if (!['http:', 'https:'].includes(url.protocol)) throw new Error('HTTP(S) only');
  return { host: url.hostname, port: Number(url.port || (url.protocol === 'https:' ? 443 : 80)), encrypted: url.protocol === 'https:' };
}
```

</LessonStep>

<LessonStep number={3} title={"Check the certificate's hostname identity"} file="labs/tcp-tls-https/starter/exercise.mjs" expected={"The matching hostname passes and a different hostname fails."}>

Use Node's checkServerIdentity with a synthetic certificate object. This is a focused hostname test, NOT a real certificate chain or handshake test. Never set rejectUnauthorized:false to make a production request work.

```js
import { checkServerIdentity } from 'node:tls';
export function verifyIdentity(hostname, subjectaltname) {
  const error = checkServerIdentity(hostname, { subjectaltname });
  return error ? { ok: false, code: error.code } : { ok: true };
}
```

</LessonStep>

## Explore it yourself

Open an HTTPS site you trust and inspect its certificate using the browser Security panel or site information. Compare its subject alternative names, issuer and validity period. Do not bypass a browser security warning. The TCP exercise intentionally uses plain text on loopback; it is not a TLS server.

## Bug Hunt: diagnose before you change code

A developer disables TLS verification when a staging hostname does not match the certificate. Fix the DNS name or obtain a certificate containing the correct hostname; retain normal verification and investigate the certificate chain.
