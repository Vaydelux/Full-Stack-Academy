## The problem we're solving

A UI card has been judged by a single desktop screenshot and misses mobile, RTL, keyboard, reduced-motion and dark-theme regressions. A code review should require a reproducible symptom and realistic verification, not only a polished image. The local fixture is synthetic, deterministic and offline.

## Build the mental model

A defensible UI QA gate separates five observable dimensions: responsive geometry, keyboard focus, directional styling, motion preference, and theme/contrast (20 points each in this local rubric). Automated checks can verify selected styles, but human inspection and assistive technology are still required for complete accessibility acceptance. A 100-point rubric is a review structure, not a measured performance score.

**Predict before running:** The card fits 320px, RTL flips its accent border, keyboard focus is visible, and motion/color-scheme preferences have explicit rules.

Apply the narrowly targeted instructor change. This is an educational repair, not a claim that browsers will use a particular GPU layer, font-loading timeline or screen-reader announcement.

```css
.qa { box-sizing: border-box; inline-size: min(100%, 46rem); padding-inline: 1.25rem; border-inline-start: 4px solid #075e7b; background: light-dark(#ffffff, #172f44); color: light-dark(#19354a, #f8fafc); color-scheme: light dark; } .qa-action:focus-visible { outline: 3px solid #c45105; outline-offset: 3px; } .qa-action { transition: transform 160ms ease; } @media (prefers-reduced-motion: reduce) { .qa-action { transition: none; } }
```

## Explore and verify

Use DevTools to inspect computed styles and the Performance recording when making speed claims. Not every transform is composited; not every font loading strategy removes CLS; not every visually distinct control is accessible. The Node tests check instructor patterns; the isolated browser suite observes representative states. Manual assistive-technology and cross-browser checks remain outside the automated guarantee.
