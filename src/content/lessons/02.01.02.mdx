## The problem we're solving

A component's text remains gray even after its developer writes a class selector to color the headline. Our task is to repair the actual style behavior, not just make a static screenshot look convincing. This workshop uses synthetic content in a standalone offline HTML file; it needs no account, cloud API or deployed preview.

## Build the mental model

The cascade resolves origin and importance, cascade layers, specificity, scoping proximity and source order; inheritance applies only when no cascaded value is set on the element. A direct author declaration wins over an inherited property from a parent, irrespective of that parent's specificity.

**Predict before running:** The headline is blue-green even though the card's paragraph stays gray.

```css

```

**Proof:** Open DevTools, select the target element, and confirm the failing computed property. Write the observed value before replacing the rule.

</LessonStep>

<LessonStep number={2} title="Apply the targeted CSS repair" file="labs/css-cascade/starter/index.html" expected="The headline is blue-green even though the card's paragraph stays gray.">

Replace the incorrect rule with the following CSS. Keep the native HTML controls and all semantic content unchanged.

```css
.card .headline { color: #075e7b; }
```

**Predict before running:** The headline is blue-green even though the card's paragraph stays gray.

**Why it works:** The cascade resolves origin and importance, cascade layers, specificity, scoping proximity and source order; inheritance applies only when no cascaded value is set on the element. A direct author declaration wins over an inherited property from a parent, irrespective of that parent's specificity.

**Proof:** getComputedStyle(headline).color differs from the card's paragraph color.

</LessonStep>

<LessonStep number={3} title="Verify responsiveness and interaction" file="labs/css-cascade/starter/index.html" expected="The repaired solution works at narrow and wide viewports without hiding keyboard focus or producing horizontal overflow.">

Use DevTools Responsive Design Mode: select a 320px width, then a wide desktop width. Inspect the relevant computed style again. Where the lab includes a button or writing-direction toggle, test it using Tab and Enter.

```js
const target = document.querySelector('.card');
console.log(getComputedStyle(target).boxSizing);
console.log(document.documentElement.scrollWidth <= innerWidth);
```

**Predict before running:** A visible computed property changes as described, but the document remains scrollable normally with no unwanted horizontal overflow.

**Why it works:** Browser-computed styles and measured dimensions describe actual rendered rules, rather than assuming the presence of source text is enough.

**Proof:** Compare the computed result with the instructor solution and record one failing case from the original starter.

</LessonStep>
