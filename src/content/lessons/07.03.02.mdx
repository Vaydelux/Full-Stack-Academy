## The problem we're solving

A public course directory can be cached, but a user's enrollment state is request-specific and must never be part of a globally reused response.

**Failure mode:** The starter combines public and private data in a single shared cache scope.

## Build the mental model

Split stable public content from request-personalized data; use cache directives only around safe public computations. This module specifically uses **Next.js 16 with `cacheComponents: true`**; avoid mixing with the legacy `dynamic`, route-segment `revalidate` or `fetchCache` configuration model. The offline assertions are data/decision models; they do not access Next's actual cache internals, HTTP, or database.

**Expected behavior:** A public catalogue is eligible for a shared cache, while a personalized enrollment list is forced dynamic.

**Framework example (illustrative; not executed here):**

```tsx
// app/courses/PublicCatalogue.tsx
import { cacheLife } from 'next/cache';
export async function PublicCatalogue(){
 'use cache';
 cacheLife('hours');
 const courses=await getPublicCourses();
 return <ul>{courses.map(c=><li key={c.id}>{c.title}</li>)}</ul>;
}
// Personalized status is rendered outside this cached component after an auth check.
```

**Operational nuance:** The string 'use cache' applies only under a configured Cache Components mode. Do not mix legacy route-segment `revalidate` exports with Cache Components conventions.
