## The problem we're solving

A large hero image is the primary contentful element, but it has no intrinsic dimensions and can cause a layout shift on load.

**Defect:** The starter produces a plan without dimensions, which cannot reserve stable space.

## Build the mental model

Reserve intrinsic image dimensions and use the Next Image component with a responsive sizes value; prioritize only an actual LCP candidate.

**Predict before running:** Hero and regular imagery preserve positive width/height, while only the hero is marked preload-worthy.

The academy exercises reviewed TypeScript/React logic locally. It does not automatically exercise the Next.js Metadata API, search crawler, browser page loading, network waterfall, Lighthouse or real-user field metrics. Those are separate qualification gates.

```tsx
export function imagePlan(width:number,height:number,hero:boolean){
 if(!Number.isSafeInteger(width)||!Number.isSafeInteger(height)||width<=0||height<=0)throw new RangeError('Invalid image dimensions');
 return {width,height,preload:hero,sizes:'(max-width: 768px) 100vw, 720px'};
}
```

**Root principle:** Reserve intrinsic image dimensions and use the Next Image component with a responsive sizes value; prioritize only an actual LCP candidate.

</LessonStep>

**Next.js 16 usage pattern (illustrative):**

```tsx
import Image from 'next/image';
export function Hero(){return <Image src="/hero.webp" alt="Study workspace" width={1440} height={900}

// Use next/font for self-hosted optimized fonts and avoid layout shifts from font swapping.
```

**Production nuance:** Preloading every large image can worsen network contention. Measure LCP on representative phones and keep dimensions/aspect ratio stable. The fixture does not measure image decoding.
