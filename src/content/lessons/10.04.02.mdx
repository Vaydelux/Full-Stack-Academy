## The problem we're solving

The starter claims every API document has valid response contracts, even when the success response or requestBody is absent. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

Every operation must document its media types, required request body and actual status-specific response schema; 201 and 422 have distinct meanings.

**Expected outcome:** The complete notes contract passes; removing the POST body or 201 response fails.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. The source assertion checks a bounded fixture, not every possible JSON Schema/OpenAPI semantic. Use a maintained validator as part of a full CI contract gate.

```js
export function hasTaskContracts(document){
 const listing=document?.paths?.['/api/notes']?.get;
 const creation=document?.paths?.['/api/notes']?.post;
 return Boolean(listing?.responses?.['200']?.content?.['application/json']?.schema&&
  creation?.requestBody?.required===true&&
  creation?.requestBody?.content?.['application/json']?.schema&&
  creation?.responses?.['201']?.content?.['application/json']?.schema&&
  creation?.responses?.['422']);
}
```
