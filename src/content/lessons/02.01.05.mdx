## The problem we're solving

A fixed-size heading clips when readers zoom or enlarge text. Our task is to repair the actual style behavior, not just make a static screenshot look convincing. This workshop uses synthetic content in a standalone offline HTML file; it needs no account, cloud API or deployed preview.

## Build the mental model

rem follows the root font size, em follows the local element's font size (or parent for font-size itself), and ch tracks the zero glyph. clamp() combines a readable floor, fluid middle and ceiling; pixels remain useful for one-pixel borders. Test browser zoom and user font preferences rather than assuming vw alone is accessible.

**Predict before running:** The heading remains at least 1.5rem and responds to viewport changes.

</LessonStep>

<LessonStep number={2} title="Apply the targeted CSS repair" file="labs/css-typography/starter/index.html" expected="The heading remains at least 1.5rem and responds to viewport changes.">

Replace the incorrect rule with the following CSS. Keep the native HTML controls and all semantic content unchanged.

```css
.card h2 { font-size: clamp(1.5rem, 2vw + 1rem, 2.5rem); line-height: 1.2; }
```

**Predict before running:** The heading remains at least 1.5rem and responds to viewport changes.

**Why it works:** rem follows the root font size, em follows the local element's font size (or parent for font-size itself), and ch tracks the zero glyph. clamp() combines a readable floor, fluid middle and ceiling; pixels remain useful for one-pixel borders. Test browser zoom and user font preferences rather than assuming vw alone is accessible.

**Proof:** Compare computed font size at narrow and wide viewports and after increasing root font size.

</LessonStep>

<LessonStep number={3} title="Verify responsiveness and interaction" file="labs/css-typography/starter/index.html" expected="The repaired solution works at narrow and wide viewports without hiding keyboard focus or producing horizontal overflow.">

Use DevTools Responsive Design Mode: select a 320px width, then a wide desktop width. Inspect the relevant computed style again. Where the lab includes a button or writing-direction toggle, test it using Tab and Enter.

```js
const target = document.querySelector('.card');
console.log(getComputedStyle(target).boxSizing);
console.log(document.documentElement.scrollWidth <= innerWidth);
```

**Predict before running:** A visible computed property changes as described, but the document remains scrollable normally with no unwanted horizontal overflow.

**Why it works:** Browser-computed styles and measured dimensions describe actual rendered rules, rather than assuming the presence of source text is enough.

**Proof:** Compare the computed result with the instructor solution and record one failing case from the original starter.

</LessonStep>
