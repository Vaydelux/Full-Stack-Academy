## The problem we're solving

A developer nests a rule for a nonexistent class, leaving the card's actual label unstyled. We will repair a specific CSS behavior in an offline component so that a future design system has predictable boundaries. There is no external font, image or API dependency.

## Build the mental model

Native CSS nesting lets related selectors live together. The & nesting selector represents the parent rule, and nested descendants still follow ordinary cascade and specificity rules. Nesting improves organization, not isolation; overdeep selector chains can still make maintenance difficult.

**Predict before running:** The label takes the accent color, and keyboard focus within the panel shows a visible outline.

<LessonStep number={2} title="Repair the theme, selector, or state rule" file="labs/css-nesting/starter/index.html" expected={"The label takes the accent color, and keyboard focus within the panel shows a visible outline."}>

Replace only the defective style block with this instructor implementation. Preserve native labels, buttons and focus order. Do not use blanket `!important` overrides to hide a state problem.

```css
.demo { & .label { color: #075e7b; font-weight: 700; } &:focus-within { outline: 3px solid #c45105; outline-offset: 3px; } }
```

**Predict before running:** The label takes the accent color, and keyboard focus within the panel shows a visible outline.

**Why the repair works:** Native CSS nesting lets related selectors live together. The & nesting selector represents the parent rule, and nested descendants still follow ordinary cascade and specificity rules. Nesting improves organization, not isolation; overdeep selector chains can still make maintenance difficult.

**Proof:** Compare the computed style against the unchanged starter using the exact same browser setting.

</LessonStep>

<LessonStep number={3} title="Test adjacent states and regression limits" file="labs/css-nesting/starter/index.html" expected="The intended state is measurable without regressing keyboard access, viewport sizing or legibility.">

At a 320px viewport and a wide layout, inspect the affected component; where relevant, toggle checked state, reduced motion, dark preference, local tokens or writing direction. Do not infer appearance from a CSS source string alone.

```js
const box = document.querySelector('#demo');
const style = getComputedStyle(box);
console.log({ background: style.backgroundColor, color: style.color, overflow: document.documentElement.scrollWidth > innerWidth });
```

**Predict before running:** The corrected component's computed state is consistent with the browser preference or native input state, and there is no unexpected horizontal page overflow.

**Why it works:** Computed styles combine the cascade, media features, supported CSS functions and the current DOM state.

**Proof:** Inspect the matched nested .label rule and the panel's computed outline when the input is focused.

</LessonStep>

## Explore and verify

A syntactically valid color, selector or animation is not necessarily accessible or performant. Test color contrast for actual foreground/background pairs; preserve focus, reduced-motion behavior and narrow layouts. The Node fixture assertions check reviewed CSS patterns, and Chromium independently checks representative rendered behavior. Neither constitutes a full multi-device accessibility certification.
