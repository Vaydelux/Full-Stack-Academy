## The problem we're solving

A notification request uses either an email destination or an SMS phone, but never both. Broad union branches allow invalid channel values.

**Broken behavior:** The starter accepts unknown channels and unchecked destination strings.

## Build the mental model

Use z.discriminatedUnion on a literal channel and define strict, branch-specific fields with validated values.

**Predict before coding:** Valid email/sms requests parse; unknown channel, invalid email and short phone are rejected.

**Important boundary:** TypeScript types are erased at runtime. These exercises import Zod 4 from the repository's locked dependencies and run actual `safeParse` or `parse` assertions, not simulated validation. Runtime validation does not authenticate a caller, authorize object access, or persist data.

<LessonStep number={2} title="Implement the Zod 4 schema and typed output" file="labs/zod-discriminated-requests/starter/solution.ts" expected="Valid email/sms requests parse; unknown channel, invalid email and short phone are rejected.">

```ts
import * as z from 'zod';
export const Delivery=z.discriminatedUnion('channel',[
 z.strictObject({channel:z.literal('email'),address:z.email()}),
 z.strictObject({channel:z.literal('sms'),phone:z.string().regex(/^\+[1-9]\d{7,14}$/)}),
]);
```

**Why this works:** Use z.discriminatedUnion on a literal channel and define strict, branch-specific fields with validated values.

</LessonStep>

import * as z from 'zod';

// TS narrows switch(event.kind) after successful parse; never assume inputs are valid before parse.
