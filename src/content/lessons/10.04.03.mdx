## The problem we're solving

The starter accepts a contract where protected note operations have no bearer requirement. API schemas, operation IDs, examples, authorization descriptions and client integrations must remain consistent across changes.

## Build the mental model

Declare bearer authentication as an HTTP security scheme, require it on protected operations, and mark health explicitly public.

**Expected outcome:** Only the declared BearerAuth security scheme protects GET and POST notes, while health remains public.

**Version and scope:** This module uses OpenAPI Specification **3.1.1** and one checked-in JSON contract at `examples/task-contract/task-api.openapi.json`. The smallest client generator is deliberately restricted to static, trusted GET/POST operations. A documented bearer scheme cannot authorize an HTTP request. Actual servers need token verification, identity and resource ownership controls.

```js
export function secureOperations(document){
 const scheme=document?.components?.securitySchemes?.BearerAuth;
 if(scheme?.type!=='http'||scheme.scheme!=='bearer')return false;
 if(JSON.stringify(document.paths?.['/health']?.get?.security)!=='[]')return false;
 for(const method of ['get','post']){
  const list=document?.paths?.['/api/notes']?.[method]?.security;
  if(!Array.isArray(list)||!list.some(item=>Object.hasOwn(item,'BearerAuth')&&Array.isArray(item.BearerAuth)&&item.BearerAuth.length===0))return false;
 }
 return true;
}
```

**Why this corrects the contract:** Declare bearer authentication as an HTTP security scheme, require it on protected operations, and mark health explicitly public.

</LessonStep>
