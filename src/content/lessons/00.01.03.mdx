## The problem we're solving

Your deployed app works on one domain but another says the name cannot be resolved. Rebuilding React will not repair a missing DNS record. First identify whether the failure is name resolution, network routing, TLS, or the HTTP application.

## Build the mental model

A domain is a human-readable name in a hierarchical naming system. A URL also contains a scheme, optional port, path, query and fragment. DNS translates names into records such as A (IPv4), AAAA (IPv6), and CNAME (canonical name aliases). A recursive resolver may cache a response for its TTL; it may obtain answers from authoritative servers. A name can resolve to several addresses, and a CDN can return different addresses by location. Resolving a name does not prove an HTTP service is reachable. Node's dns.lookup uses operating-system name resolution (including local hosts configuration), while dns.resolve4 queries DNS records. They are not interchangeable.

**Predict first:** Does changing /api/projects in a URL change the DNS lookup? No. DNS resolves the hostname, not the request path.

<LessonStep number={1} title={"Inspect URL components"} file="labs/dns-domains/starter/exercise.mjs" expected={"The parsed result contains hostname, scheme and port, never the path as a hostname."}>

Use the built-in URL parser instead of splitting on slashes. Explicit ports and IPv6 literals otherwise cause subtle bugs.

```js
export function inspect(input) {
  const url = new URL(input);
  if (!['http:', 'https:'].includes(url.protocol)) throw new Error('HTTP(S) only');
  return {hostname: url.hostname, protocol: url.protocol, port: url.port || (url.protocol === 'https:' ? '443' : '80'), path: url.pathname};
}
```

</LessonStep>

<LessonStep number={2} title={"Resolve through the operating system"} file="labs/dns-domains/starter/exercise.mjs" expected={"localhost resolves to one or more addresses; the exact IPv4/IPv6 order can vary."}>

Import lookup from node:dns/promises. Use all:true and retain each address family. Run this command on your own machine; the lab's unit tests inject a fake resolver so CI does not depend on public DNS.

```js
import { lookup } from 'node:dns/promises';
export async function resolveHost(hostname, resolver = lookup) {
  return await resolver(hostname, { all: true });
}
```

</LessonStep>

<LessonStep number={3} title={"Diagnose a failed lookup"} file="labs/dns-domains/starter/exercise.mjs" expected={"An ENOTFOUND error is distinguished from other resolver failures."}>

Return a structured diagnostic rather than pretending an empty list means the remote service is down. Do not use this educational inspector as an SSRF allowlist; resolving once does not safely authorize a later connection.

```js
export async function diagnose(hostname, resolver = lookup) {
  try { return { ok: true, addresses: await resolveHost(hostname, resolver) }; }
  catch (error) { return { ok: false, reason: error.code === 'ENOTFOUND' ? 'name-not-found' : 'lookup-failed' }; }
}
```

</LessonStep>

## Explore it yourself

Try `node -e "require('node:dns').lookup('localhost',{all:true},console.log)"`. On Windows compare `Resolve-DnsName example.com` (requires a working external resolver). In a terminal, `nslookup example.com` can show DNS answers. Compare these with the URL in DevTools. DNS success is only one diagnostic layer; do not expect a particular public IP address.
