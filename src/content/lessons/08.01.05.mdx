## The problem we're solving

Every button gets the same primary class regardless of tone. A robust component system has to work across dark and light themes, keyboard input, small screens and real data, not merely appear correct in a screenshot.

## Build the mental model

Use finite, typed variant maps; understand class-merging semantics and avoid runtime string interpolation for utility names. **Predict before executing:** Danger and secondary have different classes; sizes are distinct.

**Runtime boundary:** This lesson's fixture is local TypeScript only. It does not compile Tailwind CSS, install shadcn or Radix/Base UI, mount a browser interaction, or verify visual contrast on real content. Those require a dedicated UI build and accessibility checks.

<LessonStep number={2} title="Repair the typed source contract" file="labs/ui-variant-classes/starter/solution.tsx" expected="Danger and secondary have different classes; sizes are distinct.">

```tsx
export type Tone='primary'|'secondary'|'danger';export type Size='sm'|'lg';export function classes(tone:Tone,size:Size){const t:Record<Tone,string>={primary:'bg-sky-700 text-white',secondary:'bg-slate-100 text-slate-900',danger:'bg-red-700 text-white'};const s:Record<Size,string>={sm:'px-3 py-1.5 text-sm',lg:'px-5 py-3 text-base'};return 'rounded-md focus-visible:outline-2 '+t[tone]+' '+s[size];}
```

**Why it works:** Use finite, typed variant maps; understand class-merging semantics and avoid runtime string interpolation for utility names.

</LessonStep>
