## The problem we're solving

A product-price parser asserts JSON as a typed object and crashes when priceCents is missing. In a full-stack application, this boundary can lead to incorrect data or information disclosure even if the TypeScript project compiles successfully.

## Build the mental model

TypeScript annotations are erased during compilation, so an as assertion cannot validate JSON. Check structural fields at runtime before using numeric methods. Use unknown to force an explicit boundary rather than importing arbitrary data as a trusted domain object.

**Predict before running:** Only nonnegative integral cents reach the formatter; invalid runtime values are rejected safely.

Use unknown at the boundary, a runtime predicate or strict schema and a public result type. Handle expected invalid data explicitly.

```ts
type Product={priceCents:number};export function solve(raw:unknown):string{if(!raw||typeof raw!=='object'||!('priceCents' in raw)||typeof raw.priceCents!=='number'||!Number.isInteger(raw.priceCents)||raw.priceCents<0)return 'INVALID';const product:Product={priceCents:raw.priceCents};return product.priceCents.toFixed(0);}
```

**Predict before running:** Only nonnegative integral cents reach the formatter; invalid runtime values are rejected safely.

**Why the repair works:** TypeScript annotations are erased during compilation, so an as assertion cannot validate JSON. Check structural fields at runtime before using numeric methods. Use unknown to force an explicit boundary rather than importing arbitrary data as a trusted domain object.

**Proof:** Compare clean and malformed cases against the verified instructor module.

## Explore and verify

Use boundary-oriented reasoning: the outer layer receives unknown, the parser enforces shape and units, and only then may a domain function use a trusted type. Separate validation from authorization; a successful schema parse never proves the actor has permission.
