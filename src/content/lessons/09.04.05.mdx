## The problem we're solving

Two tabs update a local theme preference. A delayed message from an older revision arrives and overwrites a newer user choice.

**Broken behavior:** The starter applies every incoming update, including messages from the same tab and stale revisions.

## Build the mental model

Use an explicit message origin and monotonic revision gate when synchronizing selected client preferences between tabs; document conflict limitations.

**Predict:** New remote revision is accepted; stale or self-origin updates do not override more recent state.

**Evidence boundary:** The local test imports the real Zustand 5 `createStore` API and, where appropriate, the official middleware. The store is created afresh per test; it does not use a global request-scoped server singleton. Passing Node assertions does not prove browser hydration, cross-tab synchronization or HTTP authorization.

<LessonStep number={2} title="Implement the corrected Zustand 5 store" file="labs/zustand-multitab-revisions/starter/solution.ts" expected="New remote revision is accepted; stale or self-origin updates do not override more recent state.">

```ts
import {createStore} from 'zustand/vanilla';
export type Message={origin:string;revision:number;theme:'light'|'dark'};
type TabState=Message&{setTheme:(theme:Message['theme'])=>void;applyRemote:(message:Message)=>void};
export function makeTabStore(origin:string){
 return createStore<TabState>()((set,get)=>({
  origin,revision:0,theme:'light',
  setTheme:theme=>set(state=>({theme,revision:state.revision+1})),
  applyRemote:message=>{if(message.origin!==origin&&Number.isSafeInteger(message.revision)&&message.revision>get().revision){
   set({theme:message.theme,revision:message.revision});
  }},
 }));
}
```

**Reasoning:** Use an explicit message origin and monotonic revision gate when synchronizing selected client preferences between tabs; document conflict limitations.

</LessonStep>
