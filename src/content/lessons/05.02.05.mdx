## The problem we're solving

A merge gate accepts a green status from an old commit while the current head remains untested. The lesson uses synthetic local data; passing its test does not configure actual branch protection or trigger a release.

## Build the mental model

Required status checks must correspond to the exact head SHA or a verified test merge commit, depending on repository rules. A stale success is not evidence for new code. The local exercise models the SHA gate and missing/pending/failure states; actual branch protection is configured by the Git hosting provider.

**Predict before running:** Only required green checks tied to the current SHA satisfy the simplified gate.

<LessonStep number={2} title="Implement the explicit review or release contract" file="labs/team-required-checks/starter/solution.mjs" expected={"Only required green checks tied to the current SHA satisfy the simplified gate."}>

Prefer an explicit result and a narrow, auditable policy; do not invent remote approvals or call an external API.

```js
export function solve(required,checks,head){if(!Array.isArray(required)||!Array.isArray(checks)||typeof head!=='string'||!head)return false;return required.every(name=>checks.some(c=>c.name===name&&c.sha===head&&c.status==='success'));}
```

**Predict before running:** Only required green checks tied to the current SHA satisfy the simplified gate.

**Why the repair works:** Required status checks must correspond to the exact head SHA or a verified test merge commit, depending on repository rules. A stale success is not evidence for new code. The local exercise models the SHA gate and missing/pending/failure states; actual branch protection is configured by the Git hosting provider.

**Proof:** Run the same independent test after editing; a green result demonstrates this local policy only.

</LessonStep>
