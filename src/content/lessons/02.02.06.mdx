## The problem we're solving

The same course card is placed in a narrow sidebar and a wide main column, but viewport breakpoints style both identically. The goal is a predictable local repair, not a decorative mockup. The HTML fixture is fully offline and has an intentionally failing starter plus an instructor solution.

## Build the mental model

A size container query responds to the size of the declared query container rather than the whole viewport. container-type: inline-size establishes the inline-size query container; descendants can change their layout when that container grows. The query does not style its own container—only matching descendants.

**Predict before running:** The tile is stacked in a narrow parent and switches to two columns when that parent reaches 32rem.

**Proof:** In DevTools, vary the width of #demo while holding the browser viewport fixed, and inspect tile display. Record the value in the starter before moving on.

</LessonStep>

<LessonStep number={2} title="Repair the rule, not the screenshot" file="labs/css-container/starter/index.html" expected={"The tile is stacked in a narrow parent and switches to two columns when that parent reaches 32rem."}>

Replace the defective declaration with this rule from the instructor implementation. Do not change the semantic markup or hide overflow simply to mask a layout defect.

```css
.demo { container-type: inline-size; } .tile { display: block; } @container (min-width: 32rem) { .tile { display: grid; grid-template-columns: minmax(0, 1fr) minmax(0, 1fr); gap: 1rem; } }
```

**Predict before running:** The tile is stacked in a narrow parent and switches to two columns when that parent reaches 32rem.

**Why it works:** A size container query responds to the size of the declared query container rather than the whole viewport. container-type: inline-size establishes the inline-size query container; descendants can change their layout when that container grows. The query does not style its own container—only matching descendants.

**Proof:** Compare the properties and geometry with `labs/css-container/solution/index.html`, using DevTools, not merely text-searching the CSS source.

</LessonStep>

<LessonStep number={3} title="Measure and regression-check the behavior" file="labs/css-container/starter/index.html" expected="Narrow and wide states remain usable, with no unexpected horizontal overflow.">

Open Responsive Design Mode at 320px and 1100px. For applicable lessons, scroll, inspect an accessible scrolling region or constrain the query container while keeping the viewport fixed.

```js
const root = document.documentElement;
const surface = document.querySelector('#demo');
console.log({
  fitsViewport: root.scrollWidth <= innerWidth,
  display: getComputedStyle(surface).display,
  inlineSize: surface.getBoundingClientRect().width
});
```

**Predict before running:** A specific layout value changes as expected, and the repaired surface stays within its available width.

**Why it works:** Browser computed styles and bounding boxes reflect selector matching, layout algorithm and containing-block constraints.

**Proof:** In DevTools, vary the width of #demo while holding the browser viewport fixed, and inspect tile display.

</LessonStep>
