## The problem we're solving

An API returns 200 OK for every request, even a newly created resource, a missing resource or an unsupported method.

**Fault to find:** The starter collapses method semantics into one unconditional 200 response. This track uses Node 24 built-ins and fetch-compatible `Response` where appropriate; no paid platform or remote arbitrary-code execution is needed.

## Build the mental model

Map HTTP method semantics to appropriate success and error codes; distinguish GET/HEAD, POST creation, PATCH edits, DELETE success and 405 with Allow.

**Expected repair:** Known methods map to intended status codes; unsupported methods receive 405 and an Allow list.

HTTP semantics follow RFC 9110. Public errors can use RFC 9457 Problem Details; do not invent return codes or copy internal stack traces into public responses. Pure helper tests are useful but the final capstone runs a real loopback server and tests wire responses.

<LessonStep number={2} title="Implement standards-based HTTP behavior" file="labs/http-method-status/starter/solution.mjs" expected="Known methods map to intended status codes; unsupported methods receive 405 and an Allow list.">

```js
export function chooseStatus(method,exists){
 switch(method){
  case 'GET':case 'HEAD':return {status:exists?200:404};
  case 'POST':return {status:201};
  case 'PATCH':return {status:exists?200:404};
  case 'DELETE':return {status:exists?204:404};
  default:return {status:405,allow:'GET, HEAD, POST, PATCH, DELETE'};
 }
}
```

**Why this is correct:** Map HTTP method semantics to appropriate success and error codes; distinguish GET/HEAD, POST creation, PATCH edits, DELETE success and 405 with Allow.

</LessonStep>

**Production adaptation and limits:**

```js
// An HTTP 204 response has no payload body.
res.writeHead(204);res.end();
// Unsupported methods should return 405 with the Allow header.
// POST is not automatically idempotent: implement explicit request keys
// or another server-side deduplication mechanism for safe retries.
```

**Operational distinction:** The reference implementation intentionally excludes production identities, durable database transactions, distributed replay records, rate limiting, SSRF protection, and deployment. Those require separate lessons and genuine integration checks.

</LessonStep>
