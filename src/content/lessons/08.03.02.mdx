## The problem we're solving

The filtered view sorts the original source array in place and paginates before filtering, so results disappear between pages.

## Build the mental model

For client-side tables, filter, then sort deterministically, then paginate the resulting set. Use immutable data and stable secondary sort keys to avoid jumping rows. Controlled state should be reflected in accessible headers and page controls.

**Predict first:** The dataset is filtered and deterministically sorted before paging; invalid page sizes are rejected.

<LessonStep number={2} title="Fix the policy and verify edge cases" file="labs/ui-table-controls/starter/solution.ts" expected="The dataset is filtered and deterministically sorted before paging; invalid page sizes are rejected.">

```ts

export function solve(items:readonly {id:string;title:string}[],query:string,page:number,size:number){if(!Number.isInteger(page)||page<0||!Number.isInteger(size)||size<1)throw new TypeError("Invalid page");const q=query.trim().toLowerCase();return items.filter(x=>x.title.toLowerCase().includes(q)).sort((a,b)=>a.title.localeCompare(b.title)||a.id.localeCompare(b.id)).slice(page*size,(page+1)*size);}

```

**Why it works:** For client-side tables, filter, then sort deterministically, then paginate the resulting set. Use immutable data and stable secondary sort keys to avoid jumping rows. Controlled state should be reflected in accessible headers and page controls.

**Proof:** Run `npm run lab:ui-table-controls` and inspect the instructor test output.

</LessonStep>
