## Documentation and compatibility decisions

- Prisma lessons explicitly target **Prisma ORM v7**, using the `prisma-client` generator, explicit custom generated output, `PrismaPg` driver adapter and a version-matched config file. **Prisma ORM v8 is not assumed compatible.**
- Supabase lessons distinguish publishable keys from secret/service-role keys, table GRANT from RLS row filtering, verified Auth identities from editable user metadata, and direct PostgreSQL connections from Data API JWT/RLS requests.
- Auth content teaches that `getClaims()` verifies signature/expiry while an unexpired token may remain accepted after server-side session revocation; sensitive operations need appropriate freshness checks.
- RLS content requires allow and deny tests for anon and *two authenticated users*. A service-role client bypasses RLS and cannot provide a convincing end-user security test.
- Supabase schema/Storage snippets use example tables and buckets in a **local disposable test stack** only. A persistent migration must be generated by the actual installed CLI, not by inventing a timestamped migration filename.

## Engineering checks and limitations

A source-only verifier at `examples/p4-foundations/scripts/verify-source.mjs` enforces:
- All 40 IDs and titles match canonical modules and prerequisite chains.
- Each MDX exercise snippet exactly matches its checked-in language-specific starter/solution.
- Drafts remain flagged unverified; no published lesson registry or checkpoint is modified.
- Each lab has a real positive and negative test plan, source paths and an official reference.
- No already published lesson or embedded client-side lab is accidentally introduced.

**NOT executed in this environment:** Prisma ORM v7 CLI generation/build, real PostgreSQL/Prisma transactions, Supabase local Auth/RLS with two accounts, Next production build, browser workflows, real MFA/email callbacks, human screen-reader/keyboard/200% zoom accessibility review. Source parsing and code parity are not substitutes for those gates.


No Vercel or GitHub Actions workflow is required to run local qualification.

## Runtime release gates before *any* P4 publication

1. Pin Prisma v7 packages, `@prisma/adapter-pg`, `pg` and a genuine npm lockfile in an isolated example, then execute `prisma validate`, `prisma generate`, real PostgreSQL migration and per-tenant CRUD integration tests.
2. Start an approved **local Supabase** stack (not a linked production project) and verify migration replay, grant + RLS tests, Storage permissions, JWT/Auth, SSR cookie refresh and sign-out under representative accounts.
3. Test the RLS access matrix with anon and two Auth users. For each operation implemented, assert both allowed and *denied* cases, especially INSERT/UPDATE `WITH CHECK` and object membership. Confirm any Prisma/server privilege bypass separately.
4. Run the complete Node24/Next build, browser keyboard/mobile flows, reduced-motion and human accessibility review. Test no secret key appears in client build output.
5. Obtain named reviewer signoff on the source, tests and external service credentials. Promote only verified lessons, respecting the earlier P1→P2→P3 priority. Do not inflate published progress by simply merging.
