## The problem we're solving

A task-created event is emitted before persistence succeeds, triggering false notifications. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Events should be emitted after a committed operation, with durable delivery for critical side effects. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Events should be emitted after a committed operation, with durable delivery for critical side effects.
- **Reproducible failure:** A task-created event is emitted before persistence succeeds, triggering false notifications.
- **Acceptance evidence:** On a failed save, no success event is emitted; on confirmation, one event is raised.
- **Risk that remains:** For durable notifications use an outbox or queue; process-local emitters can lose events.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.

## Applied engineering walkthrough

A domain event represents something that happened, not a promise that it might happen. The solution awaits save before emitting task.created. The in-process EventEmitter is synchronous and non-durable; a listener can throw after persistence, or the process can terminate before the event is delivered. A successful save call does not prove a larger surrounding transaction has committed. Critical side effects need a transactional outbox and idempotent consumers.

### Diagnose the concrete failure

Use a writer that records success or rejects, and an emitter that records event delivery. The success order must be write then event; the failure path must not emit. Add a listener that throws after the write, and explain why an error response does not necessarily prove that the write failed. Do not silently retry creation with a new identity.

### Independent exercise and evidence

Sketch an outbox table storing an event ID and payload in the same transaction as the task. Describe a worker that publishes committed rows and a consumer that tolerates duplicate delivery. Record the failure window between write and emit in the simple fixture and the outbox mitigation.
