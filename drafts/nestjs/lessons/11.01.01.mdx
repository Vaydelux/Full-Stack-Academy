## The problem we're solving

A GET /tasks returns 404 even though TasksController exists in source. A team reviewing a NestJS service must understand *why* this is a failure, not merely memorize decorator names. This lesson isolates the failure in one short source file so the learner can compare the runtime contract before and after the change.

## Build the mental model

The root module must import a feature module for its controllers to become routes. In NestJS 12, decorators register metadata used by the Nest runtime; the TypeScript class is not automatically a route or managed provider. A running application must still compose its modules, resolve dependencies, and handle failures at the actual HTTP or service boundary.

Source existence is not evidence of a functioning server. Declare TasksModule and import it into AppModule; do not directly construct the feature controller.

## Design alternatives and debugging strategy

A quick workaround would hide the immediate symptom, but it would leave the original ownership or lifecycle error intact. Start by tracing the source that creates the Nest application and the providers registered in its module graph; then inspect the exact request path, active context, or emitted response affected by this lesson. Prefer an isolated test that can be run repeatedly without a live external database or credential.

- **When it is appropriate:** The root module must import a feature module for its controllers to become routes.
- **When it is not enough:** If multiple requests, tenants, or worker processes are involved, test the same boundary under concurrency and treat incoming data as untrusted.
- **How to confirm the repair:** Boot the full Nest application and check that GET /tasks is registered.
- **What to document:** The expected failure code, verification command, dependency version, and whether a browser, HTTP, or service-layer test actually executed.

## Applied engineering walkthrough

A module graph is a dependency graph, not a file tree. Nest starts from the root module, follows imports, then registers each reachable module's controllers and providers. Importing a TypeScript file does not register the controller. Exports make selected providers available to importing modules; controllers are not exported as service dependencies. Prefer feature modules with explicit dependencies over a global catch-all module.

### Diagnose the concrete failure

Trace AppModule → TasksModule → TasksController on paper. Start the broken root and request GET /tasks; a 404 means the route is missing, not that the process failed to boot. Add the feature import and repeat the exact request; expect HTTP 200 and the array with t1. Then remove the import again to demonstrate that a successful bootstrap alone cannot establish route availability.
