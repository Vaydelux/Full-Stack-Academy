## The problem we're solving

The filter sends an HTTP 500 for a known 404 and exposes the raw exception message. The request pipeline is a composition of stages rather than a single controller method: middleware prepares the request, a guard decides permission, pipes parse inputs, interceptors wrap handler execution and filters normalize failures. Each stage needs its own test because correct TypeScript does not prove real HTTP behavior.

## Build the mental model

An HttpException filter must return a safe status and predictable response body without leaking internals. The stage where the problem occurs matters: moving validation into an authorization check or moving a security decision into a response interceptor can accidentally expose the handler. Trace the request lifecycle from ingress to exit, and record both expected success and denial.

<LessonStep number={2} title="Repair the correct stage" file="drafts/nestjs/labs/exception-filters/solution.ts" expected="An HttpException filter must return a safe status and predictable response body without leaking internals.">

```ts
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common';
@Catch(HttpException)
export class SafeHttpFilter implements ExceptionFilter {
  catch(error: HttpException, host: ArgumentsHost) {
    const reply = host.switchToHttp().getResponse<{ status: (n: number) => any; send: (x: unknown) => void }>();
    reply.status(error.getStatus()).send({ error: 'REQUEST_FAILED', statusCode: error.getStatus() });
  }
}
```

**Why this design:** An HttpException filter must return a safe status and predictable response body without leaking internals. Never return stack traces, SQL fragments, service keys, or raw internal errors.

</LessonStep>

## Operational failure analysis

If the UI shows a generic error, classify the failure at the nearest authoritative boundary. A 400 is invalid input, a 403 is denied access, a 404 is missing resource and a 503 is a failed dependency; do not collapse these into one “success” or one database error. Log correlation IDs with bounded length rather than sensitive headers. Run both a happy-path request and a deliberate failure using independently constructed test clients.

## Applied engineering walkthrough

Exception filters translate exceptions into the transport response. A filter restricted to HttpException handles that class, not every possible error. Preserve known HTTP status codes and expose a deliberately safe error envelope. Unexpected failures should remain server errors, with details recorded only in protected logs. Adapter-specific response methods need real adapter acceptance, or use Nest's HTTP adapter abstraction for portability.

### Diagnose the concrete failure

Throw an HttpException with a sensitive internal message and status 403 using the existing filter fixture. Check that the response remains 403 and the body contains REQUEST_FAILED without the original message. Repeat with a known 404 in a real route. An exception filter must not report HTTP 200 for a failed operation.

### Independent exercise and evidence

Design an error contract with a stable code and correlation ID, with no stack or secret content. Decide which fields a UI may display and which belong only in logs. Record status and serialized body for a denied request and a missing resource.
