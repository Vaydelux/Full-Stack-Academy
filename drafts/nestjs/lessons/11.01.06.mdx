```ts
import { NestFactory } from '@nestjs/core';
import { Module } from '@nestjs/common';
import { FastifyAdapter, NestFastifyApplication } from '@nestjs/platform-fastify';
@Module({})
export class AppModule {}
export async function createApp(): Promise<NestFastifyApplication> {
  return NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter());
}
```

## Applied engineering walkthrough

Nest controllers are portable only while they use framework-level abstractions. Fastify and Express differ in request/reply objects, plugins and middleware integrations. A TypeScript generic changes the declared application type, not the actual HTTP adapter. Supply FastifyAdapter explicitly and check the real adapter. Use adapter-native features only behind a clearly documented boundary.

### Diagnose the concrete failure

Inspect createApp in each variant and compare the runtime adapter type. In an initialized application, use the existing architecture acceptance test and close the application afterward. When extending with a route, verify status, body and headers through the chosen adapter rather than relying on a typed declaration.

### Independent exercise and evidence

Pick one Express-specific middleware or response method and describe how you would replace it using a Nest abstraction or Fastify-compatible plugin. Record adapter type and the behavior a regression test must preserve. Do not claim benchmark improvements without measurement.
