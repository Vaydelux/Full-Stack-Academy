## The problem we're solving

A task title is concatenated into a raw SQL query, allowing injection. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Domain services should use an injectable repository contract instead of building SQL strings. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Domain services should use an injectable repository contract instead of building SQL strings.
- **Reproducible failure:** A task title is concatenated into a raw SQL query, allowing injection.
- **Acceptance evidence:** A hostile quote-containing title is passed as a parameter rather than interpolated SQL.
- **Risk that remains:** Use parameterized queries and server-side tenant predicates in real database tests.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.

## Applied engineering walkthrough

A repository is a boundary around persistence. The service supplies domain inputs; the adapter supplies SQL and bound values. In this example the title occupies a value placeholder, not part of the query text. Parameterization does not authorize access, and it cannot bind SQL identifiers such as a column name. Production queries also need explicit tenant predicates and a projection of required columns; SELECT * is only illustrative here.

### Diagnose the concrete failure

Use a fake query client that records the SQL string and parameter array. Compare a normal title and a title containing an apostrophe. Both must use identical SQL text and distinct parameter values. The intentionally broken starter changes SQL text instead. A recording fake proves the binding contract only, not actual PostgreSQL execution or tenant isolation.

### Independent exercise and evidence

Design a repository method to list titles within an authorized workspace. Add a tenant predicate, an explicit selected-column list and a bounded limit. Record the resulting SQL and argument array for two distinct workspaces. Later run the same contract against a disposable PostgreSQL schema.
