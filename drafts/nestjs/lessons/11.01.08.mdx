## The problem we're solving

The endpoint returns status up when a required service is unavailable. A team reviewing a NestJS service must understand *why* this is a failure, not merely memorize decorator names. This lesson isolates the failure in one short source file so the learner can compare the runtime contract before and after the change.

## Build the mental model

A health endpoint must reflect actual service readiness instead of returning a constant green response. In NestJS 12, decorators register metadata used by the Nest runtime; the TypeScript class is not automatically a route or managed provider. A running application must still compose its modules, resolve dependencies, and handle failures at the actual HTTP or service boundary.

**Predict:** Before reading the instructor solution, describe the client-visible response or container behavior when the broken starter is used. The endpoint returns status up when a required service is unavailable.

**Trust and version boundary:** Target Node.js 24, TypeScript 6 and NestJS 12 with real installed packages. The repository has not yet completed an npm-locked Nest runtime test for this draft. Source existence is not evidence of a functioning server. Bind locally for practice; production readiness requires actual dependency probes and safe failure data.

<LessonStep number={2} title="Implement a focused NestJS repair" file="drafts/nestjs/labs/hello-api-capstone/solution.ts" expected="A health endpoint must reflect actual service readiness instead of returning a constant green response.">

```ts
import { Controller, Get, Injectable, Module, ServiceUnavailableException } from '@nestjs/common';
@Injectable()
export class Readiness { ready = false; }
@Controller('health')
export class HealthController {
  constructor(private readonly readiness: Readiness) {}
  @Get() status() {
    if (!this.readiness.ready) throw new ServiceUnavailableException('Not ready');
    return { status: 'up' };
  }
}
@Module({ providers: [Readiness], controllers: [HealthController] })
export class HealthModule {}
```

**Reasoning:** A health endpoint must reflect actual service readiness instead of returning a constant green response. Bind locally for practice; production readiness requires actual dependency probes and safe failure data. This repair does not imply that external users are authorized; it solves only the bounded lesson contract.

</LessonStep>

## Design alternatives and debugging strategy

A quick workaround would hide the immediate symptom, but it would leave the original ownership or lifecycle error intact. Start by tracing the source that creates the Nest application and the providers registered in its module graph; then inspect the exact request path, active context, or emitted response affected by this lesson. Prefer an isolated test that can be run repeatedly without a live external database or credential.

- **When it is appropriate:** A health endpoint must reflect actual service readiness instead of returning a constant green response.
- **When it is not enough:** If multiple requests, tenants, or worker processes are involved, test the same boundary under concurrency and treat incoming data as untrusted.
- **How to confirm the repair:** With readiness true return 200; with readiness false return 503; check both through real HTTP.
- **What to document:** The expected failure code, verification command, dependency version, and whether a browser, HTTP, or service-layer test actually executed.
