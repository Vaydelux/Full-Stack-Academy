## The problem we're solving

The controller directly mutates records and allows blank task names. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Keep transport decorators in controllers and business invariants in injectable services. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

```ts
import { BadRequestException, Body, Controller, Injectable, Post } from '@nestjs/common';
@Injectable()
export class TasksService {
  private tasks: string[] = [];
  create(title: unknown) {
    if (typeof title !== 'string') throw new BadRequestException('Invalid title');
    const value = title.trim();
    if (value.length < 3 || value.length > 100) throw new BadRequestException('Invalid title');
    this.tasks.push(value);
    return { title: value };
  }
}
@Controller('tasks')
export class TasksController {
  constructor(private readonly tasks: TasksService) {}
  @Post() create(@Body() body: unknown) {
    const title = body && typeof body === 'object' && !Array.isArray(body)
      ? (body as Record<string, unknown>).title : undefined;
    return this.tasks.create(title);
  }
}
```

**Reasoning:** Keep transport decorators in controllers and business invariants in injectable services. Validation in a controller alone cannot protect calls from jobs, events and other modules.

</LessonStep>

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Keep transport decorators in controllers and business invariants in injectable services.
- **Reproducible failure:** The controller directly mutates records and allows blank task names.
- **Acceptance evidence:** A unit test invokes TasksService directly and rejects blank names; HTTP invokes the same service.
- **Risk that remains:** Validation in a controller alone cannot protect calls from jobs, events and other modules.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.

## Applied engineering walkthrough

Separate transport concerns from business decisions. A controller maps HTTP input into a service call; a service owns rules that must hold regardless of whether the caller is HTTP, a scheduled job, or another module. The sample service validates the title and stores it in memory. BadRequestException couples this teaching service to HTTP; a reusable domain layer could instead throw a domain error mapped by the transport layer. The array is not durable storage.

### Diagnose the concrete failure

Send blank, non-string, and whitespace-padded titles. Expect rejection for the first two and a trimmed result for a valid value. Call the service directly as well: the invariant should not depend on a controller decorator. A green direct call is not proof that body parsing and HTTP status mapping work.

### Independent exercise and evidence

Design a task rename operation that enforces the same title rule from both an HTTP controller and an import job. Record the input, normalized output, and unchanged state after rejection. Decide which layer owns persistence and which maps business errors to responses.
