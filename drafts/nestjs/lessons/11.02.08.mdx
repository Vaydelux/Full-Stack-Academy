## The problem we're solving

The guard authorizes everyone and the team mistakenly relies on validation to protect private records. The request pipeline is a composition of stages rather than a single controller method: middleware prepares the request, a guard decides permission, pipes parse inputs, interceptors wrap handler execution and filters normalize failures. Each stage needs its own test because correct TypeScript does not prove real HTTP behavior.

## Build the mental model

Guards run before pipes, making authorization an independent boundary for protected requests. The stage where the problem occurs matters: moving validation into an authorization check or moving a security decision into a response interceptor can accidentally expose the handler. Trace the request lifecycle from ingress to exit, and record both expected success and denial.

**Prediction:** The guard authorizes everyone and the team mistakenly relies on validation to protect private records. Explain whether the handler is reached, and what an HTTP client should observe.

**Release scope:** These examples target NestJS 12, Node 24, TypeScript 6. They are authored drafts, not compiler-qualified or published material. Authorization must not depend on client-side form validation, a permissive guard, or a role string in JSON.

```ts
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
@Injectable()
export class ProtectedRouteGuard implements CanActivate {
  canActivate(ctx: ExecutionContext) {
    const req = ctx.switchToHttp().getRequest<{ user?: { permissions: string[] } }>();
    return req.user?.permissions.includes('tasks:read') === true;
  }
}
```

**Why this design:** Guards run before pipes, making authorization an independent boundary for protected requests. Authorization must not depend on client-side form validation, a permissive guard, or a role string in JSON.

</LessonStep>

## Applied engineering walkthrough

For ordinary Nest HTTP requests the relevant order is middleware, guards, interceptor pre-handler logic, pipes, controller, interceptor post-handler logic; uncaught exceptions flow to applicable filters. A guard sees raw route data before a pipe validates it, so it must validate any raw identifiers it uses. Validation does not grant access. The fixture assumes a trusted, already-populated user principal; production code must ensure that assumption through verified authentication.

### Diagnose the concrete failure

Build a trace for a denied request and an authorized request. For denial, expect the guard to stop processing before the protected handler; for authorization, continue to pipe and handler. The existing direct guard test checks missing principal, missing permission and intended permission; an actual Nest HTTP test is needed to verify ordering. Do not infer runtime order from the class-only checks.

### Independent exercise and evidence

Plan three integration cases: anonymous valid body, authenticated unauthorized malformed body, and authorized malformed body. Specify which boundary should reject each, and prove the handler is never called in denial cases. Record the stage trace and HTTP status rather than exposing the request body.

**Qualification boundary:** These are acceptance instructions, not recorded results. The existing request-pipeline checks include direct class and pure-function tests; real HTTP and adapter acceptance remain distinct release requirements. Do not award course credit from source review alone.
