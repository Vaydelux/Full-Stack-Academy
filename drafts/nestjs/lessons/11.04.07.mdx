<LessonStep number={2} title="Apply the versioned NestJS repair" file="drafts/nestjs/labs/health-endpoints/solution.ts" expected="Liveness and readiness answer different operational questions and must not both report success during an outage.">

```ts
import { Controller, Get, Injectable, ServiceUnavailableException } from '@nestjs/common';
@Injectable()
export class Dependencies { ready = false; }
@Controller('health')
export class HealthController {
  constructor(private readonly deps: Dependencies) {}
  @Get('live') live() { return { status: 'alive' }; }
  @Get('ready') ready() {
    if (!this.deps.ready) throw new ServiceUnavailableException('Unavailable');
    return { status: 'ready' };
  }
}
```

## Applied engineering walkthrough

Liveness indicates whether an instance is alive; readiness indicates whether it can accept intended traffic. A required dependency outage may make readiness fail while liveness remains healthy. The sample uses a mutable flag, not a real probe. A production dependency probe needs short timeouts, bounded load and safe response details. Avoid triggering restart loops for recoverable external failures.

### Diagnose the concrete failure

Call /health/live and /health/ready before readiness is true. Expect 200 for liveness and 503 for readiness. Flip the fixture flag, repeat, then simulate an outage. Confirm readiness returns to 503 while liveness remains 200. Run through a real adapter for final acceptance.
