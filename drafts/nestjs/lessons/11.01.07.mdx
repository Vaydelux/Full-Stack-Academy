## The problem we're solving

A provider opens a polling timer but never stops it, keeping the process alive. A team reviewing a NestJS service must understand *why* this is a failure, not merely memorize decorator names. This lesson isolates the failure in one short source file so the learner can compare the runtime contract before and after the change.

## Build the mental model

Managed resources must be released when Nest shuts down. In NestJS 12, decorators register metadata used by the Nest runtime; the TypeScript class is not automatically a route or managed provider. A running application must still compose its modules, resolve dependencies, and handle failures at the actual HTTP or service boundary.

**Predict:** Before reading the instructor solution, describe the client-visible response or container behavior when the broken starter is used. A provider opens a polling timer but never stops it, keeping the process alive.

Source existence is not evidence of a functioning server. Avoid uncaught shutdown exceptions; make cleanup idempotent.

<LessonStep number={2} title="Implement a focused NestJS repair" file="drafts/nestjs/labs/lifecycle-hooks/solution.ts" expected="Managed resources must be released when Nest shuts down.">

```ts
import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
@Injectable()
export class Poller implements OnModuleInit, OnModuleDestroy {
  private timer?: ReturnType<typeof setInterval>;
  onModuleInit() { this.timer = setInterval(() => {}, 1000); }
  onModuleDestroy() {
    if (this.timer) clearInterval(this.timer);
    this.timer = undefined;
  }
}
```

**Reasoning:** Managed resources must be released when Nest shuts down. Avoid uncaught shutdown exceptions; make cleanup idempotent. This repair does not imply that external users are authorized; it solves only the bounded lesson contract.

</LessonStep>

## Design alternatives and debugging strategy

A quick workaround would hide the immediate symptom, but it would leave the original ownership or lifecycle error intact. Start by tracing the source that creates the Nest application and the providers registered in its module graph; then inspect the exact request path, active context, or emitted response affected by this lesson. Prefer an isolated test that can be run repeatedly without a live external database or credential.

- **When it is appropriate:** Managed resources must be released when Nest shuts down.
- **When it is not enough:** If multiple requests, tenants, or worker processes are involved, test the same boundary under concurrency and treat incoming data as untrusted.
- **How to confirm the repair:** Call app.close and ensure the provider has released its interval.
- **What to document:** The expected failure code, verification command, dependency version, and whether a browser, HTTP, or service-layer test actually executed.

## Applied engineering walkthrough

Lifecycle hooks provide ownership points for resources such as timers, sockets and pools. Initialize only when dependencies are ready; release resources on shutdown. A repeating timer can keep the Node event loop alive even after HTTP stops. An explicit app.close triggers lifecycle cleanup; operating-system signal handling requires the appropriate shutdown-hook configuration. Avoid relying on process.exit as cleanup.

### Diagnose the concrete failure

Follow Poller's timer creation and destruction. The existing fixture's cleanup can be inspected by checking the timer reference after the destroy hook. For real integration, initialize a Nest app containing the provider, close it, and verify that no further work occurs and the process exits naturally. A timer-based check must have a bounded deadline to avoid a hanging test.

### Independent exercise and evidence

Design an analogous provider for a connection pool. Identify startup failure handling and an idempotent close operation. Record which code owns the resource, when it is acquired and the observation that proves release.
