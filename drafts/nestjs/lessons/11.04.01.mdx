## The problem we're solving

A service creates an adapter directly and cannot be replaced inside TestingModule. At this level, correctness must survive a process restart, a concurrent request, an unavailable dependency, or an unauthorized caller. An advanced Nest decorator is only useful when the test proves that its registration, runtime scope and error behavior match the intended design.

## Build the mental model

A stable injection token separates the contract from the concrete adapter. Always identify the owner of state and the point where a failure becomes visible: at the DI container, on the socket, in the request interceptor, at shutdown or in a production health probe. A secure design is not merely a code style; it is the combination of runtime boundaries and a reproducible denial case.

<LessonStep number={2} title="Apply the versioned NestJS repair" file="drafts/nestjs/labs/custom-provider-tokens/solution.ts" expected="A stable injection token separates the contract from the concrete adapter.">

```ts
import { Inject, Injectable } from '@nestjs/common';
export const STORAGE = Symbol('STORAGE');
export interface StoragePort { read(): string; }
@Injectable()
export class Reader {
  constructor(@Inject(STORAGE) private readonly storage: StoragePort) {}
  read() { return this.storage.read(); }
}
```

**Why it works:** A stable injection token separates the contract from the concrete adapter. Prefer scoped, explicit provider exports; do not expose secret credential providers globally.

</LessonStep>

## Operational and security review

A green response from one synchronous unit test is not proof of production reliability. Review two independent request contexts, a malformed payload, an intentional dependency failure and a resource-release scenario. Do not expose a demo health endpoint or test gateway to the public internet. For anything that could send or store private data, use independently authenticated test principals and negative access checks.
