## The problem we're solving

The service stores a previous request ID; concurrent users can observe another request's context. A team reviewing a NestJS service must understand *why* this is a failure, not merely memorize decorator names. This lesson isolates the failure in one short source file so the learner can compare the runtime contract before and after the change.

## Build the mental model

Request-specific data must never be retained in a global singleton provider. In NestJS 12, decorators register metadata used by the Nest runtime; the TypeScript class is not automatically a route or managed provider. A running application must still compose its modules, resolve dependencies, and handle failures at the actual HTTP or service boundary.

<LessonStep number={2} title="Implement a focused NestJS repair" file="drafts/nestjs/labs/dependency-injection-scopes/solution.ts" expected="Request-specific data must never be retained in a global singleton provider.">

```ts
import { Inject, Injectable, Scope } from '@nestjs/common';
import { REQUEST } from '@nestjs/core';
@Injectable({ scope: Scope.REQUEST })
export class RequestIdentity {
  constructor(@Inject(REQUEST) private readonly request: { headers: Record<string, string | undefined> }) {}
  current() { return this.request.headers['x-request-id'] ?? 'missing'; }
}
```

**Reasoning:** Request-specific data must never be retained in a global singleton provider. Use Scope.REQUEST only when required; request-scoped providers increase allocation cost. This repair does not imply that external users are authorized; it solves only the bounded lesson contract.

</LessonStep>

## Design alternatives and debugging strategy

A quick workaround would hide the immediate symptom, but it would leave the original ownership or lifecycle error intact. Start by tracing the source that creates the Nest application and the providers registered in its module graph; then inspect the exact request path, active context, or emitted response affected by this lesson. Prefer an isolated test that can be run repeatedly without a live external database or credential.

- **When it is appropriate:** Request-specific data must never be retained in a global singleton provider.
- **When it is not enough:** If multiple requests, tenants, or worker processes are involved, test the same boundary under concurrency and treat incoming data as untrusted.
- **How to confirm the repair:** Create two independent request scopes and confirm the derived IDs are isolated.
- **What to document:** The expected failure code, verification command, dependency version, and whether a browser, HTTP, or service-layer test actually executed.

## Applied engineering walkthrough

Singleton providers are shared by default; transient providers are created per consumer, while request-scoped providers are resolved for a request context. Request scope can propagate to dependent providers and increase allocation cost. Store shared stateless logic in singleton services, and keep identity/context request-bound. A correlation header identifies a trace only; it is not proof of a user's identity.

### Diagnose the concrete failure

Follow the REQUEST injection token in the solution. Exercise two separate request contexts with IDs A and B; intentionally interleave their work. Both must retain their own ID even after the other begins. The class-only result cannot establish how Nest creates contexts: use the existing container tests and later real overlapping HTTP calls.
