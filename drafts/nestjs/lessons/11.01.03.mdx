## The problem we're solving

A controller manually instantiates a service, bypassing DI overrides and per-request lifecycle. A team reviewing a NestJS service must understand *why* this is a failure, not merely memorize decorator names. This lesson isolates the failure in one short source file so the learner can compare the runtime contract before and after the change.

## Build the mental model

Nest resolves registered providers through the container rather than manual new statements in controllers. In NestJS 12, decorators register metadata used by the Nest runtime; the TypeScript class is not automatically a route or managed provider. A running application must still compose its modules, resolve dependencies, and handle failures at the actual HTTP or service boundary.

**Predict:** Before reading the instructor solution, describe the client-visible response or container behavior when the broken starter is used. A controller manually instantiates a service, bypassing DI overrides and per-request lifecycle.

**Trust and version boundary:** Target Node.js 24, TypeScript 6 and NestJS 12 with real installed packages. The repository has not yet completed an npm-locked Nest runtime test for this draft. Source existence is not evidence of a functioning server. Register the service in the owning module and inject through the constructor.

<LessonStep number={2} title="Implement a focused NestJS repair" file="drafts/nestjs/labs/injectable-providers/solution.ts" expected="Nest resolves registered providers through the container rather than manual new statements in controllers.">

```ts
import { Controller, Get, Injectable, Module } from '@nestjs/common';
@Injectable()
export class TasksService { count() { return 1; } }
@Controller('tasks')
export class TasksController {
  constructor(private readonly tasks: TasksService) {}
  @Get('count') count() { return { count: this.tasks.count() }; }
}
@Module({ controllers: [TasksController], providers: [TasksService] })
export class TasksModule {}
```

**Reasoning:** Nest resolves registered providers through the container rather than manual new statements in controllers. Register the service in the owning module and inject through the constructor. This repair does not imply that external users are authorized; it solves only the bounded lesson contract.

</LessonStep>

## Design alternatives and debugging strategy

A quick workaround would hide the immediate symptom, but it would leave the original ownership or lifecycle error intact. Start by tracing the source that creates the Nest application and the providers registered in its module graph; then inspect the exact request path, active context, or emitted response affected by this lesson. Prefer an isolated test that can be run repeatedly without a live external database or credential.

- **When it is appropriate:** Nest resolves registered providers through the container rather than manual new statements in controllers.
- **When it is not enough:** If multiple requests, tenants, or worker processes are involved, test the same boundary under concurrency and treat incoming data as untrusted.
- **How to confirm the repair:** Resolve the controller through Test.createTestingModule and override its service with a fake.
- **What to document:** The expected failure code, verification command, dependency version, and whether a browser, HTTP, or service-layer test actually executed.
