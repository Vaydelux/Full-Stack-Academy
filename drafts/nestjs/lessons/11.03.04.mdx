## The problem we're solving

TasksService always constructs PostgresTaskStore, making isolated tests impossible. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Business code depends on an abstract port injected by a token, not a concrete database constructor. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Business code depends on an abstract port injected by a token, not a concrete database constructor.
- **Reproducible failure:** TasksService always constructs PostgresTaskStore, making isolated tests impossible.
- **Acceptance evidence:** Override the TASK_STORE token with a fake and verify service behavior without network access.
- **Risk that remains:** Concrete storage adapters still must enforce tenant filters and parameterized queries.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.
