## The problem we're solving

One request overwrites another request's correlation ID under concurrency. The request pipeline is a composition of stages rather than a single controller method: middleware prepares the request, a guard decides permission, pipes parse inputs, interceptors wrap handler execution and filters normalize failures. Each stage needs its own test because correct TypeScript does not prove real HTTP behavior.

## Build the mental model

A request-context value belongs in a per-request async execution scope, not a mutable process global. The stage where the problem occurs matters: moving validation into an authorization check or moving a security decision into a response interceptor can accidentally expose the handler. Trace the request lifecycle from ingress to exit, and record both expected success and denial.

**Prediction:** One request overwrites another request's correlation ID under concurrency. Explain whether the handler is reached, and what an HTTP client should observe.

**Release scope:** These examples target NestJS 12, Node 24, TypeScript 6. They are authored drafts, not compiler-qualified or published material. Never store access tokens or sensitive user profiles in diagnostic context.

```ts
import { AsyncLocalStorage } from 'node:async_hooks';
const context = new AsyncLocalStorage<{ id: string }>();
export async function withRequest<T>(id: string, work: () => Promise<T>): Promise<T> {
  return context.run({ id }, work);
}
export const requestId = () => context.getStore()?.id;
```

**Why this design:** A request-context value belongs in a per-request async execution scope, not a mutable process global. Never store access tokens or sensitive user profiles in diagnostic context.

</LessonStep>

## Applied engineering walkthrough

AsyncLocalStorage associates data with an asynchronous execution chain. The solution calls run with a distinct store for each request; asynchronous work within that callback sees its own store. Outside the scope, getStore can be undefined. It is not a durable distributed context, and a correlation ID must not be treated as a verified principal. Avoid storing secrets or mutable shared request objects in the context.

### Diagnose the concrete failure

Start request A and hold it at a promise barrier. While A is pending, start B and read B's ID. Release A and read A's ID; both must match their own scope. After completion, no store should be visible in the outer scope. The original global-value design fails when B overwrites A during the await.

### Independent exercise and evidence

Extend the pure context test with a nested scope and an exception. Predict which ID is visible before, inside and after the nested call and after rejection. Record the sequence rather than relying on arbitrary sleep delays. In an integrated HTTP app, start the scope in middleware and verify two concurrent requests.
