## The problem we're solving

ReportsModule imports TasksModule but cannot resolve TasksService because it is not exported. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

A provider must be exported by its owning module and imported through that module to be visible elsewhere. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

```ts
import { Injectable, Module } from '@nestjs/common';
@Injectable()
export class TasksService { count() { return 1; } }
@Module({ providers: [TasksService], exports: [TasksService] })
export class TasksModule {}
@Injectable()
export class ReportsService {
  constructor(private readonly tasks: TasksService) {}
  count() { return this.tasks.count(); }
}
@Module({ imports: [TasksModule], providers: [ReportsService] })
export class ReportsModule {}
```

**Reasoning:** A provider must be exported by its owning module and imported through that module to be visible elsewhere. Avoid broad global modules that expose private services across unrelated trust boundaries.

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** A provider must be exported by its owning module and imported through that module to be visible elsewhere.
- **Reproducible failure:** ReportsModule imports TasksModule but cannot resolve TasksService because it is not exported.
- **Acceptance evidence:** Compile a real Nest TestingModule and resolve ReportsService with a mocked TasksService provider.
- **Risk that remains:** Avoid broad global modules that expose private services across unrelated trust boundaries.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.
