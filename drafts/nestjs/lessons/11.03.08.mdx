## The problem we're solving

ProjectsController directly constructs its service, making the module hard to override. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

A reusable projects feature should encapsulate service, controller and store token in an explicit Nest module. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

```ts
import { Controller, Get, Injectable, Module } from '@nestjs/common';
export const PROJECT_STORE = Symbol('PROJECT_STORE');
export interface ProjectStore { list(): { id: string }[]; }
@Injectable()
export class ProjectsService {
  constructor(@InjectProjectStore() private readonly store: ProjectStore) {}
  list() { return this.store.list(); }
}
// Explicit token decorator keeps the module's dependency boundary clear.
import { Inject } from '@nestjs/common';
function InjectProjectStore(): ParameterDecorator { return Inject(PROJECT_STORE); }
@Controller('projects')
export class ProjectsController {
  constructor(private readonly service: ProjectsService) {}
  @Get() list() { return this.service.list(); }
}
@Module({
  providers: [ProjectsService, { provide: PROJECT_STORE, useValue: { list: () => [{ id: 'p1' }] } }],
  controllers: [ProjectsController],
  exports: [ProjectsService]
})
export class ProjectsModule {}
```

**Reasoning:** A reusable projects feature should encapsulate service, controller and store token in an explicit Nest module. An in-memory demo repository is not production persistence or multi-tenant authorization.

</LessonStep>

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** A reusable projects feature should encapsulate service, controller and store token in an explicit Nest module.
- **Reproducible failure:** ProjectsController directly constructs its service, making the module hard to override.
- **Acceptance evidence:** Resolve ProjectsController from a real Nest module and replace the store token for tests.
- **Risk that remains:** An in-memory demo repository is not production persistence or multi-tenant authorization.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.

## Applied engineering walkthrough

The reusable feature module owns its controller, service and store provider registration. A runtime token lets the service depend on a port without knowing the storage implementation. Exporting the service permits other modules to consume a narrow interface while the controller remains a transport adapter. The in-memory store is intentionally static and not a real multi-tenant repository.
