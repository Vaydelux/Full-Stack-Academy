## The problem we're solving

A service performs two writes without a transaction; one succeeds when the other fails. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Multi-write invariants require a real database transaction with rollback on failure. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

<LessonStep number={2} title="Repair the domain boundary" file="drafts/nestjs/labs/application-transactions/solution.ts" expected="Multi-write invariants require a real database transaction with rollback on failure.">

```ts
export interface PgResult { rowCount: number | null; }
export interface PgClient {
  // Must be a single checked-out PostgreSQL client for the entire transaction.
  query(sql: string, values?: readonly unknown[]): Promise<PgResult>;
}
export async function transfer(db: PgClient, from: string, to: string) {
  if (!from || !to || from === to) throw new Error('Distinct wallet IDs are required');
  await db.query('BEGIN');
  try {
    const debited = await db.query(
      'UPDATE wallets SET balance=balance-1 WHERE id=$1 AND balance>=1 RETURNING id', [from],
    );
    if (debited.rowCount !== 1) throw new Error('Source wallet missing or insufficient balance');
    const credited = await db.query(
      'UPDATE wallets SET balance=balance+1 WHERE id=$1 RETURNING id', [to],
    );
    if (credited.rowCount !== 1) throw new Error('Destination wallet missing');
    await db.query('COMMIT');
  } catch (error) {
    try {
      await db.query('ROLLBACK');
    } catch (rollbackError) {
      throw new AggregateError([error, rollbackError], 'Transfer failed and rollback also failed');
    }
    throw error;
  }
}
```

**Reasoning:** Multi-write invariants require a real database transaction with rollback on failure. A fake in-memory array cannot certify PostgreSQL transaction isolation or rollback. The checked-out database client must remain the **same connection** across BEGIN, both updates, COMMIT and ROLLBACK. The debit requires available balance, both writes must affect exactly one wallet, and a missing recipient must roll back the debit. This is a one-unit educational example, not a production payment or idempotency implementation.

</LessonStep>

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Multi-write invariants require a real database transaction with rollback on failure.
- **Reproducible failure:** A service performs two writes without a transaction; one succeeds when the other fails.
- **Acceptance evidence:** Force a second-write error and verify the database has neither write after rollback.
- **Risk that remains:** A fake in-memory array cannot certify PostgreSQL transaction isolation or rollback.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.

## Applied engineering walkthrough

A transaction is a database boundary, not just two awaited statements. The sample uses a single checked-out client, BEGIN, conditional debit, credit and COMMIT; rowCount confirms that each update affected exactly one row. On failure it attempts rollback and preserves a rollback failure alongside the original error. It transfers one unit for teaching purposes, not a financial ledger. Opposite-direction transfers can deadlock; production needs consistent lock ordering or bounded whole-transaction retries.

### Diagnose the concrete failure

Exercise successful transfer, insufficient balance and missing destination using a recording client. Verify the expected sequence and rollback path, then repeat against a disposable real database. If COMMIT loses its acknowledgement, the client may not know whether the transfer committed; blindly retrying is unsafe without an idempotency protocol.

### Independent exercise and evidence

Design a two-session test for competing debits from the same wallet. Assert balance conservation and no negative balance in real PostgreSQL, rather than trusting call order alone. Describe a stable operation key and explain how a committed receipt would resolve uncertain outcomes.
