## The problem we're solving

A service performs two writes without a transaction; one succeeds when the other fails. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Multi-write invariants require a real database transaction with rollback on failure. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

**Prediction:** A service performs two writes without a transaction; one succeeds when the other fails. Name the exact state that differs after this failure, and who can observe it.

```ts
export interface PgClient { query(sql: string, values?: unknown[]): Promise<unknown>; }
export async function transfer(db: PgClient, from: string, to: string) {
  await db.query('BEGIN');
  try {
    await db.query('UPDATE wallets SET balance=balance-1 WHERE id=$1', [from]);
    await db.query('UPDATE wallets SET balance=balance+1 WHERE id=$1', [to]);
    await db.query('COMMIT');
  } catch (error) {
    await db.query('ROLLBACK');
    throw error;
  }
}
```

**Reasoning:** Multi-write invariants require a real database transaction with rollback on failure. A fake in-memory array cannot certify PostgreSQL transaction isolation or rollback.

</LessonStep>

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Multi-write invariants require a real database transaction with rollback on failure.
- **Reproducible failure:** A service performs two writes without a transaction; one succeeds when the other fails.
- **Acceptance evidence:** Force a second-write error and verify the database has neither write after rollback.
- **Risk that remains:** A fake in-memory array cannot certify PostgreSQL transaction isolation or rollback.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.
