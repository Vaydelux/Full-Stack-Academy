## The problem we're solving

An API returns a stored account object including passwordHash and internalRole. Building a domain feature demands more than a decorated controller. Real services have invariants, dependencies, persistence contracts and externally visible behavior. When any one layer owns work it cannot safely verify, the resulting application becomes difficult to test and may expose private state.

## Build the mental model

Persistent entities may hold sensitive fields that must not be serialized into public DTOs. Design the feature by drawing arrows from controller → application service → repository/port → persistence. Dependencies should point toward stable contracts; inbound HTTP is an adapter, not the business model. A real Nest module composes these pieces, while transaction boundaries belong near the persistence operation that must be atomic.

**Prediction:** An API returns a stored account object including passwordHash and internalRole. Name the exact state that differs after this failure, and who can observe it.

**Scope:** NestJS 12, Node.js 24, TypeScript 6. This is **staged authoring only**. It has not passed a real installed Nest build, PostgreSQL integration (when applicable), or browser/manual accessibility qualification.

## Architecture trade-offs

Directly constructing a service or returning a database entity can be tempting because it reduces boilerplate. It also hides dependency seams and blurs the trust boundary. The practical alternative is not to abstract everything; keep one small interface for a dependency that legitimately varies and enforce invariants in exactly one authoritative place. Favor explicit module imports/exports over globally available providers.

- **Correctness invariant:** Persistent entities may hold sensitive fields that must not be serialized into public DTOs.
- **Reproducible failure:** An API returns a stored account object including passwordHash and internalRole.
- **Acceptance evidence:** An account DTO response has only public id and displayName; hidden fields are absent.
- **Risk that remains:** DTO shaping is not role authorization; enforce permissions before selecting records.

In a multi-request system, repeat the test with two independent users and at least one failure after an intermediate operation. A UI test cannot prove a transaction rollback; only the real persistence adapter can.
