## The problem we're solving

A serialized user record includes passwordHash in the HTTP response. The request pipeline is a composition of stages rather than a single controller method: middleware prepares the request, a guard decides permission, pipes parse inputs, interceptors wrap handler execution and filters normalize failures. Each stage needs its own test because correct TypeScript does not prove real HTTP behavior.

## Build the mental model

Response DTOs should expose intentionally selected public fields rather than returning persistent entities unchanged. The stage where the problem occurs matters: moving validation into an authorization check or moving a security decision into a response interceptor can accidentally expose the handler. Trace the request lifecycle from ingress to exit, and record both expected success and denial.

**Prediction:** A serialized user record includes passwordHash in the HTTP response. Explain whether the handler is reached, and what an HTTP client should observe.

**Release scope:** These examples target NestJS 12, Node 24, TypeScript 6. They are authored drafts, not compiler-qualified or published material. Never assume JSON serialization or a TypeScript interface automatically redacts secrets.

<LessonStep number={2} title="Repair the correct stage" file="drafts/nestjs/labs/structured-responses/solution.ts" expected="Response DTOs should expose intentionally selected public fields rather than returning persistent entities unchanged.">

```ts
export interface Account { id: string; displayName: string; passwordHash: string; }
export interface PublicAccount { id: string; displayName: string; }
export function accountResponse(account: Account): PublicAccount {
  return { id: account.id, displayName: account.displayName };
}
```

**Why this design:** Response DTOs should expose intentionally selected public fields rather than returning persistent entities unchanged. Never assume JSON serialization or a TypeScript interface automatically redacts secrets.

</LessonStep>

## Operational failure analysis

If the UI shows a generic error, classify the failure at the nearest authoritative boundary. A 400 is invalid input, a 403 is denied access, a 404 is missing resource and a 503 is a failed dependency; do not collapse these into one “success” or one database error. Log correlation IDs with bounded length rather than sensitive headers. Run both a happy-path request and a deliberate failure using independently constructed test clients.
