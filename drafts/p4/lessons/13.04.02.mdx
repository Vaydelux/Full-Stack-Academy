## Integration defect

**Pooled vs direct connection.** Direct and pooled connections have different connection/session characteristics. Migrations, prepared statements and session-affine operations require explicit compatibility checks.

**What fails in an actual application:** The starter silently routes schema changes through a possibly transaction-pooled session, where connection/session assumptions may break.

A full-stack application can use both a Supabase client and a direct Prisma ORM 7 PostgreSQL adapter. These access paths do not automatically share the same user authorization context. The browser may have a valid JWT while a server's database role can read far more than that JWT would authorize.

```ts
function required(name: "DATABASE_DIRECT_URL" | "DATABASE_POOL_URL") {
  const value = process.env[name];
  if (!value) throw new Error("Missing " + name);
  return value;
}
export const dbEndpoints = {
  migrations: required("DATABASE_DIRECT_URL"),
  runtime: required("DATABASE_POOL_URL"),
};
```

**Repair:** Separate the migration and runtime URL variables, choose tested endpoints deliberately, and record pooler mode and total connection budget.

This is a teaching excerpt; configure generated types, verified request guards, safe error mapping, and actual database credentials separately.

## API, RLS and migration trade-offs

Direct and pooled connections have different connection/session characteristics. Migrations, prepared statements and session-affine operations require explicit compatibility checks.

Separate the migration and runtime URL variables, choose tested endpoints deliberately, and record pooler mode and total connection budget.

Pooler modes and endpoint availability vary by project and plan. Verify current Supabase docs and live connection strings instead of hardcoding a provider host or port.

Explicitly choose how identity is propagated between Next.js, NestJS, Prisma, and Supabase. When a privileged server role bypasses RLS, the NestJS service must check permissions and the database role should still be restricted. Prefer verified membership from trusted server data over user-editable metadata or query parameters.

## Applied persistence walkthrough

Direct and pooled endpoints have different capacity and session semantics. Migration tooling may require a direct or suitable session-mode connection; runtime pools should use a compatible endpoint and mode. The sample separates environment names but does not verify host, TLS, role or pooler support. Consult the actual project connection instructions rather than copying URLs from another environment.

### Diagnose the concrete failure

Confirm both endpoints against the disposable project's settings, redact secrets and test missing variables independently. Inspect current role/database on each permitted connection. Exercise a migration on the migration target and an ordinary request on the runtime path; verify neither points to production.

### Independent exercise and evidence

Plan the runtime connection budget across API instances and workers, then a separate migration role with approved elevated privileges. Record pool mode, version, endpoint identity and session-feature compatibility.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use pinned tooling and a disposable local or explicitly approved test environment. Preserve the starter and solution; source review does not qualify real database roles or authorization.

Verify permitted rows, denied rows, mutation effects and clean database recreation from migrations.
