## Secure Storage and Realtime problem

**Content type and size validation.** Browser MIME and file.size checks improve UX but are attacker-controlled. Real upload security combines bucket-enforced limits, server-side content validation, quarantine and strict path ownership.

**Unsafe starter behavior:** The starter trusts the browser's file.type and original filename. A renamed executable or oversize payload can bypass those checks.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/validate-storage-content-size/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
const maxBytes = 5 * 1024 * 1024;
const allowed = new Set(["application/pdf", "image/png"]);
if (file.size <= 0 || file.size > maxBytes || !allowed.has(file.type))
  throw new Error("Rejected upload");
// On the server, independently sniff actual bytes, validate filename/path,
// scan or quarantine untrusted content, and verify the active bucket limit.
const safePath = verifiedUserId + "/" + crypto.randomUUID();
const { error } = await supabase.storage
  .from("academy_private_docs").upload(safePath, file, {
    contentType: file.type,
    upsert: false,
  });
if (error) throw new Error("Upload failed");
```

**Security rationale:** Validate type/size early, upload to a verified user-owned non-overwriting key, and independently inspect bytes and scan risky content on the server before making it consumable.

Teaching excerpts may depend on separately verified Auth guards, bucket policies, or helper types. They must be integrated with the actual Supabase client version, service configuration and database schema before any runtime qualification.

</LessonStep>

## Architecture and lifecycle trade-offs

Browser MIME and file.size checks improve UX but are attacker-controlled. Real upload security combines bucket-enforced limits, server-side content validation, quarantine and strict path ownership.

Validate type/size early, upload to a verified user-owned non-overwriting key, and independently inspect bytes and scan risky content on the server before making it consumable.

The snippet's browser-side checks cannot identify malicious bytes. Configure bucket allowed MIME/size, enforce quotas and add server-side malware scanning when risk justifies it.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.

## Applied persistence walkthrough

Browser MIME type and size checks improve usability but are not authoritative because clients control metadata. The storage service must enforce actual size limits, and a trusted processing path should inspect file bytes before marking a document usable. Content sniffing is not a full malware guarantee. The sample upload disables overwrite and chooses a randomized user-prefixed key.

### Diagnose the concrete failure

Attempt a valid small file, empty file, oversized file and content with a misleading extension or MIME type. Confirm the browser check alone can be bypassed and that the trusted ingestion path still rejects or quarantines invalid data. Test path collisions and cross-user access without uploading real sensitive files.

### Independent exercise and evidence

Design a pending/quarantined/ready state machine with size checks, type verification and a scanning decision. Record synthetic byte counts, accepted formats and status transitions. Do not serve unverified uploads as trusted content.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated test identities, storage and channels. Preserve the existing starter and solution; source review cannot qualify live upload, webhook or Realtime security.
