## Real-world problem

**select include and relation loading.** select defines an allowlisted response projection. include eagerly includes relations, which can be convenient but must not become an automatic public-response serializer.

**Defect in the first implementation:** The starter includes every owner column: internalRole, passwordHash and private email fields can leak into serialized responses if the model changes.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/safe-prisma-projections/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
async function listTasks(db: PrismaClient, tenantId: string) {
  return db.task.findMany({
    where: { tenantId },
    select: {
      id: true, title: true,
      owner: { select: { id: true, displayName: true } },
    },
    take: 20,
    orderBy: { id: "asc" },
  });
}
```

**Repair reasoning:** Select only the task and owner fields the route is authorized to return; bound the result and define an order.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

</LessonStep>

## Architecture and implementation choices

select defines an allowlisted response projection. include eagerly includes relations, which can be convenient but must not become an automatic public-response serializer.

Select only the task and owner fields the route is authorized to return; bound the result and define an order.

A safe projection avoids oversharing but does not grant access to the selected row; combine projection with RLS or server-side object authorization.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.
