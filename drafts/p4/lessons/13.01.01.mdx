## Why this lesson matters

**Prisma schema language.** A Prisma schema declares models, scalar types, relations, generators and datasources. In Prisma ORM 7, datasource connection URLs belong in the Prisma configuration file, while the generator needs an explicit output directory.

**Broken real-world assumption:** The starter stores tasks without a tenant key. A strongly typed client cannot reconstruct ownership that the physical schema never represented.

An ORM is not an access-control mechanism or a database deployment tool by itself. Treat the generated TypeScript types, database constraints, migration history and the authenticated request context as separate boundaries. The learner should be able to explain what each boundary guarantees and what it does not.

<LessonStep number={2} title="Implement the safe version" file="drafts/p4/labs/schema-and-generator/solution.prisma" expected="A version-7-compatible repair with explicit trust boundaries.">

```prisma
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}
datasource db { provider = "postgresql" }
model Task {
  id       Int    @id @default(autoincrement())
  tenantId String
  title    String
  @@index([tenantId, id])
}
```

**How the repair works:** Add tenantId to the Task model and index the frequent tenant-scoped lookup. Keep database connection credentials outside schema.prisma.

## Architecture, correctness and performance

A Prisma schema declares models, scalar types, relations, generators and datasources. In Prisma ORM 7, datasource connection URLs belong in the Prisma configuration file, while the generator needs an explicit output directory.

Add tenantId to the Task model and index the frequent tenant-scoped lookup. Keep database connection credentials outside schema.prisma.

No schema generator or @unique attribute grants a caller read permission. Never treat a Prisma model type as a replacement for Postgres RLS or server authorization.

A production-ready persistence boundary has to address error mapping, least-privileged database credentials, transaction/connection lifecycle, tenant authorization and request cancellation. Whenever schema changes are involved, review migration SQL and compatibility with the previous app version. Never expose database credentials in a `NEXT_PUBLIC_` variable or include them in a public web bundle.

## Applied persistence walkthrough

Separate the Prisma schema, generated client and physical database schema. Adding tenantId makes ownership representable; the composite index supports tenant-scoped lookup but does not filter rows by itself. The primary key is globally unique in this example, so two tenants cannot each reuse task ID 1. The generated client reflects the model, while deployed migrations establish the actual database constraints.

### Diagnose the concrete failure

Never infer access control from an index.
