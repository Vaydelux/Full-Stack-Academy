## Integration defect

**Authorization in NestJS.** NestJS guards authenticate requests but domain authorization must also verify tenant membership and resource-specific permissions before Prisma executes privileged queries.

**What fails in an actual application:** A user can replace the query parameter tenantId and ask a superuser-backed repository to return another tenant's records.

A full-stack application can use both a Supabase client and a direct Prisma ORM 7 PostgreSQL adapter. These access paths do not automatically share the same user authorization context. The browser may have a valid JWT while a server's database role can read far more than that JWT would authorize.

Decide which component authenticates the caller, which verifies tenant or resource membership, which PostgreSQL role executes the query, and which schema is exposed via the Data API. Write a failure assertion before changing the code. The examples use synthetic actors and isolated databases only.

## Guided implementation

<LessonStep number={1} title="Reproduce the unsafe integration" file="drafts/p4/labs/nestjs-trusted-actor-boundary/starter.ts" expected="Explain the exact scope, role, or migration boundary that fails.">

```ts
// Dangerous: a controller accepts tenantId supplied by the browser.
@Get("tasks")
list(@Query("tenantId") tenantId: string) {
  return this.prisma.task.findMany({ where: { tenantId } });
}
```

**Defect:** A user can replace the query parameter tenantId and ask a superuser-backed repository to return another tenant's records.

Observe the failure in a disposable test environment. A SQL statement executing successfully does not prove it was authorized.

</LessonStep>

<LessonStep number={2} title="Enforce the correct boundary" file="drafts/p4/labs/nestjs-trusted-actor-boundary/solution.ts" expected="Tenant or environment decisions come from verified server context.">

```ts
@Get("tasks")
@UseGuards(JwtAuthGuard)
list(@Req() req: AuthenticatedRequest) {
  const actor = req.authenticatedActor; // verified by guard
  if (!actor?.tenantId || !actor?.userId)
    throw new UnauthorizedException();
  return this.tasksService.listForActor(actor);
}
// Service checks membership and projects only allowed task fields.
```

**Repair:** Obtain verified identity from the authentication guard and delegate object-level permission checks to a service. Do not pass raw tenant query values as authority.

This is a teaching excerpt; configure generated types, verified request guards, safe error mapping, and actual database credentials separately.

</LessonStep>

<LessonStep number={3} title="Run cross-boundary allowed and denied tests" file="drafts/p4/labs/nestjs-trusted-actor-boundary/acceptance.md" expected="Record actual test identities, results and the denial evidence.">

**Allowed scenario:** The same authenticated alpha user can list only permitted tasks using a verified membership table and least-privileged DTO response.

**Denied scenario:** Log in as alpha, then set query tenantId=beta and enumerate a known beta task. The endpoint must deny or ignore the untrusted parameter.

**Unresolved risks:** A TypeScript request interface does not validate the JWT by itself. The guard must verify signature, issuer, expiry, audience/session and fresh permissions when required.

A code-fence source match is not a PostgreSQL authorization evaluation, and a service-role query does not simulate an ordinary user.

</LessonStep>

## API, RLS and migration trade-offs

NestJS guards authenticate requests but domain authorization must also verify tenant membership and resource-specific permissions before Prisma executes privileged queries.

Obtain verified identity from the authentication guard and delegate object-level permission checks to a service. Do not pass raw tenant query values as authority.

A TypeScript request interface does not validate the JWT by itself. The guard must verify signature, issuer, expiry, audience/session and fresh permissions when required.

Explicitly choose how identity is propagated between Next.js, NestJS, Prisma, and Supabase. When a privileged server role bypasses RLS, the NestJS service must check permissions and the database role should still be restricted. Prefer verified membership from trusted server data over user-editable metadata or query parameters.
