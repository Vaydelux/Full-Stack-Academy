## Authentication problem

**Lab safe login flow.** A secure login flow is more than successful credential entry: server-side verified identity, membership authorization, RLS-backed reads, session refresh and logout must work together.

**Broken starting assumption:** The starter trusts user-editable user_metadata and getSession as a server-side role decision, allowing an attacker to claim isAdmin.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/end-to-end-login-boundary/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
const { data: identity, error } = await supabase.auth.getUser();
if (error || !identity.user) throw new Error("Unauthenticated");
const { data: membership, error: membershipError } = await supabase
  .from("memberships")
  .select("tenant_id, role")
  .eq("user_id", identity.user.id)
  .eq("tenant_id", verifiedTenantId)
  .maybeSingle();
if (membershipError || !membership) throw new Error("Forbidden");
// Memberships table itself must have an RLS ownership policy.
return { userId: identity.user.id, tenantId: membership.tenant_id,
  role: membership.role };
```

**Repair reasoning:** Use a fresh getUser identity, look up resource-scoped membership from a protected table and deny missing memberships. Never use client-editable metadata as an authorization source.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

## Trust boundaries and operational choices

A secure login flow is more than successful credential entry: server-side verified identity, membership authorization, RLS-backed reads, session refresh and logout must work together.

Use a fresh getUser identity, look up resource-scoped membership from a protected table and deny missing memberships. Never use client-editable metadata as an authorization source.

The membership lookup requires its own RLS policy and Grants. This sample does not automatically secure update/delete endpoints or privileged Prisma access.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

A safe login flow must bind a verified identity to authoritative membership data. The snippet fetches a current user and queries a specific tenant membership. The supplied tenant candidate is not trusted just because it appears in a variable; the membership query is the authorization check. RLS on memberships must prevent other users' membership rows from being exposed. Privileged paths need equivalent independent checks.

### Diagnose the concrete failure

Seed two fake users and tenants. Verify an authorized membership is returned, a nonexistent or foreign membership is denied, and expired or invalid credentials fail before data access. Test duplicate memberships as a data-integrity error; maybeSingle does not make the relationship unique. Inspect actual row-policy behavior as each user.

### Independent exercise and evidence

Design a route that handles a tenant switch only after current membership is verified. Include revoked membership and no-session cases, safe public errors, and role-specific action checks. Record identity and tenant as synthetic IDs and expected versus actual authorization outcomes.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated synthetic identities and the pinned SDK. Preserve the existing starter and solution; source inspection does not establish actual Auth or session security.
