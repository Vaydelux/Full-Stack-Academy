## Authentication problem

**MFA and recovery.** Multi-factor enrollment, challenge and verification are separate states. Sensitive actions should check the current session's assurance level instead of relying on a local boolean.

**Broken starting assumption:** The starter marks MFA as completed immediately after enrollment, even if the user never proves control of the TOTP factor.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/mfa-enrollment-and-verify/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
const enrolled = await supabase.auth.mfa.enroll({ factorType: "totp" });
if (enrolled.error) throw new Error("MFA enrollment failed");
const factorId = enrolled.data.id;
const challenged = await supabase.auth.mfa.challenge({ factorId });
if (challenged.error) throw new Error("MFA challenge failed");
const result = await supabase.auth.mfa.verify({
  factorId, challengeId: challenged.data.id, code: submittedTotpCode,
});
if (result.error) throw new Error("MFA verification failed");
const assurance = await supabase.auth.mfa.getAuthenticatorAssuranceLevel();
if (assurance.error || assurance.data?.currentLevel !== "aal2")
  throw new Error("Strong session assurance required");
```

**Repair reasoning:** Enroll TOTP, challenge, verify a one-time code and confirm the current Auth assurance level before allowing an MFA-protected operation.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

## Trust boundaries and operational choices

Multi-factor enrollment, challenge and verification are separate states. Sensitive actions should check the current session's assurance level instead of relying on a local boolean.

Enroll TOTP, challenge, verify a one-time code and confirm the current Auth assurance level before allowing an MFA-protected operation.

Do not log factor secrets, recovery codes or TOTP values. Implement recovery and anti-lockout policies that fit the product's risk model.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

Enrolling a factor does not automatically establish higher assurance for the current session. The flow must verify the challenge and then check the session assurance level. Enrollment also needs a secure user interface for the generated secret or QR code. Recovery and factor removal require separate policies, and sensitive server operations must enforce the required assurance independently.

### Diagnose the concrete failure

Use a synthetic account to enroll and challenge a TOTP factor. Exercise an invalid or expired code and confirm the protected action is denied until the required assurance is present. Verify the backend's enforcement rather than relying on the client display. Never record actual factor secrets or codes.

### Independent exercise and evidence

Design recovery for a lost factor with an independently verified support or account recovery process. Specify reauthentication, audit events and rate limiting. Record the expected denial and successful assurance transition without exposing recovery secrets.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated synthetic identities and the pinned SDK. Preserve the existing starter and solution; source inspection does not establish actual Auth or session security.
