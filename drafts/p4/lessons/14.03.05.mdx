## Security defect and threat model

**Bucket RLS and signed URLs.** Storage object metadata is protected by policies on storage.objects, and signed URLs are time-limited bearer capabilities. A private bucket is not automatically private if a policy grants every user read access.

**The vulnerable starting point:** The starter lets every authenticated user read every object in the private-documents bucket.

An attacker may know an ID, send arbitrary query parameters, or hold a legitimate authenticated account. An application is not secure merely because the login screen works. The database and the authenticated server must prevent one actor from accessing another actor's rows or private objects.

## Guided repair

<LessonStep number={1} title="Reproduce the permissive or privileged access path" file="drafts/p4/labs/private-storage-owner-policies/starter.sql" expected="Identify why an authenticated request may still cross its authorization boundary.">

```sql
CREATE POLICY lab_private_objects_read ON storage.objects
 FOR SELECT TO authenticated
 USING (bucket_id = 'academy_private_docs');
```

**Why this fails:** The starter lets every authenticated user read every object in the private-documents bucket. Do not accept a successful schema statement as proof of row privacy.

</LessonStep>

<LessonStep number={2} title="Write the defensive policy or server boundary" file="drafts/p4/labs/private-storage-owner-policies/solution.sql" expected="Constrain operations by caller identity and permitted resources.">

```sql
CREATE POLICY lab_private_objects_owner_read ON storage.objects
 FOR SELECT TO authenticated
 USING (
   bucket_id = 'academy_private_docs'
   AND (storage.foldername(name))[1] = (SELECT auth.uid())::text
 );
```

**How the defense works:** Constrain object read policy to a per-user leading folder matching auth.uid(); issue short-lived signed URLs only after authorization.

</LessonStep>

## Security review and implementation details

Storage object metadata is protected by policies on storage.objects, and signed URLs are time-limited bearer capabilities. A private bucket is not automatically private if a policy grants every user read access.

Constrain object read policy to a per-user leading folder matching auth.uid(); issue short-lived signed URLs only after authorization.

A signed URL is a bearer capability for its lifetime; do not publish it. Storage upsert can require INSERT + SELECT + UPDATE. Server/service bypass keys must never appear in the browser.

RLS applies subject to PostgreSQL roles, table ownership, policy composition and operation type. In an exposed schema, verify grants and RLS together. For writes, review INSERT WITH CHECK and UPDATE USING/WITH CHECK, not just SELECT. In Supabase, do not use user-editable `user_metadata` as authority for privileged roles. A service-role client may bypass RLS; it must not be used to repair a client permission error.

## Applied persistence walkthrough

A private bucket uses access rules over storage.objects for ordinary client operations. The shown SELECT policy restricts reads to a particular bucket and a first path segment matching the current user. It does not implement membership-based tenant sharing, upload permission or signed-link issuance. A signed URL is a bearer capability within its validity period, not a permanent authorization rule.

### Diagnose the concrete failure

Create synthetic files under two user prefixes in a private test bucket. Verify direct owner read and cross-prefix denial with actual user sessions. Test a public URL and an authorized signed URL separately, including expiry; do not log the signed URL itself. Check all applicable storage policies and bucket visibility.

### Independent exercise and evidence

Design separate policies for new upload, read and replacement, noting that upsert requires additional permissions. Record bucket, synthetic object identifiers, permitted operations and denied access. Consider whether tenant membership is required in addition to path ownership.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use an isolated Supabase environment and real non-bypass caller roles. Preserve the existing starter and solution; source review cannot certify row policies or authorization.

## Security extension and release conditions

Extend the access matrix to SELECT, INSERT, UPDATE and DELETE where applicable. Build a pgTAP or equivalent isolated integration test that fails on the deliberately permissive starter and passes on the narrow policy. Run requests through the same Supabase Data API and authenticated route as the real app; test with the least-privileged role first. Include a second database connection if RLS behavior depends on transaction state.

Keep copies of all policy test results sanitized. Do not move this manuscript to the published registry before an explicit human security review and actual local RLS test runs.
