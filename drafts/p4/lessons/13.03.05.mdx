<LessonStep number={2} title="Apply the narrow corrected boundary" file="drafts/p4/labs/prisma-multi-schema-boundaries/solution.prisma" expected="The data and deployment invariant is explicitly enforced or observable.">

```prisma
datasource db {
  provider = "postgresql"
  schemas = ["app", "audit"]
}
model AuditEvent {
  id Int @id @default(autoincrement())
  action String
  @@schema("audit")
}
model Task {
  id Int @id @default(autoincrement())
  title String
  @@schema("app")
}
```

**Why it is safer:** Declare intended schemas and map each model deliberately. Test actual GRANT/revoke privileges and confirm the private schema is not Data API-exposed.

Do not assume a successful CLI or TypeScript compile proves that the caller was authorized. Generated types protect shapes, not per-request permissions. Similarly, a DB transaction cannot roll back independent external side effects.

</LessonStep>

## Design trade-offs and real-world constraints

PostgreSQL schemas separate namespaces and can support permission boundaries. Prisma multi-schema modeling uses datasource schemas and explicit @@schema assignments.

Declare intended schemas and map each model deliberately. Test actual GRANT/revoke privileges and confirm the private schema is not Data API-exposed.

A PostgreSQL schema name or Prisma @@schema does not itself provide access control. Misconfigured grants, SECURITY DEFINER functions and privileged Prisma roles can still leak data.

In a multi-tenant API, input validation, role-aware database credentials, optimistic concurrency, migration review and response-shape controls must be considered together. Favor bounded queries and explicit domain operations over returning raw privileged ORM interfaces to HTTP handlers. Record the query plan or migration state instead of guessing.

## Applied persistence walkthrough

PostgreSQL schemas organize database objects; they do not automatically isolate tenants or authorize roles. Prisma multi-schema mapping associates models with app or audit. Model names and SQL schema qualification must be reviewed when generating migrations. The runtime role should not gain audit write access merely because both models exist in one generated client.

### Diagnose the concrete failure

Inspect the resulting SQL on a disposable target and confirm each table resides in the expected schema. Run an application-role read and a forbidden audit mutation. Check schema USAGE and object grants separately. An introspection result cannot prove least privilege.

### Independent exercise and evidence

Design independent DDL ownership and runtime grants for app and audit schemas. Explain how a new schema is introduced without broadening the public API surface. Record table locations, effective role and negative privilege results.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use the pinned Prisma 7 toolchain and disposable PostgreSQL database. Preserve the starter and solution; source review does not qualify generated code or authorization.
