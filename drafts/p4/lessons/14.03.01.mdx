## Security defect and threat model

**RLS policy mechanics.** PostgreSQL RLS filters records according to the caller's SQL role and policy predicates. When RLS is enabled, access is denied by default until a policy matches, except for privileged bypass roles and table owners unless FORCE RLS applies.

**The vulnerable starting point:** USING (true) grants every authenticated caller visibility into all task rows, including another user's private tasks.

An attacker may know an ID, send arbitrary query parameters, or hold a legitimate authenticated account. An application is not secure merely because the login screen works. The database and the authenticated server must prevent one actor from accessing another actor's rows or private objects.

## Guided repair

<LessonStep number={1} title="Reproduce the permissive or privileged access path" file="drafts/p4/labs/deny-by-default-rls/starter.sql" expected="Identify why an authenticated request may still cross its authorization boundary.">

```sql
ALTER TABLE public.academy_lab_tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY lab_tasks_open_read ON public.academy_lab_tasks
 FOR SELECT TO authenticated USING (true);
```

**Why this fails:** USING (true) grants every authenticated caller visibility into all task rows, including another user's private tasks. Do not accept a successful schema statement as proof of row privacy.

</LessonStep>

<LessonStep number={2} title="Write the defensive policy or server boundary" file="drafts/p4/labs/deny-by-default-rls/solution.sql" expected="Constrain operations by caller identity and permitted resources.">

```sql
ALTER TABLE public.academy_lab_tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY lab_tasks_owner_read ON public.academy_lab_tasks
 FOR SELECT TO authenticated
 USING (owner_id = (SELECT auth.uid()));
```

**How the defense works:** Use a narrowly scoped SELECT policy with an authenticated role and an owner_id predicate tied to auth.uid(). Test two users and anon behavior.

</LessonStep>

<LessonStep number={3} title="Prove allow and deny with real Supabase identities" file="drafts/p4/labs/deny-by-default-rls/acceptance.md" expected="A real denied cross-actor operation and an authorized operation are independently observed.">

**Required positive test:** Apply to an isolated local Supabase stack, seed two users and run authenticated API and pgTAP allow/deny tests. Check GRANT privileges separately from RLS.

**Required negative test:** With alpha's authenticated token, request beta's task ID. The Data API must return no row; anon must also not retrieve private records.

**Caveat:** Policy tests must use the actual caller role; a service-role key bypasses RLS and cannot demonstrate that an ordinary JWT is protected. Table owners may bypass unless configured otherwise.

A static code-fence match or even a SQL statement compiling is not evidence that a privileged role, policy composition, JWT, Storage signed URL or application-level permission boundary is correct.

</LessonStep>

## Security review and implementation details

PostgreSQL RLS filters records according to the caller's SQL role and policy predicates. When RLS is enabled, access is denied by default until a policy matches, except for privileged bypass roles and table owners unless FORCE RLS applies.

Use a narrowly scoped SELECT policy with an authenticated role and an owner_id predicate tied to auth.uid(). Test two users and anon behavior.

Policy tests must use the actual caller role; a service-role key bypasses RLS and cannot demonstrate that an ordinary JWT is protected. Table owners may bypass unless configured otherwise.

RLS applies subject to PostgreSQL roles, table ownership, policy composition and operation type. In an exposed schema, verify grants and RLS together. For writes, review INSERT WITH CHECK and UPDATE USING/WITH CHECK, not just SELECT. In Supabase, do not use user-editable `user_metadata` as authority for privileged roles. A service-role client may bypass RLS; it must not be used to repair a client permission error.

## Bug Hunt and regression matrix

1. Predict the disclosure caused by the starter: USING (true) grants every authenticated caller visibility into all task rows, including another user's private tasks.
2. Confirm one valid user can complete the intended action.
3. Attempt the forbidden action with a different user: With alpha's authenticated token, request beta's task ID. The Data API must return no row; anon must also not retrieve private records.
4. Apply the policy/server repair: Use a narrowly scoped SELECT policy with an authenticated role and an owner_id predicate tied to auth.uid(). Test two users and anon behavior.
5. Retest with anon, two authenticated identities and any privileged path: Policy tests must use the actual caller role; a service-role key bypasses RLS and cannot demonstrate that an ordinary JWT is protected. Table owners may bypass unless configured otherwise.

## Security extension and release conditions

Extend the access matrix to SELECT, INSERT, UPDATE and DELETE where applicable. Build a pgTAP or equivalent isolated integration test that fails on the deliberately permissive starter and passes on the narrow policy. Run requests through the same Supabase Data API and authenticated route as the real app; test with the least-privileged role first. Include a second database connection if RLS behavior depends on transaction state.

Keep copies of all policy test results sanitized. Do not move this manuscript to the published registry before an explicit human security review and actual local RLS test runs.
