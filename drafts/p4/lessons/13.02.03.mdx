## Real-world problem

**Create update delete.** Create, update and delete operations are authorization-sensitive mutations. updateMany with a tenant and ID predicate returns an affected-row count that lets the service detect no matching authorized record.

**Defect in the first implementation:** The starter changes any row with the supplied ID and exposes the full database result without checking tenant ownership.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/scoped-prisma-writes/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
async function renameTask(
  db: PrismaClient, tenantId: string, taskId: number, title: string,
) {
  if (!tenantId || title.trim().length < 3 || title.length > 100)
    throw new Error("Invalid input");
  const result = await db.task.updateMany({
    where: { id: taskId, tenantId },
    data: { title: title.trim() },
  });
  if (result.count !== 1) throw new Error("Task not found");
  return { updated: true };
}
```

**Repair reasoning:** Require verified tenant identity, validate title length, scope updateMany to the tenant, and handle zero affected rows. For create/delete, adopt the same identity and conflict checks.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

</LessonStep>

## Architecture and implementation choices

Create, update and delete operations are authorization-sensitive mutations. updateMany with a tenant and ID predicate returns an affected-row count that lets the service detect no matching authorized record.

Require verified tenant identity, validate title length, scope updateMany to the tenant, and handle zero affected rows. For create/delete, adopt the same identity and conflict checks.

Even a tenant-matched update may violate finer-grained project membership rules. The complete policy belongs in domain authorization, not merely a tenant filter.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.
