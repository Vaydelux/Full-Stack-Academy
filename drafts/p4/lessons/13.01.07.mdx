## Why this lesson matters

**Seed strategies.** A good seed script is deterministic and repeatable on a disposable environment. Prisma ORM v7 requires an explicit prisma db seed command configured through migrations.seed.

**Broken real-world assumption:** The starter is not idempotent: rerunning a seed may create duplicates or fail after a partial previous run.

An ORM is not an access-control mechanism or a database deployment tool by itself. Treat the generated TypeScript types, database constraints, migration history and the authenticated request context as separate boundaries. The learner should be able to explain what each boundary guarantees and what it does not.

## Architecture, correctness and performance

A good seed script is deterministic and repeatable on a disposable environment. Prisma ORM v7 requires an explicit prisma db seed command configured through migrations.seed.

Use a unique business key with upsert, isolate dev seed data, keep deterministic IDs and values, and configure migrations.seed to point at the script.

An idempotent upsert can still overwrite sensitive production data if the connection URL is wrong. Environment isolation is mandatory.

A production-ready persistence boundary has to address error mapping, least-privileged database credentials, transaction/connection lifecycle, tenant authorization and request cancellation. Whenever schema changes are involved, review migration SQL and compatibility with the previous app version. Never expose database credentials in a `NEXT_PUBLIC_` variable or include them in a public web bundle.

## Applied persistence walkthrough

A seed is an explicit development or test data operation, not a production migration. The compound unique key identifies the demo tenant/email pair. Upsert with an empty update preserves an existing record instead of generating a new user on each run. Prisma 7 requires an explicit seed command and configured seed script; never assume migration automatically seeds.

### Diagnose the concrete failure

Run the configured seed twice on the same disposable database and verify one demo user with the same identity. Compare a plain create-based seed, which either duplicates records or hits uniqueness. Test that a refusal guard blocks an unrelated environment before connecting.

### Independent exercise and evidence

Design deterministic fixture data for two tenants with fake users and projects. Explain which rows may be reset safely and how to avoid removing unrelated records. Record the two run counts, key identity and explicit target check.
