## Authentication problem

**OAuth and PKCE.** OAuth authenticates users through a configured provider; PKCE binds the authorization code flow to the initiating client. Callback destinations must be strictly allowlisted.

**Broken starting assumption:** The starter lets an untrusted redirect destination receive the OAuth callback flow, creating a redirect/session-handling risk.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/pkce-approved-redirects/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
const appOrigin = process.env.NEXT_PUBLIC_APP_ORIGIN;
if (!appOrigin) throw new Error("Missing app origin");
const redirectTo = new URL("/auth/callback", appOrigin).toString();
const { error } = await supabase.auth.signInWithOAuth({
  provider: "google", options: { redirectTo },
});
if (error) throw new Error("Unable to start sign-in");
// Handle code exchange in the dedicated, trusted callback route.
```

**Repair reasoning:** Derive the callback from an approved application origin and handle the returned code through a trusted auth callback that verifies flow state and exchanges the code for a session.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

<LessonStep number={3} title="Prove both allowed and rejected states" file="drafts/p4/labs/pkce-approved-redirects/acceptance.md" expected="One authenticated success and one negative session/authorization case are recorded.">

**Allowed behavior:** In a local test identity provider flow, verify approved redirects, PKCE flow tracking, callback expiration and a single authenticated server session.

**Denied behavior:** Inject an external redirectTo parameter and verify it is never passed to signInWithOAuth. Test an invalid or replayed callback code and expect failure.

**Security limitations:** A correct redirect URL does not replace checking state, verifier association and identity/session freshness. Never place authorization codes or tokens in logs.

A successful source integrity check cannot stand in for a real Auth token refresh, signed JWT verification, email delivery, OAuth callback or MFA challenge.

</LessonStep>

## Trust boundaries and operational choices

OAuth authenticates users through a configured provider; PKCE binds the authorization code flow to the initiating client. Callback destinations must be strictly allowlisted.

Derive the callback from an approved application origin and handle the returned code through a trusted auth callback that verifies flow state and exchanges the code for a session.

A correct redirect URL does not replace checking state, verifier association and identity/session freshness. Never place authorization codes or tokens in logs.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.
