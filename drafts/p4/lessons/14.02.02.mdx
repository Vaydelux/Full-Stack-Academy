## Authentication problem

**Next.js SSR cookies.** Supabase SSR uses cookies to make an authenticated session available to Next.js server code. Token refresh must propagate Set-Cookie through a route or Proxy that can write cookies.

**Broken starting assumption:** The starter treats attacker-controlled cookie JSON as an authority for administrator access, without verifying a token or its issuer.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/nextjs-ssr-cookie-boundary/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
import { cookies } from "next/headers";
import { createServerClient } from "@supabase/ssr";

export async function serverSupabase() {
  const cookieStore = await cookies();
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL!;
  const key = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!;
  return createServerClient(url, key, {
    cookies: {
      getAll() { return cookieStore.getAll(); },
      setAll(toSet) {
        // Cookie writes belong in a Server Action, Route Handler or refresh Proxy.
        try { toSet.forEach(({ name, value, options }) =>
          cookieStore.set(name, value, options)); }
        catch { /* Read-only Server Component: configured Proxy refreshes */ }
      },
    },
  });
}
```

**Repair reasoning:** Use createServerClient with correct getAll/setAll cookie adapters and ensure the framework's refresh Proxy is configured. Guard sensitive server data with getClaims or getUser and resource-specific authorization.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

## Trust boundaries and operational choices

Supabase SSR uses cookies to make an authenticated session available to Next.js server code. Token refresh must propagate Set-Cookie through a route or Proxy that can write cookies.

Use createServerClient with correct getAll/setAll cookie adapters and ensure the framework's refresh Proxy is configured. Guard sensitive server data with getClaims or getUser and resource-specific authorization.

Do not rely on getSession's user object as independent server authorization. Cookie adapters and token refresh behavior vary with framework version and must be verified against the installed @supabase/ssr.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

SSR needs request-scoped cookie access. Server Components cannot persist cookie updates, so the shown catch relies on a correctly configured Next.js Proxy or other writable response boundary. The helper alone does not implement refresh. Never share a user-specific server client across requests or cache a personalized response as public content. Validate identity at protected server actions and routes.

### Diagnose the concrete failure

Test a signed-in request, expired access token with valid refresh and forged or invalid session data. Verify refreshed cookies reach the request and browser via the actual response path. Run two independent user sessions and confirm their cookies and cached results never mix. Use redacted headers only.

### Independent exercise and evidence

Design the complete request path from Proxy to server component and mutation endpoint, including a logout transition and no-store handling for private responses. Record HTTP outcomes, refresh behavior and two-user isolation; inspect the pinned SSR library contract.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated synthetic identities and the pinned SDK. Preserve the existing starter and solution; source inspection does not establish actual Auth or session security.
