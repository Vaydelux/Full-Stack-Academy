## Integration defect

**Project connection methods.** Prisma connects to Supabase PostgreSQL through a SQL connection string. Supabase browser clients normally use the HTTPS Data API with a user JWT; the connection/authentication and authorization models are different.

**What fails in an actual application:** An SQL database URL placed under NEXT_PUBLIC exposes database credentials in the web bundle and allows direct connections outside the intended server perimeter.

A full-stack application can use both a Supabase client and a direct Prisma ORM 7 PostgreSQL adapter. These access paths do not automatically share the same user authorization context. The browser may have a valid JWT while a server's database role can read far more than that JWT would authorize.

```ts
// Server-only Prisma composition root for an approved test/production role.
import "server-only";
import { PrismaPg } from "@prisma/adapter-pg";
const directOrPooled = process.env.DATABASE_POOL_URL;
if (!directOrPooled) throw new Error("Missing server DB URL");
const adapter = new PrismaPg({ connectionString: directOrPooled, max: 5 });
// Pass adapter to the version-pinned generated PrismaClient.
```

**Repair:** Use a server-only PostgreSQL adapter with a secret URL and a least-privileged database role. Select the connection endpoint based on the actual environment.

This is a teaching excerpt; configure generated types, verified request guards, safe error mapping, and actual database credentials separately.

## API, RLS and migration trade-offs

Prisma connects to Supabase PostgreSQL through a SQL connection string. Supabase browser clients normally use the HTTPS Data API with a user JWT; the connection/authentication and authorization models are different.

Use a server-only PostgreSQL adapter with a secret URL and a least-privileged database role. Select the connection endpoint based on the actual environment.

A successful SQL connection does not inherit per-user Supabase JWT/RLS context. Server request handlers must still validate actor and object permissions.

Explicitly choose how identity is propagated between Next.js, NestJS, Prisma, and Supabase. When a privileged server role bypasses RLS, the NestJS service must check permissions and the database role should still be restricted. Prefer verified membership from trusted server data over user-editable metadata or query parameters.

## Applied persistence walkthrough

A direct PostgreSQL connection and the Supabase Data API are different trust paths. The adapter uses database credentials, not a user's API JWT. server-only helps prevent accidental browser imports in a supported Next.js build, but does not make a privileged database role safe. Connection settings and access rights must match the intended server operation.

### Diagnose the concrete failure

Inspect the local composition root and confirm a missing pool URL fails before construction. Connect only to an approved disposable project or local database, inspect current_user and current_database, and run an authorized read. Build the application and check that no credentials or generated server-only module enter a browser bundle.

### Independent exercise and evidence

Design two access paths for a task app: user-scoped Data API and server-side Prisma with restricted database role. Record which path enforces RLS, which has independent authorization, and the test evidence required for each.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use pinned tooling and a disposable local or explicitly approved test environment. Preserve the starter and solution; source review does not qualify real database roles or authorization.
