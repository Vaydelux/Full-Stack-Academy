## Architecture problem

**PostgreSQL Auth Storage and Realtime.** Supabase bundles PostgreSQL, Auth, Storage and Realtime, but each has a distinct authorization boundary. The browser uses a publishable client; privileged operations must remain on the server and be individually authorized.

**Unsafe starting point:** A single shared client constructed with a secret key can leak privileged access when imported by browser code or a shared component.

Supabase is not a single unrestricted database client. Different credentials and services have different trust boundaries. This source lesson makes the boundary explicit so a working demonstration does not accidentally teach learners to expose server credentials, ignore RLS, or apply migrations against the wrong project.

<LessonStep number={2} title="Use scoped configuration or explicit RLS" file="drafts/p4/labs/supabase-product-boundaries/solution.ts" expected="A clear, reviewable boundary appropriate to the operation.">

```ts
// Browser client: URL + publishable key only.
import { createBrowserClient } from "@supabase/ssr";
export function browserSupabase() {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const key = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;
  if (!url || !key) throw new Error("Public Supabase config missing");
  return createBrowserClient(url, key);
}
// Service-only privileged clients belong in separate server modules.
```

**Repair:** Create a browser client with only the public project URL and publishable key. Keep privileged operations behind authenticated server handlers and resource-specific authorization.

</LessonStep>

<LessonStep number={3} title="Verify in an isolated local Supabase stack" file="drafts/p4/labs/supabase-product-boundaries/acceptance.md" expected="Positive behavior and an independently denied operation are recorded.">

**Positive proof:** Use local Supabase with two test identities. Verify Auth sign-in, RLS-protected PostgreSQL data, private Storage policy, and an authorized Realtime channel separately.

**Required negative proof:** Search browser bundles for secret/service_role values. Authenticate as alpha and attempt beta's data and private storage paths, expecting denial.

**Remaining boundary:** A publishable key is not a permission grant. RLS, Grants and Storage policies must deny unauthorized users. Service roles can bypass RLS.

The acceptance file is a manual/real-stack qualification plan. It is not an automatically successful integration test and does not qualify a production project.

</LessonStep>
