## Secure Storage and Realtime problem

**Lab safe document upload.** A secure document upload combines verified Auth, tenant membership, a server-chosen path, private Storage RLS, constrained signed upload, scanning and consistent metadata state.

**Unsafe starter behavior:** The starter trusts client tenant/path, uploads to public storage and creates unscoped metadata; failure between upload and DB insert creates inconsistent or exposed files.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/safe-document-upload-capstone/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
// Teaching excerpt: actor is verified by server Auth and membership.
async function createUploadIntent(actor: VerifiedActor, documentId: string) {
  if (!actor.canWrite || !actor.tenantId || !actor.userId)
    throw new Error("Forbidden");
  if (!/^[a-f0-9]{8}-[a-f0-9]{4}-[1-8][a-f0-9]{3}-[89ab][a-f0-9]{3}-[a-f0-9]{12}$/i.test(documentId))
    throw new Error("Invalid document ID");
  const objectPath = actor.userId + "/" + documentId.toLowerCase() + ".pdf";
  // Durable PENDING row is tenant-scoped and unique by object path.
  await prisma.document.create({ data: {
    tenantId: actor.tenantId, ownerId: actor.userId,
    objectPath, status: "PENDING",
  }});
  const { data, error } = await serverStorage.storage
    .from("academy_private_docs").createSignedUploadUrl(objectPath);
  if (error || !data) throw new Error("Unable to issue upload");
  return { path: data.path, token: data.token };
}
// After upload: verify real bytes + scan and mark READY or clean up.
```

**Security rationale:** Authenticate, authorize the tenant and document, create a durable PENDING intent at a server-controlled path, issue a private signed upload token, then verify and finalize or compensate after upload.

Teaching excerpts may depend on separately verified Auth guards, bucket policies, or helper types. They must be integrated with the actual Supabase client version, service configuration and database schema before any runtime qualification.

</LessonStep>

## Architecture and lifecycle trade-offs

A secure document upload combines verified Auth, tenant membership, a server-chosen path, private Storage RLS, constrained signed upload, scanning and consistent metadata state.

Authenticate, authorize the tenant and document, create a durable PENDING intent at a server-controlled path, issue a private signed upload token, then verify and finalize or compensate after upload.

Storage and PostgreSQL are not one atomic transaction. Plan idempotency, token expiry, orphan cleanup, retries and safe failure states. Never report a signed upload token as proof the file was scanned.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.

## Applied persistence walkthrough

An upload intent separates permission to start an upload from the decision to publish an object. The example creates a durable PENDING document and issues a token for a server-chosen path. Token issuance can fail after the database row is created; a retry or cleanup path is required. User prefix and a document ID are not by themselves proof of tenant membership. READY must depend on trusted content verification.

### Diagnose the concrete failure

Test authorized intent creation, invalid ID, denied actor and duplicate intent, then inject token issuance failure after the PENDING write. Verify that the row remains non-public and can be safely reconciled. Complete a synthetic upload and validate actual bytes before transitioning to READY. Test cross-tenant download and failed scan separately.

### Independent exercise and evidence

Design a reconciliation worker for expired intents, orphaned objects and duplicate completion events. Define a state transition contract and how tenant ownership is checked for every operation. Record intent identity, final state and cleanup evidence without logging tokens.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated test identities, storage and channels. Preserve the existing starter and solution; source review cannot qualify live upload, webhook or Realtime security.
