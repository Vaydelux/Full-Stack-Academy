## Architecture problem

**Client vs server keys.** Publishable keys identify the Supabase project and are designed for clients. Secret/service-role keys are privileged and must remain in server-only secret storage. The database still enforces row policies for normal clients.

**Unsafe starting point:** The starter exposes a secret key in the browser bundle, allowing attackers to act with privileges that may bypass RLS.

Supabase is not a single unrestricted database client. Different credentials and services have different trust boundaries. This source lesson makes the boundary explicit so a working demonstration does not accidentally teach learners to expose server credentials, ignore RLS, or apply migrations against the wrong project.

```ts
import { createBrowserClient } from "@supabase/ssr";
const projectUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
const publishable = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;
if (!projectUrl || !publishable) throw new Error("Missing browser config");
export const client = createBrowserClient(projectUrl, publishable);
```

**Repair:** Use a publishable key for the browser. Access secret keys only in separate server-only modules, behind explicit authorization and auditing.

</LessonStep>

## Applied persistence walkthrough

The publishable key identifies the application at Supabase's API boundary; it is designed for public clients. A user access token establishes the authenticated session. Secret or legacy service-role credentials belong only on trusted servers and can have elevated access. A public key is safe to distribute only with appropriate grants and row policies; it is not a substitute for them.

### Diagnose the concrete failure

Build the browser sample with dummy public config and inspect the resulting bundle for only the intended public variables. In a disposable project compare anonymous access with an authenticated user and a server-only privileged path. Test that forbidden rows remain inaccessible, not merely that the client starts.

### Independent exercise and evidence

Draw a key inventory showing purpose, allowed environment and rotation response for each credential type. Design a check that prevents privileged variables from entering public builds and record actual bundle evidence separately from RLS tests.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use an isolated local Supabase environment or an explicitly approved disposable project. Preserve the starter and solution; do not treat source review as live platform or security qualification.
