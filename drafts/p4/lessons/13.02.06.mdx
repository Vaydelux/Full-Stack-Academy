## Real-world problem

**Error handling and constraint failures.** Prisma known request errors include codes such as P2002 (unique constraint) and P2025 (missing required record). Map them to stable public errors without serializing internal exception details.

**Defect in the first implementation:** The starter returns an internal database exception directly to the client, potentially disclosing table names, query parameters, constraint identifiers or credentials.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/map-prisma-constraint-errors/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
function mapDatabaseError(error: unknown) {
  if (typeof error === "object" && error !== null && "code" in error) {
    const code = (error as { code?: unknown }).code;
    if (code === "P2002") return { status: 409, error: "Conflict" };
    if (code === "P2025") return { status: 404, error: "Not found" };
  }
  return { status: 500, error: "Request failed" };
}
try { await createTask(); }
catch (error) {
  console.error("Database request failed", { event: "task.create.failed" });
  return mapDatabaseError(error);
}
```

**Repair reasoning:** Handle known constraint cases with controlled status/body, log sanitized telemetry server-side, and return a generic message for unknown faults.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

## Architecture and implementation choices

Prisma known request errors include codes such as P2002 (unique constraint) and P2025 (missing required record). Map them to stable public errors without serializing internal exception details.

Handle known constraint cases with controlled status/body, log sanitized telemetry server-side, and return a generic message for unknown faults.

A unique conflict is not a reason to echo the conflicting record or reveal another tenant's existence. Error semantics must preserve object-level privacy.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.
