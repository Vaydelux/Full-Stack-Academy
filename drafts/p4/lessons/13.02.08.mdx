## Real-world problem

**Lab repository API.** A repository API should expose domain-safe methods, not arbitrary privileged query primitives. It accepts server-authenticated tenant context and returns allowlisted DTOs only.

**Defect in the first implementation:** The starter lets callers enumerate tasks in any project ID, with unrestricted result fields and no tenant/project authorization boundary.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/tenant-scoped-repository-lab/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
export async function listProjectTasks(
  db: PrismaClient, trustedTenantId: string, projectId: number,
) {
  if (!trustedTenantId || !Number.isSafeInteger(projectId))
    throw new Error("Invalid request context");
  const project = await db.project.findFirst({
    where: { id: projectId, tenantId: trustedTenantId },
    select: { id: true },
  });
  if (!project) return [];
  return db.task.findMany({
    where: { projectId, tenantId: trustedTenantId },
    select: { id: true, title: true, status: true },
    orderBy: { id: "asc" }, take: 100,
  });
}
```

**Repair reasoning:** Check the project exists inside the verified tenant, then query a bounded, tenant-scoped task list with public fields and stable ordering.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

</LessonStep>

## Architecture and implementation choices

A repository API should expose domain-safe methods, not arbitrary privileged query primitives. It accepts server-authenticated tenant context and returns allowlisted DTOs only.

Check the project exists inside the verified tenant, then query a bounded, tenant-scoped task list with public fields and stable ordering.

Tenant isolation is the baseline, not all authorization. Add user-to-project membership rules if not every tenant member may read every project.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.

## Applied persistence walkthrough

A typed repository centralizes data access, but its input types do not establish authenticated context. The example checks the project in the tenant, then queries tasks with the same tenant and project ID. Returning an empty array for missing or forbidden projects avoids disclosing existence, but may obscure a legitimate empty project; decide whether the API contract needs a distinct safe result.

### Diagnose the concrete failure

Test a project with tasks, an empty project and another tenant's project. Verify the permitted response is limited to one hundred ordered rows and public fields. Check missing tenant and invalid project IDs. In a real database, simulate a project deletion between the lookup and child query and define the expected behavior.

### Independent exercise and evidence

Design a repository port with a bounded page contract and a clear not-found policy. Specify how the service derives the tenant from membership and how a real database test proves cross-tenant exclusion. Record response shape, exact IDs and denied cases.
