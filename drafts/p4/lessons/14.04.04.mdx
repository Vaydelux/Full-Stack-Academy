## Secure Storage and Realtime problem

**Realtime channel authorization.** Supabase Realtime uses RLS on realtime.messages to authorize private Broadcast and Presence channels. A topic name and a valid JWT are not enough; membership must be checked.

**Unsafe starter behavior:** The starter's read policy allows any signed-in user to receive broadcasts from any other tenant's private channel.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/tenant-realtime-private-channel/solution.sql" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```sql
-- Assumes public.academy_realtime_memberships with tenant_id/user_id.
ALTER TABLE realtime.messages ENABLE ROW LEVEL SECURITY;
CREATE POLICY academy_tenant_broadcast_read ON realtime.messages
FOR SELECT TO authenticated
USING (
  extension = 'broadcast'
  AND EXISTS (
    SELECT 1 FROM public.academy_realtime_memberships m
    WHERE m.user_id = (SELECT auth.uid())
      AND m.tenant_id = split_part((SELECT realtime.topic()), ':', 2)
  )
);
-- A separate scoped INSERT policy is required for sending.
-- Client joins with config: { private: true }.
```

**Security rationale:** Use a membership lookup tied to auth.uid and the channel topic, restrict message extension and join with private:true. Review separate send/receive permissions.

**Allowed outcome:** Alpha can subscribe to its own approved topic, receive a non-sensitive test event, and remain isolated from beta.

**Denied or failure outcome:** Subscribe as alpha to beta's private topic with a valid JWT and expect CHANNEL_ERROR or denial without any beta payload.

**Residual limitations:** Realtime policies are evaluated for channel joining and refreshed under certain events; membership changes may require reconnect/re-authorization. Broadcast payloads should not contain long-lived secrets.

## Architecture and lifecycle trade-offs

Supabase Realtime uses RLS on realtime.messages to authorize private Broadcast and Presence channels. A topic name and a valid JWT are not enough; membership must be checked.

Use a membership lookup tied to auth.uid and the channel topic, restrict message extension and join with private:true. Review separate send/receive permissions.

Realtime policies are evaluated for channel joining and refreshed under certain events; membership changes may require reconnect/re-authorization. Broadcast payloads should not contain long-lived secrets.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.
