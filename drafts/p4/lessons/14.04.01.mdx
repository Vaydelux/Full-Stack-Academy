## Secure Storage and Realtime problem

**Buckets public vs private.** Supabase Storage separates bucket visibility from authenticated object operations. A public bucket grants link-based downloads; a private bucket requires authorized reads or short-lived signed URLs.

**Unsafe starter behavior:** The starter marks sensitive business documents as public, making them readable without an authorized user session.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/bucket-visibility-boundary/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
// Approved local admin setup for a PRIVATE bucket.
const { data, error } = await admin.storage.createBucket(
  "academy_private_docs",
  {
    public: false,
    allowedMimeTypes: ["application/pdf", "image/png"],
    fileSizeLimit: "5MB",
  },
);
if (error) throw new Error("Private bucket setup failed");
// Separately define storage.objects RLS policies before client access.
```

**Security rationale:** Create a private bucket with appropriate type/size limits, add path-scoped Storage RLS policies, and authorize signed download requests on the server.

**Allowed outcome:** Authenticated alpha may download the same private object using permitted access; bucket config remains private.

**Denied or failure outcome:** Upload an alpha document; request its regular public URL with no token and attempt to read it as beta. Both must fail.

**Residual limitations:** A private flag alone does not prevent overbroad authenticated Storage policies. Public URLs, CDN/browser cache and signed URLs require their own revocation and expiry review.

## Architecture and lifecycle trade-offs

Supabase Storage separates bucket visibility from authenticated object operations. A public bucket grants link-based downloads; a private bucket requires authorized reads or short-lived signed URLs.

Create a private bucket with appropriate type/size limits, add path-scoped Storage RLS policies, and authorize signed download requests on the server.

A private flag alone does not prevent overbroad authenticated Storage policies. Public URLs, CDN/browser cache and signed URLs require their own revocation and expiry review.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.
