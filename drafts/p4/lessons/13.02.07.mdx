## Real-world problem

**Avoiding N plus one.** Batching or an appropriately scoped Prisma relation load reduces repetitive database queries. Group the results into their parent records in memory only after filtering at the database boundary.

**Defect in the first implementation:** The starter issues one task query per project and does not filter child tasks by tenant, causing N+1 round trips and possible cross-tenant results.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/batch-prisma-relations/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
const projects = await db.project.findMany({
  where: { tenantId }, select: { id: true, name: true },
  take: 50, orderBy: { id: "asc" },
});
const ids = projects.map(p => p.id);
const tasks = await db.task.findMany({
  where: { tenantId, projectId: { in: ids } },
  select: { id: true, title: true, projectId: true },
});
const byProject = new Map(ids.map(id => [id, [] as typeof tasks]));
for (const task of tasks) byProject.get(task.projectId)?.push(task);
return projects.map(p => ({ ...p, tasks: byProject.get(p.id) ?? [] }));
```

**Repair reasoning:** Fetch a bounded list of tenant projects, query all corresponding tasks in one tenant-scoped IN query and group them by project ID.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

</LessonStep>

**Positive case:** Instrument actual Prisma query events or DB statistics on a disposable dataset with 1, 10 and 50 projects; inspect number of database round trips, result bytes and latency.

**Negative case:** Test projects with zero tasks and cross-tenant tasks sharing project IDs. Assert no tenant leak and query counts remain approximately constant as projects increase.

**Production boundary:** One large batch is not always optimal. Very large IN lists and relations may require chunking, filtering and a measured plan; do not claim a speedup without profiling.

## Architecture and implementation choices

Batching or an appropriately scoped Prisma relation load reduces repetitive database queries. Group the results into their parent records in memory only after filtering at the database boundary.

Fetch a bounded list of tenant projects, query all corresponding tasks in one tenant-scoped IN query and group them by project ID.

One large batch is not always optimal. Very large IN lists and relations may require chunking, filtering and a measured plan; do not claim a speedup without profiling.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.
