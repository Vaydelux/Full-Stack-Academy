## Integration defect

**Supabase schemas and RLS boundaries.** An exposed schema plus GRANT exposes an API operation; RLS filters rows for the PostgREST user role. Prisma's direct SQL role is a separate privilege path.

**What fails in an actual application:** A GRANT on an exposed public table without owner-scoped RLS can expose every tenant's records to a legitimate signed-in client.

A full-stack application can use both a Supabase client and a direct Prisma ORM 7 PostgreSQL adapter. These access paths do not automatically share the same user authorization context. The browser may have a valid JWT while a server's database role can read far more than that JWT would authorize.

Decide which component authenticates the caller, which verifies tenant or resource membership, which PostgreSQL role executes the query, and which schema is exposed via the Data API. Write a failure assertion before changing the code. The examples use synthetic actors and isolated databases only.

## Guided implementation

<LessonStep number={1} title="Reproduce the unsafe integration" file="drafts/p4/labs/exposed-schema-rls-separation/starter.sql" expected="Explain the exact scope, role, or migration boundary that fails.">

```sql
-- Exposed public table with no RLS protection.
CREATE TABLE public.academy_project_notes (
 id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 tenant_id text NOT NULL,
 body text NOT NULL
);
GRANT SELECT ON public.academy_project_notes TO authenticated;
```

**Defect:** A GRANT on an exposed public table without owner-scoped RLS can expose every tenant's records to a legitimate signed-in client.

Observe the failure in a disposable test environment. A SQL statement executing successfully does not prove it was authorized.

</LessonStep>

<LessonStep number={2} title="Enforce the correct boundary" file="drafts/p4/labs/exposed-schema-rls-separation/solution.sql" expected="Tenant or environment decisions come from verified server context.">

```sql
CREATE TABLE public.academy_project_notes (
 id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 tenant_id text NOT NULL,
 owner_id uuid NOT NULL,
 body text NOT NULL
);
ALTER TABLE public.academy_project_notes ENABLE ROW LEVEL SECURITY;
CREATE POLICY notes_own ON public.academy_project_notes
 FOR SELECT TO authenticated
 USING (owner_id = (SELECT auth.uid()));
GRANT SELECT ON public.academy_project_notes TO authenticated;
```

**Repair:** Enable RLS and an owner-scoped SELECT policy before granting the client role. Audit all other operations and avoid accidental view/function bypasses.

This is a teaching excerpt; configure generated types, verified request guards, safe error mapping, and actual database credentials separately.

</LessonStep>

## API, RLS and migration trade-offs

An exposed schema plus GRANT exposes an API operation; RLS filters rows for the PostgREST user role. Prisma's direct SQL role is a separate privilege path.

Enable RLS and an owner-scoped SELECT policy before granting the client role. Audit all other operations and avoid accidental view/function bypasses.

SELECT policies do not secure INSERT/UPDATE/DELETE. Verify WITH CHECK and authenticated identity. SECURITY DEFINER and service roles may bypass normal RLS.

Explicitly choose how identity is propagated between Next.js, NestJS, Prisma, and Supabase. When a privileged server role bypasses RLS, the NestJS service must check permissions and the database role should still be restricted. Prefer verified membership from trusted server data over user-editable metadata or query parameters.

## Applied persistence walkthrough

Data API exposure, object grants and row policies are distinct controls. The shown policy permits authenticated owners to select their notes; the grant allows that operation at the object level. It does not authorize insert, update or delete, nor does owner_id alone prove tenant membership. Existing project default grants may differ, so inspect them explicitly. A direct privileged role may bypass RLS.

### Diagnose the concrete failure

In an isolated Supabase environment, create two fake users with notes and invoke the Data API as each real authenticated user. Verify exact permitted IDs and absence of other users' notes. Attempt anonymous access and ungranted writes, inspecting effective grants instead of assuming defaults. Test the privileged server path separately.

### Independent exercise and evidence

Design a membership-based read policy for shared tenant notes, using verified membership rather than editable user metadata. Record the role, permitted rows and forbidden rows, and include a security-invoker view review if views are exposed.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use pinned tooling and a disposable local or explicitly approved test environment. Preserve the starter and solution; source review does not qualify real database roles or authorization.

## Extend the ERP laboratory

Create synthetic organizations alpha and beta with overlapping IDs, a membership table and private documents. Run requests through both Supabase's Data API and a Prisma-backed NestJS endpoint. Verify permitted rows, denied rows, mutation effects and clean database recreation from migrations. Record whether your test uses a JWT-backed user or a privileged SQL role; those results are not interchangeable.
