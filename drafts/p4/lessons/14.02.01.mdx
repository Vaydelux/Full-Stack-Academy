## Authentication problem

**Sign up sign in and verification.** Email/password sign-up and sign-in may require a separate email verification step. UI state must distinguish a pending verification from an authenticated session.

**Broken starting assumption:** A created user object does not necessarily mean the email is verified or an active session has been established.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/signup-verification-state/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
const { data, error } = await supabase.auth.signUp({ email, password });
if (error) throw new Error("Sign-up failed");
if (!data.session) {
  return { state: "verify-email" as const };
}
return { state: "signed-in" as const, userId: data.session.user.id };
```

**Repair reasoning:** Inspect error and returned session explicitly, show a neutral verification state when there is no session, and protect data access using actual verified server authentication.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

## Trust boundaries and operational choices

Email/password sign-up and sign-in may require a separate email verification step. UI state must distinguish a pending verification from an authenticated session.

Inspect error and returned session explicitly, show a neutral verification state when there is no session, and protect data access using actual verified server authentication.

Never treat a non-null user in a signUp response as permission to read private data. Rate-limit login endpoints and avoid detailed account-enumeration errors.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

Sign-up and an authenticated session are distinct outcomes. When email confirmation is enabled, a successful sign-up may return no session, and the interface should present the verification step rather than granting access. Provider settings can alter the flow. A returned user ID is identity information, not permission to a tenant's records.

### Diagnose the concrete failure

In a disposable Auth environment register a synthetic email and inspect the returned session state without logging tokens. Confirm unverified users cannot use protected routes, complete verification using the local test mailbox, then sign in. Test invalid credentials and repeated registration without revealing account existence.

### Independent exercise and evidence

Sketch a state machine for signed-out, verification pending, signed-in and error states. Add rate limiting and neutral public messaging to the design. Record actual transition results, not passwords or confirmation links.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated synthetic identities and the pinned SDK. Preserve the existing starter and solution; source inspection does not establish actual Auth or session security.
