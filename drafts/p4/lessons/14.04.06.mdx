## Secure Storage and Realtime problem

**Presence and broadcast.** Presence indicates connected participants; Broadcast carries ephemeral messages. Both need private-channel authorization, bounded payloads and clear disconnect lifecycle.

**Unsafe starter behavior:** The starter uses a public room with a predictable tenant topic. Unauthorized clients may join, observe presence or receive messages.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/presence-broadcast-auth/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
// Server-derived tenant and Auth JWT; authorization policy required.
const channel = supabase.channel("tenant:" + verifiedTenantId, {
  config: { private: true, presence: { key: verifiedUserId } },
});
channel.on("presence", { event: "sync" }, () => {
  renderMembers(channel.presenceState());
});
channel.on("broadcast", { event: "task.changed" }, () => {
  invalidateTaskQueryCache();
});
channel.subscribe();
// Remove channel and clear presence on logout/unmount.
```

**Security rationale:** Use private:true and a trusted membership-based realtime.messages SELECT/INSERT policy. Use verified identity for presence keys and avoid trusting broadcast payloads as authoritative database state.

## Architecture and lifecycle trade-offs

Presence indicates connected participants; Broadcast carries ephemeral messages. Both need private-channel authorization, bounded payloads and clear disconnect lifecycle.

Use private:true and a trusted membership-based realtime.messages SELECT/INSERT policy. Use verified identity for presence keys and avoid trusting broadcast payloads as authoritative database state.

Presence is ephemeral and not a durable user-status or access-control database. Private Realtime policy joins require real authenticated tests and may have connection-rate costs.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.

## Applied persistence walkthrough

Presence represents connected client state and Broadcast sends ephemeral application messages. Neither establishes a durable record nor proves a user's identity by itself. The sample uses a private channel and a proposed verified-user presence key, but client-controlled presence payloads must not grant authority. The shown handler observes presence; it does not register a track call.

### Diagnose the concrete failure

Connect two authorized clients and one nonmember. Verify private channel access, presence synchronization after explicit tracking where appropriate, and broadcast behavior under the configured policies. Disconnect and reconnect a client and verify stale display state is reconciled. Do not interpret a client-supplied presence label as verified permission.

### Independent exercise and evidence

Design a collaboration UI that uses presence only as an availability hint, while fetching authoritative membership from the server. Record channel access, event delivery, cleanup and reconnection behavior. Keep sensitive data out of ephemeral messages.
