## Architectural challenge

**Prisma migration histories.** Schema history is a first-class deployable artifact. Development migration generation and production application are different operations and need separate credentials and review.

**Reproducible failure:** A developer changes the live schema with db push while previously applied migration files are untracked. Recreating a clean environment no longer reproduces the same database.

When a service evolves from a single-developer prototype into an API used by several organizations, an apparently valid query may introduce security gaps, schema drift, or operational load. <LessonStep number={2} title="Apply the narrow corrected boundary" file="drafts/p4/labs/reviewed-migration-histories/solution.sh" expected="The data and deployment invariant is explicitly enforced or observable.">

```bash
# Generate in a dedicated development database.
npx prisma migrate dev --name add_task_state
# Inspect and commit the generated SQL under prisma/migrations.
npx prisma migrate status
npx prisma generate
# In a separately approved test/release database:
npx prisma migrate deploy
```

**Why it is safer:** Use migrate dev only on a disposable dev database, review checked-in SQL, inspect migration status, regenerate the client, and use migrate deploy only after release approval.

Do not assume a successful CLI or TypeScript compile proves that the caller was authorized. Generated types protect shapes, not per-request permissions. Similarly, a DB transaction cannot roll back independent external side effects.

</LessonStep>

## Design trade-offs and real-world constraints

Schema history is a first-class deployable artifact. Development migration generation and production application are different operations and need separate credentials and review.

Use migrate dev only on a disposable dev database, review checked-in SQL, inspect migration status, regenerate the client, and use migrate deploy only after release approval.

Prisma migrate deploy does not automatically certify a zero-downtime change or regenerate the client. Do not run migrate reset, db push, or migrate dev on production credentials.

In a multi-tenant API, input validation, role-aware database credentials, optimistic concurrency, migration review and response-shape controls must be considered together. Favor bounded queries and explicit domain operations over returning raw privileged ORM interfaces to HTTP handlers. Record the query plan or migration state instead of guessing.
