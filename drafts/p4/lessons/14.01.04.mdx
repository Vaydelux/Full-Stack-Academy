## Architecture problem

**SQL editor vs migrations.** A SQL editor is useful for exploration; migration files establish a reviewable, reproducible schema history. Only one migration owner should control a table's DDL when Prisma and Supabase coexist.

**Unsafe starting point:** The starter suggests pushing database changes without a checked-in, reviewed migration or verifying the project target.

Supabase is not a single unrestricted database client. Different credentials and services have different trust boundaries. This source lesson makes the boundary explicit so a working demonstration does not accidentally teach learners to expose server credentials, ignore RLS, or apply migrations against the wrong project.

## Applied persistence walkthrough

Reviewed migrations preserve reproducible database changes; the SQL editor is useful for exploration but out-of-band DDL can create drift. Local reset replays migration history and seed data and destroys existing local database contents. The CLI version determines available commands. Never execute reset against an unrelated linked project or assume that local data is disposable.

### Diagnose the concrete failure

Check CLI help and verify the dedicated local project before generating a migration with the installed tool. Review the generated SQL, rebuild the disposable local database, and compare schema and policies. Test replay from a clean environment, not just from the one where the SQL was manually tried.

### Independent exercise and evidence

Plan a release for adding a table and its access policies, including explicit grants and RLS. Record migration order, clean replay result and a forward-repair strategy. Keep platform-managed schemas outside unrelated app DDL changes.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use an isolated local Supabase environment or an explicitly approved disposable project. Preserve the starter and solution; do not treat source review as live platform or security qualification.
