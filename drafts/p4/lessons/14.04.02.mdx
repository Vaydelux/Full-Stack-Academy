## Secure Storage and Realtime problem

**Signed upload URLs.** A signed upload URL is a temporary bearer capability. Minting it must happen only after verifying that a caller may create the particular object at a server-chosen path.

**Unsafe starter behavior:** The starter signs arbitrary client-selected paths. An attacker can request a token for another user's folder and upload into it even when ordinary client RLS would deny that operation.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/safe-signed-upload-authorization/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
// Server-side endpoint: actor is verified from Auth + membership DB.
async function issueUpload(
  actor: { userId: string; tenantId: string; canUpload: boolean },
  documentId: string,
) {
  if (!actor.userId || !actor.tenantId || !actor.canUpload)
    throw new Error("Forbidden");
  if (!/^[a-f0-9-]{36}$/i.test(documentId))
    throw new Error("Invalid ID");
  // The server chooses the full key; never accept a client-supplied path.
  const key = actor.userId + "/" + documentId + ".pdf";
  const { data, error } = await service.storage
    .from("academy_private_docs").createSignedUploadUrl(key);
  if (error || !data) throw new Error("Upload authorization failed");
  return { path: data.path, token: data.token };
}
```

**Security rationale:** Verify user membership and upload permission, generate a non-caller-controlled path, and issue only a narrowly scoped one-use upload capability. Upload with the SDK's uploadToSignedUrl using that token.

Teaching excerpts may depend on separately verified Auth guards, bucket policies, or helper types. They must be integrated with the actual Supabase client version, service configuration and database schema before any runtime qualification.

</LessonStep>

<LessonStep number={3} title="Test allowed and forbidden flows end to end" file="drafts/p4/labs/safe-signed-upload-authorization/acceptance.md" expected="Record authorized success and cross-tenant denial with actual service responses.">

**Allowed outcome:** Alpha receives a token for alpha's deterministic path and uses uploadToSignedUrl on a disposable private bucket.

**Denied or failure outcome:** As alpha, request a token for a beta folder, reused document key or unauthorized MIME type; no cross-owner token should be issued.

**Residual limitations:** Upload tokens are bearer secrets valid for a limited window; they must not be logged, embedded in analytics, or mistaken for a permanent ACL. Backend must still validate content independently.

## Architecture and lifecycle trade-offs

A signed upload URL is a temporary bearer capability. Minting it must happen only after verifying that a caller may create the particular object at a server-chosen path.

Verify user membership and upload permission, generate a non-caller-controlled path, and issue only a narrowly scoped one-use upload capability. Upload with the SDK's uploadToSignedUrl using that token.

Upload tokens are bearer secrets valid for a limited window; they must not be logged, embedded in analytics, or mistaken for a permanent ACL. Backend must still validate content independently.

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.
