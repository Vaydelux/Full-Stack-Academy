## Authentication problem

**Secure sign-out and session refresh.** Supabase Auth sessions use access and refresh tokens with rotation and sign-out scopes. A logout action should invalidate the intended sessions and clear cached private UI state.

**Broken starting assumption:** The starter only toggles browser UI state. It does not ask Supabase Auth to revoke refresh sessions or invalidate server-side access decisions.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

## Trust boundaries and operational choices

Supabase Auth sessions use access and refresh tokens with rotation and sign-out scopes. A logout action should invalidate the intended sessions and clear cached private UI state.

Call Supabase Auth signOut with deliberate scope, handle errors and clear private application caches; protect sensitive routes with fresh verification rather than a local UI flag.

Global sign-out revokes refresh tokens but may not make every already-issued JWT immediately fail RLS checks. Use session freshness validation for high-risk actions.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

Sign-out invalidates the selected session scope's refresh capability; an already issued access token may remain valid until its expiry. The example chooses global sign-out and clears app cache after success. A production app also needs local private-state handling on failure and server-side freshness checks where immediate revocation matters. Do not equate a redirect with session invalidation.

### Diagnose the concrete failure

Sign in on two independent test clients, choose global sign-out and observe refresh failure on both. Separately test the previously issued unexpired access token and document its bounded lifetime. Verify private cache and UI state are cleared and that protected routes check identity and resource permission again.

### Independent exercise and evidence

Design a sign-out failure state that hides private UI data while clearly indicating that server revocation is unconfirmed. Record local cache behavior, refresh outcomes and session scope without storing token values.
