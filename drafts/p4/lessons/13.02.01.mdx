## Real-world problem

**findMany findUnique and filters.** findUnique targets a declared unique key; findFirst and findMany support richer predicates. A tenant-scoped query must receive a server-verified tenant identity and return only authorized fields.

**Defect in the first implementation:** An ID may be globally unique but it does not prove the caller is permitted to read its record. The starter returns a task by ID alone.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/scoped-prisma-reads/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
async function getTask(db: PrismaClient, tenantId: string, taskId: number) {
  if (!tenantId) throw new Error("Missing verified tenant");
  return db.task.findFirst({
    where: { id: taskId, tenantId },
    select: { id: true, title: true, status: true },
  });
}
```

**Repair reasoning:** Require tenant context and filter by both taskId and tenantId. When the schema declares a compound unique key, a compound findUnique is another valid design; always verify permissions explicitly.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

</LessonStep>

## Architecture and implementation choices

findUnique targets a declared unique key; findFirst and findMany support richer predicates. A tenant-scoped query must receive a server-verified tenant identity and return only authorized fields.

Require tenant context and filter by both taskId and tenantId. When the schema declares a compound unique key, a compound findUnique is another valid design; always verify permissions explicitly.

The Prisma Client type system does not enforce BOLA prevention. Treat a client-provided tenantId or JWT user_metadata as untrusted unless the server verified it.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.

## Applied persistence walkthrough

findUnique identifies a record using a unique key; findFirst searches for a record matching supplied predicates; findMany returns a collection. The example deliberately uses both ID and tenantId in findFirst. A unique ID alone says nothing about whether a caller is permitted to see the record. The trusted tenant must be resolved before repository execution.

### Diagnose the concrete failure

Seed a matching ID in the authorized tenant and a distinct ID in another tenant. Compare permitted lookup, nonexistent lookup and cross-tenant lookup: the last two should return null under this contract. Check the selected fields and verify missing context fails before querying.

### Independent exercise and evidence

Design a tenant-scoped list with an optional validated status filter. Specify whether an omitted filter means all permitted statuses, and how an invalid status is rejected. Record returned IDs, projection and the denied case.
