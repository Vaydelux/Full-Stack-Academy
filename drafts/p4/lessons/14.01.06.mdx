## Architecture problem

**Network and pooling.** Direct and pooled PostgreSQL URLs serve different connection lifecycles. Migration tooling may need session semantics, while short-lived server instances often benefit from a compatible pooler mode.

**Unsafe starting point:** The starter assumes transaction-pooling semantics are safe for all migration and session-affine operations.

Supabase is not a single unrestricted database client. Different credentials and services have different trust boundaries. This source lesson makes the boundary explicit so a working demonstration does not accidentally teach learners to expose server credentials, ignore RLS, or apply migrations against the wrong project.

<LessonStep number={2} title="Use scoped configuration or explicit RLS" file="drafts/p4/labs/direct-vs-pooled-supabase/solution.ts" expected="A clear, reviewable boundary appropriate to the operation.">

```ts
function required(name: "DATABASE_DIRECT_URL" | "DATABASE_POOL_URL") {
  const value = process.env[name];
  if (!value) throw new Error(name + " missing");
  return value;
}
// Server-only configuration; never use NEXT_PUBLIC_ for these URLs.
export const databaseConnections = {
  migration: required("DATABASE_DIRECT_URL"),
  runtime: required("DATABASE_POOL_URL"),
};
```

**Repair:** Separate migration/direct and runtime/pooled credentials, inspect pooler mode and adapter compatibility, and configure least-privilege roles.

</LessonStep>
