## Architectural challenge

**Bug Hunt migration drift.** Migration drift is a disagreement between the physical database and the checked-in migration history. Regenerating a client doesn't reconcile schema history.

**Reproducible failure:** A hotfix changes the database directly, but the migration history remains unchanged. The next release succeeds locally yet fails or loses the hotfix in a clean environment.

When a service evolves from a single-developer prototype into an API used by several organizations, an apparently valid query may introduce security gaps, schema drift, or operational load. Before looking at the corrected code, describe the invariant and the actor or environment whose behavior violates it.

<LessonStep number={2} title="Apply the narrow corrected boundary" file="drafts/p4/labs/detect-and-resolve-schema-drift/solution.sh" expected="The data and deployment invariant is explicitly enforced or observable.">

```bash
# Never mutate prod while investigating.
npx prisma migrate status
# On disposable local dev: inspect drift and generate a reviewed repair.
npx prisma migrate dev --create-only --name reconcile_schema
# Review SQL and match the intended checked-in schema.
npx prisma generate
# Test the reviewed migration against a fresh disposable database.
```

**Why it is safer:** Inspect migration status, compare physical schema with expected history in disposable environments, prepare a reviewed forward repair and avoid blind reset of live data.

Do not assume a successful CLI or TypeScript compile proves that the caller was authorized. Generated types protect shapes, not per-request permissions. Similarly, a DB transaction cannot roll back independent external side effects.

</LessonStep>

**Expected positive case:** Verify a fresh replay produces the intended schema and the migration file is checked in with known checksum and release notes.

**Required negative case:** Manually alter a disposable test table, then compare it to a database recreated only from migration files. Confirm the mismatch is detected and the repair is reviewed.

**What remains unverified:** Never use migrate reset on production. A schema diff can suggest destructive SQL; always review data impact and migration ownership before applying.

## Design trade-offs and real-world constraints

Migration drift is a disagreement between the physical database and the checked-in migration history. Regenerating a client doesn't reconcile schema history.

Inspect migration status, compare physical schema with expected history in disposable environments, prepare a reviewed forward repair and avoid blind reset of live data.

Never use migrate reset on production. A schema diff can suggest destructive SQL; always review data impact and migration ownership before applying.

In a multi-tenant API, input validation, role-aware database credentials, optimistic concurrency, migration review and response-shape controls must be considered together. Favor bounded queries and explicit domain operations over returning raw privileged ORM interfaces to HTTP handlers. Record the query plan or migration state instead of guessing.
