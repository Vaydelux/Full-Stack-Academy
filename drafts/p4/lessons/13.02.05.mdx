## Real-world problem

**Pagination and ordering.** Cursor pagination seeks after a stable unique key. The page size is bounded and the cursor must belong to the same authorized tenant, not an arbitrary external ID.

**Defect in the first implementation:** Deep offset pages grow expensive and can shift when new rows arrive. createdAt alone is not unique, so ties may reorder results.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

```ts
const limit = Math.min(Math.max(Number(pageSize) || 20, 1), 50);
if (afterId != null) {
  const cursorOwner = await db.task.findFirst({
    where: { id: afterId, tenantId },
    select: { id: true },
  });
  if (!cursorOwner) throw new Error("Invalid cursor");
}
return db.task.findMany({
  where: { tenantId },
  orderBy: { id: "asc" },
  cursor: afterId == null ? undefined : { id: afterId },
  skip: afterId == null ? 0 : 1,
  take: limit,
  select: { id: true, title: true },
});
```

**Repair reasoning:** Validate cursor ownership in trusted server context, order by a unique key, skip the cursor row, cap page size and project only public fields.

## Architecture and implementation choices

Cursor pagination seeks after a stable unique key. The page size is bounded and the cursor must belong to the same authorized tenant, not an arbitrary external ID.

Validate cursor ownership in trusted server context, order by a unique key, skip the cursor row, cap page size and project only public fields.

Keyset pagination is not a snapshot: deletions, mutable sort keys and authorization changes can still change what later pages return. Define cursor semantics.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.
