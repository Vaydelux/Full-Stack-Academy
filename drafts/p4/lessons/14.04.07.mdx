## Secure Storage and Realtime problem

**Webhook-triggered processing.** Database webhooks may retry delivery. A consumer must authenticate the webhook origin using an explicitly configured signing mechanism and deduplicate effects by a stable event ID.

**Unsafe starter behavior:** The starter treats arbitrary JSON POST bodies as trusted instructions and reprocesses the same document on every retry.

Storage objects and Realtime messages are not ordinary React local state. They cross network and authorization boundaries; a caller can inspect URLs, retry requests, join predictable channel topics or forge payloads. The lesson teaches a concrete positive outcome and an explicit forbidden outcome.

<LessonStep number={2} title="Implement authorized, bounded operations" file="drafts/p4/labs/authenticated-webhook-processing/solution.ts" expected="Constrain the actor, object and operation with explicit server/Storage or Realtime policy.">

```ts
// The delivery provider must be configured for a signed secret header.
// Verify HMAC over RAW bytes; adapt header/signature format to provider.
function verify(body: Buffer, suppliedHex: string, secret: string) {
  const expected = createHmac("sha256", secret).update(body).digest();
  const got = Buffer.from(suppliedHex, "hex");
  return got.length === expected.length && timingSafeEqual(got, expected);
}
async function acceptWebhook(rawBody: Buffer, signature: string) {
  if (!verify(rawBody, signature, requiredSecret))
    throw new Error("Unauthorized webhook");
  // Parse ONLY the verified bytes; never accept a separate caller event.
  const parsed: unknown = JSON.parse(rawBody.toString("utf8"));
  if (!parsed || typeof parsed !== "object" || Array.isArray(parsed))
    throw new Error("Invalid event");
  const event = parsed as { id?: unknown; tenantId?: unknown };
  if (typeof event.id !== "string" || !event.id ||
      typeof event.tenantId !== "string" || !event.tenantId)
    throw new Error("Invalid event");
  await processOnceWithDatabaseUniqueEventId(event);
}
```

**Security rationale:** Verify a provider-configured HMAC over the raw request body in constant time, validate event shape, and process idempotently with a unique delivery ID in a database transaction.

Teaching excerpts may depend on separately verified Auth guards, bucket policies, or helper types. They must be integrated with the actual Supabase client version, service configuration and database schema before any runtime qualification.

</LessonStep>

Private buckets need specific Storage policies, server-controlled paths and explicit expiration/cleanup rules. Realtime private channels require policies on realtime.messages for permitted operations; a client-specified filter alone is not authorization. Persistent business state remains in PostgreSQL, not in Presence or Broadcast payloads.
