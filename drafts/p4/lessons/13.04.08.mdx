## Integration defect

**Lab cross-tenant security check.** A successful Supabase Auth login and a Prisma-backed server connection are different trust boundaries. A privileged database role can bypass end-user policies unless the server explicitly scopes queries.

**What fails in an actual application:** The starter uses findUnique by record ID without any verified actor membership and returns another organization's document via the service route.

A full-stack application can use both a Supabase client and a direct Prisma ORM 7 PostgreSQL adapter. These access paths do not automatically share the same user authorization context. The browser may have a valid JWT while a server's database role can read far more than that JWT would authorize.

<LessonStep number={2} title="Enforce the correct boundary" file="drafts/p4/labs/cross-tenant-prisma-bypass-capstone/solution.ts" expected="Tenant or environment decisions come from verified server context.">

```ts
async function getDocument(
  db: PrismaClient, actor: VerifiedActor, id: number
) {
  if (!actor.userId || !actor.tenantId) throw new Error("Unauthenticated");
  const allowed = await db.membership.findFirst({
    where: { tenantId: actor.tenantId, userId: actor.userId },
    select: { userId: true },
  });
  if (!allowed) throw new Error("Forbidden");
  return db.document.findFirst({
    where: { id, tenantId: actor.tenantId },
    select: { id: true, title: true },
  });
}
```

**Repair:** Require verified actor identity, check membership from trusted server data and filter the document by tenant before selecting a safe public response.

This is a teaching excerpt; configure generated types, verified request guards, safe error mapping, and actual database credentials separately.

</LessonStep>

## API, RLS and migration trade-offs

A successful Supabase Auth login and a Prisma-backed server connection are different trust boundaries. A privileged database role can bypass end-user policies unless the server explicitly scopes queries.

Require verified actor identity, check membership from trusted server data and filter the document by tenant before selecting a safe public response.

The example implements tenant-level access only. Add per-document ACLs when tenancy alone is too broad and test revocation/session freshness. Never prove RLS by using service_role credentials.

Explicitly choose how identity is propagated between Next.js, NestJS, Prisma, and Supabase. When a privileged server role bypasses RLS, the NestJS service must check permissions and the database role should still be restricted. Prefer verified membership from trusted server data over user-editable metadata or query parameters.

## Applied persistence walkthrough

The repository checks membership then fetches a tenant-scoped document with public projection. A verified actor is a prerequisite, not a public request object. The two queries can race with membership revocation, so sensitive operations may require an atomic policy or transaction-level authorization design. The snippet is not a complete authentication or revocation guarantee.

### Diagnose the concrete failure

Use two actual test tenants and a known document in each. Verify membership absence produces a denial, a permitted document returns only public fields, and a cross-tenant document returns null. Add a membership-revocation test between lookup and read in a disposable environment, and document the remaining consistency requirement.

### Independent exercise and evidence

Design an authorization boundary that couples the membership predicate to the resource read, or uses a correctly scoped RLS policy under a non-bypass role. Compare exact allowed and denied IDs, actual role and revocation behavior. No production project is needed.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use pinned tooling and a disposable local or explicitly approved test environment. Preserve the starter and solution; source review does not qualify real database roles or authorization.
