## Architecture problem

**Lab local development.** Local Supabase development runs a disposable service stack for migrations, Auth, Storage and API testing. It should not be silently linked to the production project during exercises.

**Unsafe starting point:** The starter jumps to a remote database push and skips local schema replay and environment validation.

Supabase is not a single unrestricted database client. Different credentials and services have different trust boundaries. This source lesson makes the boundary explicit so a working demonstration does not accidentally teach learners to expose server credentials, ignore RLS, or apply migrations against the wrong project.

## Applied persistence walkthrough

The local Supabase stack lets learners rehearse migrations and auth/storage behavior without using a production project. It requires the supported CLI and container runtime, available ports and an isolated working directory. Reset destroys the local database and should be used only with synthetic fixtures. Local behavior is useful evidence but hosted configuration can still differ.

### Diagnose the concrete failure

Inspect CLI help and container prerequisites, then initialize a dedicated disposable project. Start the local services, verify their actual status and target identity, and replay tracked migrations with fake users only. Confirm the intended sample data after reset. Do not copy real production data or secrets into the lab.

### Independent exercise and evidence

Design a repeatable local acceptance checklist for database schema, Auth, Data API and private storage. Record versions, expected services and real positive/negative cases, including cleanup. Hosted provider qualification remains separate.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use an isolated local Supabase environment or an explicitly approved disposable project. Preserve the starter and solution; do not treat source review as live platform or security qualification.
