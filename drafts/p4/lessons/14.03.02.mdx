## Security defect and threat model

**auth.uid and roles.** auth.uid() identifies the caller for requests bearing an authenticated Supabase JWT. The Postgres authenticated role is a broad capability class, not evidence that the caller owns a particular row.

**The vulnerable starting point:** The starter gives any caller in the authenticated Postgres role access to all tasks and ignores row ownership.

An attacker may know an ID, send arbitrary query parameters, or hold a legitimate authenticated account. An application is not secure merely because the login screen works. The database and the authenticated server must prevent one actor from accessing another actor's rows or private objects.

## Guided repair

<LessonStep number={1} title="Reproduce the permissive or privileged access path" file="drafts/p4/labs/auth-uid-and-role-scope/starter.sql" expected="Identify why an authenticated request may still cross its authorization boundary.">

```sql
CREATE POLICY lab_tasks_authenticated_read ON public.academy_lab_tasks
 FOR SELECT TO authenticated USING (true);
```

**Why this fails:** The starter gives any caller in the authenticated Postgres role access to all tasks and ignores row ownership. Do not accept a successful schema statement as proof of row privacy.

</LessonStep>

<LessonStep number={2} title="Write the defensive policy or server boundary" file="drafts/p4/labs/auth-uid-and-role-scope/solution.sql" expected="Constrain operations by caller identity and permitted resources.">

```sql
ALTER TABLE public.academy_lab_tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY lab_tasks_authenticated_owner ON public.academy_lab_tasks
 FOR SELECT TO authenticated
 USING ((SELECT auth.uid()) IS NOT NULL
   AND owner_id = (SELECT auth.uid()));
```

**How the defense works:** Pair TO authenticated with an auth.uid()-based owner predicate and an explicit non-null requirement; avoid user-editable user_metadata for permissions.

</LessonStep>

**Required positive test:** Use the real Supabase Auth local stack and actual client JWTs. Log expected allowed/denied rows while withholding token contents from Git.

## Security review and implementation details

auth.uid() identifies the caller for requests bearing an authenticated Supabase JWT. The Postgres authenticated role is a broad capability class, not evidence that the caller owns a particular row.

Pair TO authenticated with an auth.uid()-based owner predicate and an explicit non-null requirement; avoid user-editable user_metadata for permissions.

Supabase Auth anonymous sign-ins can use the authenticated Postgres role; TO authenticated does not necessarily mean a permanent nonanonymous identity. Enforce app-specific eligibility separately.

RLS applies subject to PostgreSQL roles, table ownership, policy composition and operation type. In an exposed schema, verify grants and RLS together. For writes, review INSERT WITH CHECK and UPDATE USING/WITH CHECK, not just SELECT. In Supabase, do not use user-editable `user_metadata` as authority for privileged roles. A service-role client may bypass RLS; it must not be used to repair a client permission error.

## Applied persistence walkthrough

The authenticated role describes the database request role, not ownership of every row. auth.uid obtains the identity from the request context and can return NULL without an authenticated identity. A role-targeted owner predicate constrains the result; the explicit non-null check makes the intended boundary clear. Anonymous sign-ins can still use the authenticated role, so verify any stronger identity requirement separately.

### Diagnose the concrete failure

Compare a request without a session, one with a valid synthetic user and one attempting another user's ID. Verify the query uses the actual caller's context rather than a privileged service key. Check that user-editable metadata cannot alter access and that no broad policy overrides the expected restriction.

### Independent exercise and evidence

Design a policy for resources available only to verified members, not just anyone in the authenticated role. Decide which current membership or session attributes are authoritative. Record allowed and denied IDs and the verified role context.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use an isolated Supabase environment and real non-bypass caller roles. Preserve the existing starter and solution; source review cannot certify row policies or authorization.

## Security extension and release conditions

Extend the access matrix to SELECT, INSERT, UPDATE and DELETE where applicable. Build a pgTAP or equivalent isolated integration test that fails on the deliberately permissive starter and passes on the narrow policy. Run requests through the same Supabase Data API and authenticated route as the real app; test with the least-privileged role first. Include a second database connection if RLS behavior depends on transaction state.

Keep copies of all policy test results sanitized. Do not move this manuscript to the published registry before an explicit human security review and actual local RLS test runs.
