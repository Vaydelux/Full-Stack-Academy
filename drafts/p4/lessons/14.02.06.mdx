## Authentication problem

**JWT claims and JWKS.** JWT signing keys and JWKS enable cryptographic validation of access-token claims. getClaims validates token signature/expiry; getUser consults Auth for a fresher identity check when revocation matters.

**Broken starting assumption:** Base64-decoding a JWT without verifying its signature or expiry lets an attacker forge claims such as an admin role.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

<LessonStep number={2} title="Implement the authenticated flow" file="drafts/p4/labs/verified-jwt-claims/solution.ts" expected="Use verified identity/session APIs and narrow resource access.">

```ts
const { data, error } = await supabase.auth.getClaims();
if (error || !data?.claims?.sub)
  throw new Error("Unauthenticated");
const userId = data.claims.sub;
// For sensitive revocation-dependent operations, fetch fresh user/session info.
const fresh = await supabase.auth.getUser();
if (fresh.error || fresh.data.user?.id !== userId)
  throw new Error("Session invalid");
// Authorization still requires trusted server membership/permission lookup.
```

**Repair reasoning:** Use the Supabase Auth verification APIs and resolve role/tenant permissions from server-controlled data. Never authorize based on raw_user_meta_data or an unverified decoded payload.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

</LessonStep>

<LessonStep number={3} title="Prove both allowed and rejected states" file="drafts/p4/labs/verified-jwt-claims/acceptance.md" expected="One authenticated success and one negative session/authorization case are recorded.">

**Allowed behavior:** Using local Auth test users and rotated/expired tokens, verify getClaims, getUser and role lookup behavior. Record access-token expiry semantics; don't overstate immediate revocation of JWTs.

**Denied behavior:** Provide an altered JWT payload with isAdmin true and a stale/revoked session; the privileged route must reject the forgery and apply its revocation freshness requirements.

**Security limitations:** An unexpired JWT can remain signature-valid after a session is revoked. Select getUser/session checks for operations needing fresher session revocation guarantees.

A successful source integrity check cannot stand in for a real Auth token refresh, signed JWT verification, email delivery, OAuth callback or MFA challenge.

</LessonStep>

## Trust boundaries and operational choices

JWT signing keys and JWKS enable cryptographic validation of access-token claims. getClaims validates token signature/expiry; getUser consults Auth for a fresher identity check when revocation matters.

Use the Supabase Auth verification APIs and resolve role/tenant permissions from server-controlled data. Never authorize based on raw_user_meta_data or an unverified decoded payload.

An unexpired JWT can remain signature-valid after a session is revoked. Select getUser/session checks for operations needing fresher session revocation guarantees.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.
