## Real-world problem

**Transactions and isolation.** The interactive $transaction callback runs dependent writes as one database transaction. An error aborts the unit; a conditional decrement protects against a negative balance.

**Defect in the first implementation:** A failure after the debit but before the credit leaves the first wallet reduced. It also omits tenant predicates and an insufficient-balance check.

The goal of this lesson is a testable database-access invariant, not a clever-looking call to Prisma. A server process may have broader database permissions than the user making the HTTP request. The ORM knows model types but does not necessarily know the caller's tenant membership or object-level permission.

<LessonStep number={2} title="Implement the constrained repository operation" file="drafts/p4/labs/transactional-prisma-transfer/solution.ts" expected="Add an explicit correctness and trust boundary.">

```ts
if (!Number.isSafeInteger(amount) || amount <= 0 || fromId === toId)
  throw new Error("Invalid transfer");
await db.$transaction(async (tx) => {
  const from = await tx.wallet.updateMany({
    where: { id: fromId, tenantId, balance: { gte: amount } },
    data: { balance: { decrement: amount } },
  });
  if (from.count !== 1) throw new Error("Insufficient or missing source");
  const to = await tx.wallet.updateMany({
    where: { id: toId, tenantId },
    data: { balance: { increment: amount } },
  });
  if (to.count !== 1) throw new Error("Missing destination");
});
```

**Repair reasoning:** Validate amount, use one transaction callback and tenant filters for both wallets, check affected rows and throw on any missing row so the entire unit rolls back.

Any identifier or tenant context in the code sample must be provided by an authenticated server handler. The snippet is an excerpt of a larger module: it should be integrated with the generated Prisma Client type, validated domain input and a database role appropriate for the application's trust boundary.

## Architecture and implementation choices

The interactive $transaction callback runs dependent writes as one database transaction. An error aborts the unit; a conditional decrement protects against a negative balance.

Validate amount, use one transaction callback and tenant filters for both wallets, check affected rows and throw on any missing row so the entire unit rolls back.

A database transaction cannot atomically commit an external message broker or payment provider. Use an outbox and idempotency policy for cross-system work.

A safe persistence layer should accept explicit request-scoped identities, use bounded queries, reject unsupported input, and keep internal query types from becoming public API DTOs. For permission-sensitive mutations, reason about database constraints and application authorization separately: a valid foreign key does not mean the calling actor may update that row.

## Applied persistence walkthrough

An interactive transaction supplies a transaction-scoped client for all participating statements. The debit uses a balance predicate and an atomic decrement; the credit must update exactly one destination row. Throwing aborts the transaction. The example does not specify an isolation level, durable operation key or deterministic lock order; production transfers need those decisions separately.

### Diagnose the concrete failure

Check valid transfer, insufficient balance, missing destination and same-account rejection. For the missing destination case, verify the source debit rolls back. On a real database, run concurrent competing transfers with bounded deadlines and inspect final balances. Do not treat a fake transaction callback as PostgreSQL isolation evidence.

### Independent exercise and evidence

Design a retry policy for transient serialization or deadlock failures. Retry the whole operation only when safe, and use a durable idempotency record for uncertain outcomes. Record affected rows, final balance totals and actual transaction failure classes.
