## Authentication problem

**Email templates and redirect URLs.** Supabase email links rely on configured Site URL and redirect allowlists. Templates and application callbacks must use approved destinations and avoid leaking tokens to third parties.

**Broken starting assumption:** An untrusted redirectTo parameter can be used to send password-reset flows to an attacker-controlled destination.

An application can show a signed-in UI and still lack a valid server-side session or permission to read a specific tenant's data. Authentication identifies the actor; authorization decides which resources that actor may use. This module trains both concepts without embedding production credentials in the examples.

```ts
const approvedOrigin = process.env.NEXT_PUBLIC_APP_ORIGIN;
if (!approvedOrigin) throw new Error("Missing app origin");
const redirectTo = new URL("/auth/update-password", approvedOrigin).toString();
const { error } = await supabase.auth.resetPasswordForEmail(email, {
  redirectTo,
});
if (error) throw new Error("Unable to request password reset");
```

**Repair reasoning:** Build the redirect from a controlled application origin and fixed path; configure that exact URL in Supabase Auth's allowed redirect list.

The code sample is a teaching excerpt; integrate it with the framework's generated types, secure cookie handling and a fail-closed route handler. Any example variable representing a role, application origin or tenant must be obtained from trusted configuration and server-side authorization.

## Trust boundaries and operational choices

Supabase email links rely on configured Site URL and redirect allowlists. Templates and application callbacks must use approved destinations and avoid leaking tokens to third parties.

Build the redirect from a controlled application origin and fixed path; configure that exact URL in Supabase Auth's allowed redirect list.

Avoid sensitive info in URLs, referrer headers and analytics. Ensure callback endpoints have no open-redirect forwarding and do not expose token hashes.

In production, model expired access tokens, refresh-token rotation, multiple concurrent tabs, CSRF/state handling where applicable, cookie attributes, MFA enrollment and logout propagation. Never rely on raw JWT decoding, a mutable cookie JSON field, an unverified redirect URL or a user-editable metadata claim to authorize administrative actions.

## Applied persistence walkthrough

Password-reset emails should lead only to approved application destinations. The shown code constructs a fixed path from configured origin; it does not validate that configuration against an explicit allowlist or implement the password-update callback. Public responses should avoid account enumeration. Reset tokens and links are sensitive credentials.

### Diagnose the concrete failure

Use a local test mailbox and synthetic account. Confirm the reset link targets the expected environment and that a valid recovery session can update the password. Exercise expired and reused links and an unapproved redirect. Review template configuration without copying secret links into evidence.

### Independent exercise and evidence

Create a matrix of local and deployed callback origins with exact intended paths. Define a neutral response for unknown email addresses and a bounded request rate. Record status and redirect decisions, not token values.

**Qualification boundary:** These are acceptance instructions, not recorded results. Use isolated synthetic identities and the pinned SDK. Preserve the existing starter and solution; source inspection does not establish actual Auth or session security.
