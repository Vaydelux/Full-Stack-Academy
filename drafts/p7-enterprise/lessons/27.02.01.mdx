# OpenAPI and Zod contracts

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A frontend and API disagree about task payload.

## Step 1 — Mental model

OpenAPI describes the HTTP contract; runtime validation enforces trusted boundaries. Keep schemas and generated clients aligned.

## Step 2 — Guided practice

Define create-task request/response with Zod and OpenAPI; test invalid length and unknown fields.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Valid request matches documented response.

**Negative:** Invalid body or divergent schema fails.

## Applied engineering walkthrough

A create-task contract defines accepted request fields, bounded values, success response and expected error shapes. OpenAPI describes the interface; runtime validation still must reject untrusted input. Keep a single reviewed mapping between the Zod schema and generated client contract rather than allowing silent drift.

### Diagnose the concrete failure

Submit a valid synthetic task, an overlong title, a missing property and an unexpected organization field. Verify the server validates each request before invoking the use case and returns the documented error shape.

### Independent exercise and evidence

Compare generated client types, OpenAPI examples and actual HTTP responses for the same fixture. Record the request and response evidence and ensure validation does not replace membership or object authorization.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual API, database, authentication and reviewer evidence.
