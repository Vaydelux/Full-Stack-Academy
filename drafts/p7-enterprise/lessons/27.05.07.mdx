# Upgrade plan

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A dependency upgrade may break the system.

## Step 1 — Mental model

Upgrade plan inventories versions, advisories, compatibility, migrations and rollback; test incrementally.

## Step 2 — Guided practice

Create a reviewable upgrade branch for one dependency with lockfile and regression checks.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Actual upgrade diff and test results are recorded.

**Negative:** Fabricated lock or unexplained breaking change fails.

Inspect the complementary `defenseAcceptance` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Final defense rubric only; actual human review, exploit verification, performance, costs and upgrade rehearsal remain separate.

## Applied engineering walkthrough

An upgrade is a controlled change to an existing system, not a reason to refresh every dependency simultaneously. Inventory the affected versions, advisories, compatibility constraints and migration obligations. Preserve the previous lockfile and artifact identity so the impact and recovery path remain reviewable.

### Diagnose the concrete failure

Choose one dependency in a disposable branch and inspect its relevant migration notes. Generate a genuine resolved lockfile with the supported toolchain, run focused tests and the full applicable gate, then compare the candidate to the baseline.

### Independent exercise and evidence

Record version changes, lockfile differences, regression outcomes and deployment compatibility. Define rollback or forward recovery and unresolved findings; if registry access or the required runtime is unavailable, stop without inventing a lockfile or claiming an upgrade succeeded.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual implementation, review, recovery, cost and candidate evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
