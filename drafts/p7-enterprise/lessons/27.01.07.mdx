# Accessibility acceptance

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A keyboard-only user completes a task.

## Step 1 — Mental model

Accessibility acceptance requires keyboard, focus, label, contrast, zoom and assistive technology review.

## Step 2 — Guided practice

Complete a local task flow with keyboard and 200% zoom; record screen-reader observations.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** User can complete and recover from errors.

**Negative:** Trapped focus, unreadable text or unlabeled control fails.

Inspect the complementary `webAcceptance` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

## Applied engineering walkthrough

Accessibility acceptance combines keyboard navigation, meaningful names and roles, visible focus, contrast, zoom and assistive technology observations. Automated tests cover selected rules but do not establish that a complete task journey is usable. Include errors and dynamic updates in the review.

### Diagnose the concrete failure

Complete the task creation flow using only keyboard input at normal and 200 percent zoom. Trigger invalid input, inspect focus and error association, then repeat with an available screen reader and record what is announced.

### Independent exercise and evidence

Prepare a review matrix with browser, viewport, assistive technology, observed behavior and defect severity. Include dark and light themes and narrow screens. Mark unavailable human review not-run rather than inventing evidence.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and verify actual application, browser and human review evidence independently.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
