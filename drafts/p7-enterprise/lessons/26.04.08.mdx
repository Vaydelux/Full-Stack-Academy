# Lab safe admin console

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A learner designs an administrative console.

## Step 1 — Mental model

Privileged UI must enforce server authorization for every operation, with reason, confirmation and audit for sensitive actions.

## Step 2 — Guided practice

Run adminAllowed; implement a disposable scoped settings action with denial and audit assertions.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Authorized action recorded, unauthorized action blocked.

**Negative:** Client-only permission check or missing audit evidence fails.

Inspect the complementary `adminAllowed` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Synthetic tenant-admin authorization model only; actual RBAC, audit integrity, support workflows and migration safety require runtime acceptance.

## Applied engineering walkthrough

A privileged administration interface needs server-side authorization for each operation, explicit reason and appropriate confirmation for sensitive actions, plus an attributable audit record. Hiding controls helps usability but does not prevent direct API requests. Define failure and recovery paths before enabling destructive controls.

### Diagnose the concrete failure

Run adminAllowed for authorized and forbidden cases, then design a disposable settings action with direct API bypass attempts, stale revision and failed audit persistence. Verify foreign and denied actions leave state unchanged.

### Independent exercise and evidence

Submit an administration capstone matrix covering permissions, confirmations, audit events, concurrent changes and recovery. Record actual request and database results and independent reviewer evidence, not only visible UI behavior.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual API, database, authorization, browser and reviewer evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
