# Lab enterprise auth threat model

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A learner reviews enterprise authentication threats.

## Step 1 — Mental model

Model IdP trust, provisioning, sessions, MFA, tenant identity and admin control as separate boundaries.

## Step 2 — Guided practice

Run enterpriseAccess tests; write an abuse-case matrix for assertion replay, deprovisioning and cross-tenant escalation.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Each threat has denial test, owner and recovery plan.

**Negative:** Trusting unvalidated claims or missing revocation evidence blocks acceptance.

Inspect the complementary `enterpriseAccess` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Synthetic policy check on already-validated claims only; no actual SAML assertion, SCIM, MFA, token or identity-provider verification.

## Applied engineering walkthrough

Enterprise identity joins multiple independent boundaries: IdP trust, provisioning, organization membership, session lifecycle, step-up authentication and administrative authorization. A successful SSO login establishes identity under the configured trust rules, not blanket access to all enterprise resources.

### Diagnose the concrete failure

Use synthetic enterpriseAccess cases and build a matrix for replayed assertions, removed group membership, revoked devices and foreign-tenant escalation. Trace each case to the component responsible for denying it.

### Independent exercise and evidence

Prepare a disposable IdP and application acceptance plan with explicit expected state changes, audit records and recovery procedures. Record actual integration and negative results separately from the local teaching model.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual IdP, application authorization, database and reviewer evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
