# Milestone integrated workspace

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A learner integrates workspace features.

## Step 1 — Mental model

Cross-feature acceptance verifies behavior, security boundaries, error recovery and audit together.

## Step 2 — Guided practice

Run workspaceAcceptance; execute actual create/upload/notification/cache/live/search flow with negative cases.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Required journey works with isolation and audit evidence.

**Negative:** Passing isolated units but failing integrated journey blocks milestone.

Inspect the complementary `workspaceAcceptance` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Synthetic integrated-feature rubric; actual upload, mail, Redis, websocket, search and audit behavior require live isolated tests.

## Applied engineering walkthrough

Cross-feature acceptance follows a task from authorized creation through attachment, assignment, notification, cache, live update, search and audit. Each feature has its own failure boundary and recovery contract; the whole workflow must preserve tenant isolation and authoritative task state when a dependency fails.

### Diagnose the concrete failure

Run workspaceAcceptance with a missing security or recovery item, then execute the available real workflow with synthetic tenants. Interrupt one background effect, reconnect the live client and compare the authoritative task to cache and search views.

### Independent exercise and evidence

Build a commit-bound matrix of expected and observed outcomes, including negative upload, foreign access and duplicate job cases. Record unresolved dependencies and actual runtime evidence separately from a rubric result; do not promote on a declared checklist alone.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual API, storage, database, queue, cache, browser and reviewer evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
