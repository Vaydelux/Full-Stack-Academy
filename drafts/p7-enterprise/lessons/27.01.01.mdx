# Requirements and scope

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A small team proposes a multi-tenant task workspace.

## Step 1 — Mental model

Requirements distinguish actors, core journeys, constraints, non-goals and measurable acceptance.

## Step 2 — Guided practice

Write scope for sign-in, task editing and organization separation; exclude optional billing and mobile from first release.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Each must-have has a testable outcome.

**Negative:** Unbounded feature list without acceptance fails.

Inspect the complementary `webAcceptance` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Capstone rubric checks supplied evidence flags only; no actual app build, SEO, browser or accessibility verification.

## Applied engineering walkthrough

Start the capstone with a small multi-tenant task workspace, not a list of frameworks. Separate anonymous visitors, members and administrators, and define what each can accomplish. A useful requirement names the actor, action, expected result and measurable failure condition. Optional billing and native clients remain outside this first release.

### Diagnose the concrete failure

Write acceptance cases for sign-in, task creation, editing and isolation between two synthetic organizations. Ask what happens when a member is removed, a request fails or a task does not exist; turn each ambiguity into an explicit requirement.

### Independent exercise and evidence

Create a traceability table linking each requirement to a route, server invariant and test. Mark non-goals and dependencies, and record a review decision before adding features. Use the same scope throughout subsequent capstone modules.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and verify actual application, browser and human review evidence independently.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
