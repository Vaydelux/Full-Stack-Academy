# Source and API documentation

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A future maintainer needs to understand the app.

## Step 1 — Mental model

Source and API documentation should cover setup, contracts, architecture, operational limits and troubleshooting.

## Step 2 — Guided practice

Write a fresh-checkout guide and OpenAPI examples; ask another reviewer to follow them.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** A reviewer can reproduce supported flow.

**Negative:** Missing prerequisites or invented test outcomes fail.

## Qualification boundary

## Applied engineering walkthrough

Good documentation makes a fresh checkout reproducible and explains the public contracts, setup, architecture, operational boundaries and troubleshooting. Keep commands aligned with checked-in scripts, specify supported tool versions and identify required versus optional dependencies. Use safe synthetic examples rather than copying production configuration.

### Diagnose the concrete failure

Ask a reviewer to follow the setup guide from an isolated clean checkout. Compare documented API examples to actual responses, including invalid input and denied access. Record the first broken or ambiguous instruction rather than silently fixing the reviewer's environment.

### Independent exercise and evidence

Write a concise maintenance guide with configuration sources, migration steps, common failures and verification commands. Include a versioned OpenAPI reference and evidence of actual execution; mark steps that could not be reproduced.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual implementation, review, recovery, cost and candidate evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
