# Continuous integration

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A candidate commit must pass repeatable checks.

## Step 1 — Mental model

CI specifies immutable inputs, required jobs and exact-commit evidence; local qualification can precede hosted automation.

## Step 2 — Guided practice

Use existing local coordinator and design required lint/type/test/build jobs without enabling Actions.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Required checks have actual matching results.

**Negative:** Skipped or stale job cannot pass.

Inspect the complementary `productionAcceptance` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

## Qualification boundary

Capstone readiness rubric only; no container, deployment, scan, benchmark or restore is verified by supplied booleans.

## Applied engineering walkthrough

A delivery pipeline should bind immutable source, toolchain, dependency lockfiles and required checks to a candidate artifact. Define the local verification matrix first and preserve failure exit codes; hosted automation is a transport for those checks, not a substitute for them. Never label an absent check as passing.

### Diagnose the concrete failure

Run the existing qualification coordinator in plan mode, inspect its required commands and simulate a failing test or missing toolchain. Verify the release cannot proceed merely because earlier checks succeeded or an unrelated artifact exists.

### Independent exercise and evidence

Create a commit-bound receipt containing actual tool versions, commands, results, log locations and artifact hashes. Keep the existing Actions and deployment freeze; record missing runtime checks as blockers rather than changing required gates to obtain a green result.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual infrastructure, build, security, performance, recovery and reviewer evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
