# Deployment and rollback

> Instructor draft. Local models do not qualify external identity, billing, privacy compliance or an actual capstone release.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A new release must be reversible.

## Step 1 — Mental model

Deploy a reviewed immutable artifact, verify compatibility and health, define rollback and migration recovery.

## Step 2 — Guided practice

Rehearse a disposable release with failed smoke and rollback to prior known version.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Rollback restores intended service and preserves data.

**Negative:** Incompatible destructive change or unverified rollback fails.

## Applied engineering walkthrough

A deployment should use a reviewed immutable artifact with known configuration and database compatibility. Plan schema changes for the old and new application versions if they may coexist. Rollback of application code may not undo data changes, so define recovery for migrations separately.

### Diagnose the concrete failure

Rehearse a disposable release from a known baseline to a candidate. Inject a failed smoke check and return traffic to the prior compatible version. Verify the database and user-visible workflow remain consistent rather than only observing a process restart.

### Independent exercise and evidence

Document artifact digest, migration strategy, health check, rollback trigger and responsible operator. Record the observed recovery time and any irreversible changes. No live deployment is required for the practice.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual infrastructure, build, security, performance, recovery and reviewer evidence.
