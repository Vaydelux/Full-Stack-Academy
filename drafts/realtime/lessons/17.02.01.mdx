# In-app notification schema

> Unpublished instructor manuscript. This topic is not available in the public Academy reader and has not passed Node 24/production browser qualification.

## Learning outcomes

Trace the authenticated actor, tenant boundary, relevant state transition, and failure path. Implement or describe a minimal correction and reproduce a positive case plus a negative case with synthetic data.

## Context

A SaaS app sends an in-app message when an export completes.

This scenario connects directly to a real full-stack engineering concern: security, consistency, user experience and the cost of retries must be considered together.

## Step 1 — Explain the model

Define a minimal recipient-scoped schema with stable deduplication ID, title, created-at and read status.

**Design exercise:** Draw the actor → browser/client → API or transport → authoritative store → other clients path. Label which inputs are controlled by callers and which authorization and version decisions must be enforced server-side.

## Step 2 — Find the failure

The notification only stores message text, without a tenant, recipient, event ID, timestamp or read state.

**Adversarial exercise:** Describe the smallest reproducible request or event sequence that exposes this failure. Record what data must remain private, what state must remain durable, and what a reconnecting client is allowed to replay.

## Step 3 — Correct and test

Define a minimal recipient-scoped schema with stable deduplication ID, title, created-at and read status.

**Acceptance target:** Enqueue one synthetic completion event and inspect the resulting unread item.

Run the related dependency-free teaching exercise:

node --test examples/p5-realtime/notifications.test.mjs

The tests exercise local Node state or loopback HTTP behavior. Document separately any real Supabase Realtime, push/email provider or Yjs integration that is still missing.

## Misconception

A notification row is not evidence that an email or push provider delivered it.

## Applied engineering walkthrough

A notification is a durable recipient-specific record, not merely a message string. Tenant, recipient, event identity, creation time and read state belong to its contract. The event can be shared across recipients while delivery records remain distinct.

### Diagnose the concrete failure

Create a synthetic export-completed notification and inspect its identity and unread state. Repeat the same event for the same recipient and verify the intended deduplication behavior. Query as another recipient and assert exclusion.

### Independent exercise and evidence

Design a notification schema with a recipient-scoped uniqueness rule, retention policy and stable pagination. Record expected item count and fields before testing actual persistence.
