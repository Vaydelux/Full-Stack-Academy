# Authorization for channels

> Unpublished instructor manuscript. This topic is not available in the public Academy reader and has not passed Node 24/production browser qualification.

## Learning outcomes

Trace the authenticated actor, tenant boundary, relevant state transition, and failure path. Implement or describe a minimal correction and reproduce a positive case plus a negative case with synthetic data.

## Context

Two organizations subscribe to similar room identifiers.

This scenario connects directly to a real full-stack engineering concern: security, consistency, user experience and the cost of retries must be considered together.

## Step 1 — Explain the model

Resolve the principal server-side and authorize channel reads and writes on every subscribe/publish boundary.

**Design exercise:** Draw the actor → browser/client → API or transport → authoritative store → other clients path. Label which inputs are controlled by callers and which authorization and version decisions must be enforced server-side.

## Step 2 — Find the failure

The client can construct any channel name and receives another organization's event stream.

**Adversarial exercise:** Describe the smallest reproducible request or event sequence that exposes this failure. Record what data must remain private, what state must remain durable, and what a reconnecting client is allowed to replay.

## Step 3 — Correct and test

Resolve the principal server-side and authorize channel reads and writes on every subscribe/publish boundary.

**Acceptance target:** Assert an authenticated alpha user receives alpha events but a beta subscription gets a nonrevealing denial.

Run the related dependency-free teaching exercise:

```bash
node --test examples/p5-realtime/feed.test.mjs
```

The tests exercise local Node state or loopback HTTP behavior. Document separately any real Supabase Realtime, push/email provider or Yjs integration that is still missing.

## Misconception

Hiding a room name is not the same as enforcing channel authorization.

## Knowledge check

1. Which actor, resource, version or event cursor is authoritative in this scenario?
2. Where must tenant membership or consent be checked rather than trusting the browser?
3. Which deliberate failure or duplicate event proves the unsafe implementation is wrong?
4. What would you need to test against a real service before promoting this lesson?

**Instructor rubric:** Require a concrete sequence, the trust boundary, a positive and negative observation, and an explicit statement of which infrastructure has not yet been exercised.
