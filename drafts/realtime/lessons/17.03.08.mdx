# Lab collaborative notes prototype

> Unpublished instructor manuscript. This topic is not available in the public Academy reader and has not passed Node 24/production browser qualification.

## Learning outcomes

Trace the authenticated actor, tenant boundary, relevant state transition, and failure path. Implement or describe a minimal correction and reproduce a positive case plus a negative case with synthetic data.

## Context

Students prototype a collaborative notes workspace.

This scenario connects directly to a real full-stack engineering concern: security, consistency, user experience and the cost of retries must be considered together.

## Step 1 — Explain the model

Implement a versioned notes service with document permissions, compare-and-swap, operation replay protection, TTL-based presence and an offline queue.

**Design exercise:** Draw the actor → browser/client → API or transport → authoritative store → other clients path. Label which inputs are controlled by callers and which authorization and version decisions must be enforced server-side.

## Step 2 — Find the failure

The UI presents presence and optimistic edits as if they offer Yjs-style convergence.

**Adversarial exercise:** Describe the smallest reproducible request or event sequence that exposes this failure. Record what data must remain private, what state must remain durable, and what a reconnecting client is allowed to replay.

## Step 3 — Correct and test

Implement a versioned notes service with document permissions, compare-and-swap, operation replay protection, TTL-based presence and an offline queue.

**Acceptance target:** Run collaboration tests for stale writes, idempotent replay, forbidden edits, transient presence and unresolved offline conflicts.

Run the related dependency-free teaching exercise:

```bash
node --test examples/p5-realtime/collaboration.test.mjs
```

The tests exercise local Node state or loopback HTTP behavior. Document separately any real Supabase Realtime, push/email provider or Yjs integration that is still missing.

## Misconception

This is a process-local CAS exercise; genuine CRDT convergence requires a real Yjs/provider integration.

## Applied engineering walkthrough

The collaborative notes prototype combines permissions, revisions, local pending edits and ephemeral presence. These mechanisms teach conflict detection and recovery, not distributed CRDT convergence. Treat each state boundary and failure mode as a separate acceptance requirement.

### Diagnose the concrete failure

Run the existing collaboration suite and trace a permitted edit, a stale edit, duplicate operation identity, denied write and offline retry. Verify final text, revision and retained pending state. Confirm presence expiry never changes document data.

### Independent exercise and evidence

Prepare a capstone acceptance matrix including real browser offline behavior, persistent storage, authorized transport and optional actual Yjs convergence. Record local model outcomes separately from those external gates.

**Qualification boundary:** These are practice instructions, not recorded results. Preserve the original laboratory and publication status. Local simulations do not qualify actual browser or distributed provider behavior.
