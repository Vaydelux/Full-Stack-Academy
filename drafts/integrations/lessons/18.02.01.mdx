# Transactional vs marketing email

> Source-only instructor manuscript. Not published; no Node 24, cloud provider, production database, Next browser or human accessibility qualification is claimed by this page.

## Learning outcomes

Explain the trust boundary for this feature, design the secure state transition, and demonstrate both successful and adversarial behavior. Distinguish a teaching fixture from a qualified production integration.

## Context

A billing app sends receipts and optional promotional campaigns to the same account.

**Architectural concern:** Keep authenticated identity and tenant scope under server control. Treat browser inputs, provider callbacks, file bytes and retry state as untrusted until validated.

## Step 1 — Model the failure

Applying marketing consent rules to receipts or bypassing consent for offers confuses legal purposes.

Draw the caller → API boundary → persisted state → worker/provider → response chain. Identify which fields the browser or external service may alter and which identities only the server may authorize.

## Step 2 — Design the correction

Separate transactional and marketing message intents; require positive opt-in before marketing enqueue and claim.

Identify an appropriate transactional or idempotency boundary and specify a stable identifier for retries. Record what must be denied, rather than assuming a happy-path demonstration is sufficient.

## Step 3 — Practice and verify

An opted-in user gets a marketing job and every authorized purchase can create a receipt.

**Negative acceptance target:** An opted-out user never gets a claimed marketing send even if consent is revoked after enqueue.

From the root of the repository, execute the local P5 integrations teaching tests:

## Engineering review

**Hardening boundary:** The teaching outbox does not send an email, inspect DNS, run React Email, or connect to a delivery provider; these are independent live release gates.

For a production implementation, document the secret-owner or principal, durability plan, error and recovery policy, rate/resource bounds, privacy guarantees, observability without sensitive payloads, and the credential/version-rotation procedure.
