# Signed upload and download

> Source-only instructor manuscript. Not published; no Node 24, cloud provider, production database, Next browser or human accessibility qualification is claimed by this page.

## Learning outcomes

Explain the trust boundary for this feature, design the secure state transition, and demonstrate both successful and adversarial behavior. Distinguish a teaching fixture from a qualified production integration.

## Context

A browser requests one short-lived upload capability for its own tenant workspace.

**Architectural concern:** Keep authenticated identity and tenant scope under server control. Treat browser inputs, provider callbacks, file bytes and retry state as untrusted until validated.

## Step 1 — Model the failure

An unscoped token remains valid for any user and may be replayed after its expiration.

Draw the caller → API boundary → persisted state → worker/provider → response chain. Identify which fields the browser or external service may alter and which identities only the server may authorize.

## Step 2 — Design the correction

Sign a tenant/user/filename/nonce/expiry claim and verify binding before accepting an upload intent.

Identify an appropriate transactional or idempotency boundary and specify a stable identifier for retries. Record what must be denied, rather than assuming a happy-path demonstration is sufficient.

## Step 3 — Practice and verify

The intended actor can validate a token during its short validity window.

**Negative acceptance target:** Another tenant, another user, an altered token or an expired token is denied.

From the root of the repository, execute the local P5 integrations teaching tests:

```bash
node --test examples/p5-integrations/labs.test.mjs

Inspect the lab implementation in `examples/p5-integrations/labs.mjs`, find the nearest positive and negative test, and write an additional case for your own scenario. ## Engineering review

**Hardening boundary:** These are byte-signature and state-machine teaching controls only: real image decoders, antivirus engines, durable object storage and provider URL signing require separate qualification.

For a production implementation, document the secret-owner or principal, durability plan, error and recovery policy, rate/resource bounds, privacy guarantees, observability without sensitive payloads, and the credential/version-rotation procedure.

## Applied engineering walkthrough

A signed capability delegates a specific operation under defined conditions. Bind the actor, tenant, object identity and expiry to the signed claims; do not accept independent request fields as overrides. Expiry limits the window of use but does not enforce single-use semantics without durable nonce tracking.

### Diagnose the concrete failure

Issue a synthetic token for an allowed actor using the local signer. Verify it before expiry, then exercise wrong actor, wrong tenant, altered token and expiry. Test whether repeated valid use is permitted by the fixture rather than claiming replay prevention automatically.

### Independent exercise and evidence

Design distinct upload and download capability contracts, including object state, expiration and optional single-use enforcement. Record decisions and synthetic claim IDs, never live signed URLs.

**Qualification boundary:** These are practice instructions, not recorded results. Preserve existing specifications and laboratory contracts. Qualify actual external services separately using authorized disposable infrastructure.
