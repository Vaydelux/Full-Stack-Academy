# Secure defaults

> **Draft — not published or runtime-qualified.** This instructor manuscript uses an original multi-tenant workspace scenario. It does not claim that any production API was audited.

## Learning outcomes

After completing this lesson, you should be able to explain the underlying security boundary, identify a realistic failure, propose a testable mitigation, and write evidence that distinguishes a control from an aspiration.

## The scenario

A newly created project has no explicit sharing configuration.

## Step 1 — Build the mental model

Use deny-by-default for access, restrictive feature flags and privacy-preserving object visibility; require explicit opt-in for broad sharing.

Write down the trusted principal, requested operation, resource identifier, and where authorization or validation must happen. A browser payload is never authoritative merely because it passes schema validation.

## Step 2 — Investigate the failure

Missing access-policy rows are treated as public access, exposing documents from incomplete provisioning.

**Prediction:** What information or action becomes available to an attacker? Write one request that should fail, identify the expected status/response without leaking another tenant's data, and specify what must *not* appear in logs.

## Step 3 — Design and verify the fix

Default to private; absence of a policy denies access; keep privileged paths separate from public handlers.

**Practice task:** Write a table-driven test for missing policy, private, member, explicit public, and malformed policy values.

Your acceptance criteria must include a positive authorized case and a negative adversarial case. Use the actual identity and persistence boundary where applicable; mocks alone do not prove isolation.

## Misconception to challenge

Safe default behavior must be enforced on the server, not only by hiding UI controls.

## Applied engineering walkthrough

Fail-closed defaults mean missing configuration does not expand permissions. An absent sharing policy is different from an explicit public policy. A provisioning workflow may create resources before all policy rows exist, so private defaults must hold during incomplete or failed setup. Administrative access should have a separate explicit authorization path.

### Diagnose the concrete failure

Seed a newly created project with no sharing policy, a private project and an explicitly shared project. Verify only the intended actor can read the first two, and check the public case against the documented sharing rule. Simulate failed provisioning and verify the resource remains private.

### Independent exercise and evidence

Define a sharing state machine with private, invited and public states. Specify who can transition each state and how revocation works. Record allowed and denied reads before and after transitions, including missing or malformed policy records.

**Qualification boundary:** These are practice instructions, not recorded audit results. Use synthetic data and authorized disposable infrastructure. Preserve existing laboratory contracts and publication status.

## Knowledge check

1. Which input is controlled by the attacker in this scenario?
2. Where does authority originate, and why must the check execute server-side?
3. What negative test proves this specific failure is addressed?
4. Which evidence remains missing after a static source review?

**Instructor marking guide:** Answers must name the principal, resource, trust boundary, concrete forbidden action and a repeatable test result. General claims such as “we have authentication” do not earn verification credit.
