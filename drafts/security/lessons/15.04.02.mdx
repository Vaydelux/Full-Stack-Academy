# Incident response

> Source-only teaching manuscript. Not yet available to learners or runtime qualified.

## Learning outcomes

Explain the security boundary, predict a failure, implement or describe a safe correction, and distinguish verified tests from an untested design.

## Context

A workspace reports suspicious downloads.

## Step 1 — Mental model

Prepare detection, containment, evidence, recovery and postmortem.

Record the actor, trusted identity, data flow, requested action, target object and decision boundary. Client-supplied values and authenticated identities are not interchangeable.

## Step 2 — Debug the unsafe design

Operator deletes logs and restores service without revoking credentials.

**Guided task:** In a synthetic local fixture, trace an adversarial request. Identify exactly what is controlled by the caller, what should happen, and which fact is mistakenly trusted. Do not use real third-party systems or personal data.

## Step 3 — Correct and verify

Preserve evidence and use written containment and communication protocol.

**Lab acceptance target:** Tabletop a synthetic data exposure with timeline and roles.

Document both a permitted happy path and a rejected adversarial path. Integration claims require the actual HTTP, database, identity, or browser boundary rather than only mocks.

## Misconception

A passing UI check or source-only checklist cannot establish secure production behavior. An observed negative test and reviewed trust boundary are essential.

## Applied engineering walkthrough

Incident response separates detection, containment, evidence preservation, eradication and recovery. Restoring availability without removing compromised access can recreate the incident. Prioritize containment according to business impact and avoid deleting evidence while investigating.

### Diagnose the concrete failure

Run a tabletop exercise using synthetic alerts for a leaked service credential. Identify who owns containment, which affected access should be revoked, and which logs and artifacts must be preserved. Verify a replacement credential can be tested in isolation.

### Independent exercise and evidence

Write a timed incident record with observed facts, hypotheses, decisions and owners. Include communication, recovery validation and a post-incident action list. Do not report a simulated incident as an actual breach.

**Qualification boundary:** These are practice instructions, not recorded audit results. Use synthetic data and authorized disposable infrastructure. Preserve existing laboratory contracts and publication status.

## Knowledge check

1. Which input is attacker-controlled?
2. Where does the trusted authorization or validation decision occur?
3. Which negative test would fail under the unsafe design?
4. Which environment or evidence remains unverified after source review?

**Instructor rubric:** Require actor, resource, action, violated boundary, specific mitigation, and reproducible positive/negative observations. Missing evidence is not a pass.
