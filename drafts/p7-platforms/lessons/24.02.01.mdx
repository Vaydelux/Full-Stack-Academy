# SQLite local schema

> Instructor draft. Local models do not qualify native platforms, real providers or production deployments.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A field worker edits tasks without internet.

## Step 1 — Mental model

Local SQLite schema needs stable IDs, version, deletion marker and pending operations; transactionally write changes and queue intent.

## Step 2 — Guided practice

Create a disposable SQLite schema and insert a synthetic task and queue row in one transaction.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Both local record and operation persist together.

**Negative:** Partial write after simulated failure violates the invariant.

## Qualification boundary

In-memory sync model; actual SQLite persistence, durable queue, crash recovery and conflict reconciliation are not established.

## Applied engineering walkthrough

Keep each local entity edit and its pending operation in one SQLite transaction. Either both survive a restart or neither does; a server acknowledgement is a separate event. Stable entity identifiers and revisions make subsequent reconciliation possible.

### Diagnose the concrete failure

Interrupt between entity update and queue insert, roll back, and reopen the database. Verify neither write survives. Repeat with commit and confirm both survive.

### Independent exercise and evidence

Add an account partition and verify another synthetic account cannot read its queue. Record transaction boundaries, database rows before and after restart and the unresolved remote acknowledgement.
