# Network and storage permissions

> Instructor draft. Local models do not qualify native platforms, real providers or production deployments.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A mobile app requests access to photos and network.

## Step 1 — Mental model

Permissions should be minimal, contextual, and degrade safely when denied.

## Step 2 — Guided practice

Request one scoped permission in a disposable app and test denial, revocation and retry.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Allowed operation succeeds and denial is recoverable.

**Negative:** Unnecessary broad storage permission or crash on denial fails.

## Qualification boundary

Native builds, WebView isolation and plugin permissions require a real device.

## Applied engineering walkthrough

Ask for a platform permission only at the point where a feature needs it. A denial is a normal application state, not an exceptional crash path. Prefer scoped system pickers when they satisfy the requirement; the operating system version and plugin determine whether broader access is even available. Network connectivity and authorization are separate from media access.

### Diagnose the concrete failure

Start with permission denied, invoke the relevant feature, and inspect whether it presents a usable alternative. Grant access, then revoke it through system settings and retry. The application should re-evaluate current permission rather than relying on an old in-memory flag.

### Independent exercise and evidence

Design a matrix for first request, denial, revocation and restricted selection. Record OS version, requested scope, user-visible behavior and whether access remains confined to the requested resource.
