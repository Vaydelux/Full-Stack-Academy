# Device UX and touch targets

> Instructor draft. Local models do not qualify native platforms, real providers or production deployments.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A phone user struggles to tap tightly spaced controls.

## Step 1 — Mental model

Touch targets, safe areas, orientation and text scaling must be tested on representative devices.

## Step 2 — Guided practice

Build a synthetic form and test portrait, landscape, enlarged text and keyboard overlap.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Controls remain reachable and labels readable.

**Negative:** Clipping, tiny targets or obscured submit fails.

Inspect the complementary `resumeQueue` teaching model. Extend its assertions when relevant; it is not an implementation of the full external technology.

node --test --test-name-pattern="24[.]04" examples/p7-platforms/labs.test.mjs

## Qualification boundary

Synthetic queue acknowledgement model only; physical touch, OS background behavior, push delivery and store acceptance require device tests.

## Applied engineering walkthrough

Responsive web layout does not guarantee usable native screens. Account for safe-area insets, system keyboards, touch interaction and OS text scaling. A layout must accommodate changing vertical space as well as width, rather than depending on one named phone breakpoint.

### Diagnose the concrete failure

Use a synthetic form, rotate the device, enlarge text and open the keyboard. Verify focus and the submit action remain reachable without clipping or overlapping system UI.

### Independent exercise and evidence

Record a device matrix with portrait, landscape, enlarged text and keyboard states. Include actual observations and test hardware navigation or assistive input where supported.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify actual device, provider and human accessibility evidence.

## Knowledge check

1. What is the invariant and trust boundary?
2. Which negative result falsifies an unsafe design?
3. Which real tool or reviewer must supply missing evidence?

**Assessment:** Record exact fixture input, expected and actual output, negative evidence and not-run checks. Do not substitute a design or model for a real acceptance result.
