# Deep links

> Instructor draft. Local models do not qualify native platforms, real providers or production deployments.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

A link opens an authenticated workspace screen.

## Step 1 — Mental model

Deep links need verified scheme/domain, validated parameters and authorization after routing.

## Step 2 — Guided practice

Test a known task link, unknown ID and foreign-tenant link in a disposable app.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** Authorized link opens intended screen.

**Negative:** Link payload bypassing authentication or tenant checks fails.

## Qualification boundary

Synthetic queue acknowledgement model only; physical touch, OS background behavior, push delivery and store acceptance require device tests.

## Applied engineering walkthrough

An application link is routing input, not an authorization grant. Validate scheme or associated domain, parse only known route shapes and bounded parameters, then enforce server authorization for protected resources. Avoid placing credentials and sensitive payloads in URLs.

### Diagnose the concrete failure

Open a known task link, invalid identifier and foreign-tenant link. Compare navigation and actual API outcomes; do not show cached private content before the authorization decision.

### Independent exercise and evidence

Test cold launch, running app and signed-out recovery. Record association verification, routing results and access decisions separately. Reject malformed encodings without forwarding them to native commands.
