# Conflict models and merge rules

> Instructor draft. Local models do not qualify native platforms, real providers or production deployments.

## Learning outcomes

Explain the engineering decision, reproduce or design the positive and negative experiment, and identify the remaining evidence.

## Context

Two devices edit the same task version.

## Step 1 — Mental model

Conflict policy must be explicit: reject stale version, merge defined fields, or reconcile with user input. Last-writer-wins can lose data.

## Step 2 — Guided practice

Apply version 0 edit then another version 0 edit; specify UI reconciliation for rejection.

Use synthetic data, a disposable environment and authorized accounts only. Record expected behavior before execution.

## Step 3 — Acceptance

**Positive:** The accepted version advances and conflict is surfaced.

**Negative:** Silently overwriting the first edit fails.

## Qualification boundary

In-memory sync model; actual SQLite persistence, durable queue, crash recovery and conflict reconciliation are not established.

## Applied engineering walkthrough

Carry a base revision with every edit and compare it atomically with the update. Last-writer-wins may silently erase another user's work. Merge only fields with a documented domain rule, and display unresolved conflicts without mutating the server again.

### Diagnose the concrete failure

Have two clients edit revision zero. Commit one, then send the second. Verify that the earlier change remains visible and that the rejection contains a usable recovery path.

### Independent exercise and evidence

Build a field-level decision table for titles, completion state and deletion. Record a second conflict occurring during reconciliation and require a new revision check.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve draft status and independently verify real persistence, network, device and reviewer evidence.
