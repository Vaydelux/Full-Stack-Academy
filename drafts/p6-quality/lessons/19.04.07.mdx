# CI test sharding

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A test suite is divided into several shards.

## Step 1 — Mental model

Aggregation verifies distinct expected shard identities and exact commit.

## Step 2 — Guided practice

Use matrixGate for shard-1, shard-2, shard-3; omit a result.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** All expected shards must pass on one commit.

**Negative:** Missing, duplicated or stale results fail.

## Qualification boundary

Metrics model uses supplied samples; no real load generation, chaos or database benchmark.

## Applied engineering walkthrough

Sharding reduces test wall time by distributing independent test cases, but release evidence requires every expected shard from the same candidate. Missing, duplicate or stale shard results cannot be treated as success. Shared fixtures must be isolated across workers.

### Diagnose the concrete failure

Feed matrixGate the three expected synthetic shard identities for one commit. Omit one, duplicate another and substitute a stale commit result; verify each incomplete set fails. Compare with the complete result set.

### Independent exercise and evidence

Design a shard inventory with deterministic partitioning, unique identity and artifact binding. Record execution times and aggregation outcomes without enabling any hosted CI workflow.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
