# VPS hardening

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A small VPS hosts a proxy, app and DB.

## Step 1 — Mental model

Minimize open services, use patched software, service accounts, backups and tested firewall.

## Step 2 — Guided practice

Evaluate topologyPolicy and sketch a disposable VM; list intended ports and verify from authorized local network.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Public edge separated from private data services.

**Negative:** Public DB or unverified restore fails; no live host changes.

## Qualification boundary

Synthetic topology policy; no OS/firewall/TLS/DNS/IaC or restore enforcement tested.

## Applied engineering walkthrough

A small VPS still needs a defined trust boundary. Expose only required ingress, restrict administrative access, keep runtime identities least-privileged and maintain patching and recovery procedures. A host firewall is one layer, not proof of database authorization or safe application code.

### Diagnose the concrete failure

Evaluate topologyPolicy for an edge, private app and private data service. Model an accidentally public database and verify rejection. In an authorized disposable VM, inspect listening services and effective network rules rather than probing unrelated hosts.

### Independent exercise and evidence

Prepare a VPS release checklist with patch baseline, administrative access, service roles, network policy, backups and restore verification. Record model outcomes separately from actual host configuration.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
