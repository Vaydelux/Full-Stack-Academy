# p95 and tail latency

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

Most requests are fast, but the tail is slow.

## Step 1 — Mental model

Nearest-rank p95 is the sorted sample at ceil(.95*n)-1; averages can hide outliers.

## Step 2 — Guided practice

Use 18 samples at 10ms and two at 1000ms; compare mean with p95.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** p95 is 1000ms and exceeds 100ms.

**Negative:** A mean-only gate can conceal a bad tail.

Run the complementary local module model and inspect `latencyReport` in `examples/p6-quality/labs.mjs`. Add an assertion for the relevant boundary. This command does not execute the external tools described above.

Metrics model uses supplied samples; no real load generation, chaos or database benchmark.

## Applied engineering walkthrough

A mean hides distribution shape. Tail percentiles describe the upper part of observed request latency and depend on the estimator and sample size. The supplied nearest-rank example contains eighteen ten-millisecond samples and two one-second samples; its p95 is one second.

### Diagnose the concrete failure

Run the model with the prescribed twenty samples and inspect the reported percentile. Compare a dataset with the same mean but a different tail. Check that the threshold fails even though many requests are fast.

### Independent exercise and evidence

Design latency reporting with sample count, estimator, p50, p95, p99 and error rate. Specify how timeouts enter the measurement. Record the observed results, not estimated production latency.
