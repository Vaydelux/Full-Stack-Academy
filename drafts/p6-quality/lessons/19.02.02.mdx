# Accessible queries

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

An icon-only Save button has a hidden text label.

## Step 1 — Mental model

Accessible role and name describe control semantics rather than classes.

## Step 2 — Guided practice

In a real DOM fixture query `getByRole('button', {name: 'Save'})`; change its CSS class and rerun.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** The query survives cosmetic change.

**Negative:** Removing the accessible name breaks the test.

Run the complementary local module model and inspect `latestRequest` in `examples/p6-quality/labs.mjs`. Add an assertion for the relevant boundary. This command does not execute the external tools described above.

```bash
node --test --test-name-pattern="19[.]02" examples/p6-quality/labs.test.mjs
```

## Qualification boundary

Plain JavaScript UI state model; installed React/Vitest/Testing Library/MSW and real browsers require separate tests.

## Applied engineering walkthrough

Accessible role and name queries express how a user identifies a control. A CSS selector targets implementation details and may survive even when a button loses its accessible name. A role query is not a complete accessibility audit; keyboard, focus and screen-reader behavior remain relevant.

### Diagnose the concrete failure

Find a synthetic Save button by its role and accessible name. Change only the styling and verify the test still passes. Remove the label in a disposable fixture and confirm the query fails for the intended reason.

### Independent exercise and evidence

Design queries for a labeled input, dialog and status message. Record their roles and names, then plan a manual screen-reader check for announcements and interaction.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.

## Knowledge check

1. Which public behavior or invariant is being protected?
2. Which negative case falsifies the unsafe implementation?
3. Which real runtime or manual check is still required?

**Assessment:** Submit the exact synthetic input, expected and observed outputs, a negative result, and the untested boundaries. Mark unavailable external checks not-run.
