# Schema migration tests

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A migration adds a non-null field to existing rows.

## Step 1 — Mental model

Migrations need representative old data, compatibility and explicit backfill.

## Step 2 — Guided practice

Apply the previous schema in a disposable DB, seed a legacy row, apply expansion and backfill, then validate constraints.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Legacy rows survive and new writes satisfy the schema.

**Negative:** Unresolved nulls prevent enforcement; never test on production.

## Qualification boundary

## Applied engineering walkthrough

Migration tests validate both fresh installation and upgrades from real prior schema shapes. A new NOT NULL constraint requires existing rows and concurrent writers to satisfy it. A clean install alone misses compatibility and backfill defects.

### Diagnose the concrete failure

Replay the prior migration history in a disposable database and insert a synthetic legacy row. Apply the proposed expansion and backfill, inspect data, then verify the final constraint. Test old and new application writes during the compatibility window.

### Independent exercise and evidence

Design upgrade acceptance with row-count reconciliation, reviewed SQL, constraint checks and a data-preserving failure strategy. Record migration versions and actual legacy data outcomes.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
