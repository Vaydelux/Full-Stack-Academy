# React component interaction

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

Two search requests finish out of order.

## Step 1 — Mental model

The newest request owns the current UI state; earlier results must be ignored.

## Step 2 — Guided practice

Start A and B in latestRequest, resolve B then A; translate into a real React interaction test.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** B remains displayed.

**Negative:** Stale A overwriting B fails.

## Qualification boundary

## Applied engineering walkthrough

Asynchronous React state must distinguish the latest intended request from earlier in-flight work. Cancellation can reduce unnecessary work, but a late response still needs protection when cancellation is ineffective. A component test should assert the visible result, not simply that two fetches occurred.

### Diagnose the concrete failure

Use explicit promise barriers for search A and B. Resolve B first and verify the new result appears, then resolve A and ensure it cannot replace B. Repeat with an older request rejecting after B succeeds.

### Independent exercise and evidence

Design a component test for rapid filter changes, unmount cleanup and stale error suppression. Record resolution order and final rendered content; the pure model is not React execution evidence.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
