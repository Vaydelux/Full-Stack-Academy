# Incident-ready releases

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A release elevates error rates off-hours.

## Step 1 — Mental model

Incident-ready delivery defines ownership, abort threshold, evidence and recovery path.

## Step 2 — Guided practice

Write a synthetic receipt containing artifact ID, threshold, reviewer, action; model failed health.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Decision maps to a predefined abort condition.

**Negative:** Missing owner or health evidence does not qualify release.

## Qualification boundary

Boolean release decision model, not deployment, migration, traffic switching or verified rollback.

## Applied engineering walkthrough

Incident-ready delivery defines the candidate, operational owner, measurable abort conditions and recovery procedure before exposure. An elevated error rate is actionable only when population, baseline and threshold are understood. A deployment record should preserve relevant observations without leaking secrets.

### Diagnose the concrete failure

Create a synthetic release receipt and simulate a failed health or smoke condition. Verify the decision follows the documented stop or rollback rule. Remove required approval and check the candidate remains held.

### Independent exercise and evidence

Design a release watch checklist with error rate, latency, queue age, owner and escalation. Record measured outcomes and decision timestamps during a real authorized rehearsal.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
