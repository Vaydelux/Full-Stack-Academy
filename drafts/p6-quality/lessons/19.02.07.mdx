# Keyboard and a11y checks

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A modal must work without a mouse.

## Step 1 — Mental model

Keyboard order, visible focus and restoration are behavioral requirements; manual assistive technology review remains necessary.

## Step 2 — Guided practice

Tab to the trigger, open with Enter, traverse controls, close with Escape, verify focus restoration in a real browser.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** The keyboard user can operate and dismiss the dialog.

**Negative:** Trapped focus or a mouse-only close action fails.

## Applied engineering walkthrough

Keyboard accessibility involves logical focus order, operable controls and meaningful focus restoration. A modal should contain focus while open without creating an inescapable trap. Escape and focus restoration need actual browser checks; automated rule scans alone are insufficient.

### Diagnose the concrete failure

In a real browser fixture, reach the trigger with Tab, open it, traverse controls with Tab and Shift+Tab, then dismiss with Escape. Verify focus returns to the triggering control and background interaction follows the dialog contract.

### Independent exercise and evidence

Design a manual and automated acceptance checklist for a modal at normal and enlarged zoom. Record keyboard sequence, active elements and announcement behavior using appropriate assistive technology.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
