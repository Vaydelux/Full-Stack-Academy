# Rolling deploys and downtime

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A rolling deployment has old and new app instances.

## Step 1 — Mental model

Versions need shared schema/API compatibility; readiness and draining control traffic.

## Step 2 — Guided practice

Draw two-instance replacement sequence and model a healthy then unhealthy candidate.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Compatible ready version advances.

**Negative:** Unready candidate should not receive traffic; real balancing still untested.

Run the complementary local module model and inspect `releaseDecision` in `examples/p6-quality/labs.mjs`. Add an assertion for the relevant boundary. This command does not execute the external tools described above.

```bash
node --test --test-name-pattern="20[.]03" examples/p6-quality/labs.test.mjs
```

## Qualification boundary

Boolean release decision model, not deployment, migration, traffic switching or verified rollback.

## Knowledge check

1. Which public behavior or invariant is being protected?
2. Which negative case falsifies the unsafe implementation?
3. Which real runtime or manual check is still required?

**Assessment:** Submit the exact synthetic input, expected and observed outputs, a negative result, and the untested boundaries. Mark unavailable external checks not-run.
