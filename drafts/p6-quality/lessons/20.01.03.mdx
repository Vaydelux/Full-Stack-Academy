# Compose services and health checks

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

An API boots before the database is ready.

## Step 1 — Mental model

Startup order is not readiness; health checks and bounded retries are separate.

## Step 2 — Guided practice

Require a healthcheck in containerPolicy; in real Compose test a service_healthy dependency with a failed DB.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** API becomes usable only after DB is healthy.

**Negative:** An unhealthy dependency cannot be treated as ready.

## Applied engineering walkthrough

Compose expresses local service topology, but a started container is not necessarily ready to serve. Health checks should verify a meaningful dependency or service condition with bounded timing. Startup ordering does not eliminate the need for runtime reconnection and graceful degradation.

### Diagnose the concrete failure

In an isolated stack, start the application with its database healthy and inspect a functional query. Repeat with a deliberately unavailable test database and verify readiness remains false. Check recovery after the dependency returns without replacing production services.

### Independent exercise and evidence

Design separate liveness and readiness probes and an application retry budget. Record actual service health transitions, query results and cleanup; the policy fixture checks configuration only.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
