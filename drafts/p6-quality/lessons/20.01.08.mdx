# Lab local stack

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A developer needs an isolated API/database stack.

## Step 1 — Mental model

A safe local stack combines reviewed images, non-root identity, health checks and network isolation.

## Step 2 — Guided practice

## Step 3 — Acceptance

**Positive:** Models pass and real health/isolation checks remain required.

**Negative:** Privileged execution, exposed DB or Docker socket fails the policy.

## Qualification boundary

Declarative policy model; no Docker engine, image build, scan or real network isolation executed.

## Applied engineering walkthrough

An isolated local stack combines reproducible images, dependency health, persistence, least privilege and explicit network boundaries. The local policy model tests declared requirements; it cannot inspect running containers or verify backup recovery. Use synthetic fixtures and a dedicated project namespace.

### Diagnose the concrete failure

Evaluate containerPolicy and topologyPolicy for the intended architecture, then create the corresponding isolated stack when Docker is available. Verify application health, private database connectivity and persistent test data. Test unsafe configuration in the model only.

### Independent exercise and evidence

Prepare a stack acceptance record listing images, ports, roles, health, mounts and cleanup. Record each actual Docker test separately and mark unavailable infrastructure not-run.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
