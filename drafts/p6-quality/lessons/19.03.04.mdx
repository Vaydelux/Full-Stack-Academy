# Test database transactions

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A DB test modifies rows before failing.

## Step 1 — Mental model

Rollback isolates changes only on the same transaction and connection.

## Step 2 — Guided practice

In a disposable PostgreSQL DB seed data, BEGIN, update then force failure, ROLLBACK and query via a fresh connection.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Baseline rows remain unchanged.

**Negative:** Separately committed updates escape rollback and must be detected.

## Qualification boundary

## Applied engineering walkthrough

Rollback-based test isolation works only for changes participating in the same transaction. Another pooled connection may commit independently, and background jobs or external calls are outside the rollback boundary. Parallel tests need separate namespaces or an explicitly coordinated strategy.

### Diagnose the concrete failure

On a dedicated PostgreSQL database, capture baseline rows, begin a transaction, update and force an error, then roll back. Query using a fresh connection and compare baseline state. Separately demonstrate why an independently committed test write survives rollback.

### Independent exercise and evidence

Design disposable-schema or database-per-worker isolation with deterministic fixtures and guaranteed cleanup. Record connected database identity and before/after rows; never point a destructive test at production.

**Evidence boundary:** These are practice instructions, not recorded test results. Preserve the existing model, specification and draft flag; external runtime qualification remains independent.
