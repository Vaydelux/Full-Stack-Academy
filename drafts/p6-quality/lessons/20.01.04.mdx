# Bind mounts vs volumes

> Unpublished instructor manuscript. A green model test is not real runtime acceptance.

## Learning outcomes

Explain the design rule, reproduce or specify an observable positive and negative experiment, and distinguish the model from external evidence.

## Context

A DB container is recreated during development.

## Step 1 — Mental model

Named volumes persist independently; bind mounts map host paths and permissions.

## Step 2 — Guided practice

In disposable Docker seed a named volume, recreate without removing it and test a read-only config mount.

Predict the outcome before running the experiment. Use only synthetic data and disposable fixtures.

## Step 3 — Acceptance

**Positive:** Synthetic data survives recreation.

**Negative:** Writes to read-only config fail; do not remove valuable volumes.

## Applied engineering walkthrough

Bind mounts expose a host path to a container, whereas named volumes are managed storage with an independent lifecycle. Container recreation need not remove a named volume, but volume deletion can destroy data. Mounts can obscure files already present in an image.

### Diagnose the concrete failure

Seed synthetic data in a dedicated named volume, recreate the disposable container without deleting the volume, and verify the data remains. Mount a fake configuration read-only and verify the intended process cannot write it. Inspect only the designated test paths.

### Independent exercise and evidence

Design an explicit persistence and backup plan for database data and read-only configuration. Record mount type, ownership and retention behavior; avoid destructive cleanup of unrelated volumes.
