# Lab recover failed webhook

> Unpublished source lesson. This manuscript and its example are educational, not production-qualified or a deployable service.

## Learning outcomes

Explain the underlying correctness problem, identify the unsafe assumption, select an operationally defensible alternative, and reproduce a positive and negative test on synthetic data.

## Context

A webhook provider recovers after several failures.

The objective is a predictable data flow, not adding Redis or BullMQ simply because they are popular. Decide which state is authoritative, which work can be repeated, and which failure modes require human recovery.

## Step 1 — Build the mental model

Preserve stable event and idempotency IDs during reviewed redrive and record terminal outcomes.

**Draw the boundary:** Describe the producer or HTTP caller, trusted tenant context, authoritative store, cache or queue, worker, and external side effect. Mark everything that could become stale or be delivered twice.

## Step 2 — Reproduce the unsafe behavior

Operators rerun a failed webhook with a new ID, creating duplicate external effects.

**Guided task:** Make a prediction before running the fixture. Record the input, the unsafe observed outcome, and why the outcome violates the intended freshness, isolation, delivery, or recovery invariant. Never use real customer data.

## Step 3 — Implement and verify the correction

Preserve stable event and idempotency IDs during reviewed redrive and record terminal outcomes.

**Acceptance scenario:** Redrive an exhausted outbox event and assert a second delivery cannot override a previous completion.

Run the relevant offline teaching suite from the repository root:

```bash
node --test examples/p5-cache-jobs/outbox.test.mjs
```

In the test notes, separate what the in-memory fixture genuinely observed from Redis/BullMQ behavior that still needs a live integration environment.

## Misconception

The simulator demonstrates state transitions, not external webhook signatures or network security.

## Applied engineering walkthrough

Recovering a failed webhook requires retaining its logical event identity. Redrive is a controlled new attempt of the same operation, not a new business event. A completed event should not be reopened by a stale or duplicate delivery. External effects need durable deduplication beyond queue state.

### Diagnose the concrete failure

Drive a synthetic event to terminal failure, correct the stubbed cause and redrive it. Verify successful completion and reject a repeated completion or stale claim. Compare event identity before and after the recovery.

### Independent exercise and evidence

Write an operator handoff with original event ID, attempts, failure category, remediation and final effect count. Include a crash-after-effect scenario and record which live provider or database checks remain missing.

**Qualification boundary:** These are practice instructions, not recorded results. Preserve the existing lab and publication status; in-memory tests do not qualify live Redis or BullMQ behavior.

## Knowledge check

1. What is authoritative in this scenario, and what state is derived or replayable?
2. What precise sequence of requests or job deliveries would expose the unsafe design?
3. Which two observations distinguish success from a silent failure?
4. What remains unverified until a real Redis/BullMQ integration or external provider is exercised?

**Instructor rubric:** Accept only a traced scenario, corrected invariant, reproducible success and failure case, and a clear statement of the limits of simulation.
