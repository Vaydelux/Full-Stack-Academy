# Multi-region latency

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

Users in two regions access shared data.

## Step 1 — Mental model

Replication and request routing trade latency against consistency and recovery; define write authority.

## Step 2 — Guided practice

Draw region A/B paths and simulate network delay, stale read and failover.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Applied engineering walkthrough

Multi-region deployment adds network latency and independent failure domains. Define write authority, replication lag and failover behavior explicitly. Two regions accepting writes without a coordination or conflict strategy can violate invariants. A local model cannot establish real regional latency.

### Diagnose the concrete failure

Draw two regional request paths and simulate a delayed replica, unavailable primary and promotion decision. Identify which reads may be stale and which operations must reach the authoritative writer. Do not assume automatic failover is safe.

### Independent exercise and evidence

Design a regional recovery record including consistency, write authority, traffic cutover and recovery objectives. Record actual latency and failover evidence only from an authorized deployment rehearsal.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual distributed runtime qualification remains independent.
