# Clean architecture tradeoffs

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A simple CRUD app grows multiple layers of mapping.

## Step 1 — Mental model

Clean architecture prioritizes dependency direction and replaceable boundaries; extra layers have maintenance cost.

## Step 2 — Guided practice

Compare direct CRUD module versus domain-rich module and justify each boundary using change scenarios.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Chosen design solves actual coupling and test needs.

**Negative:** Adding abstractions with no change or testing benefit is unjustified.

## Applied engineering walkthrough

Clean architecture can improve change isolation, but additional layers introduce mapping, maintenance and debugging costs. A straightforward CRUD feature may need only a small module and explicit DTOs; complex domain behavior benefits more from isolated policies. Choose boundaries based on real coupling and test needs.

### Diagnose the concrete failure

Compare a synthetic settings CRUD feature with an order reservation feature requiring invariants and external effects. Identify changes that justify a separate domain model in the second case and why the first may not need the same layers.

### Independent exercise and evidence

Write a decision record comparing direct feature modules and layered architecture. Include failure modes, test costs and measurable triggers for adding abstraction.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual source dependency and runtime qualification remain independent.

## Knowledge check

1. Which invariant or operational measurement determines success?
2. What failure case disproves the unsafe design?
3. Which evidence remains missing before this can be applied to a production service?

**Assessment:** Submit input, expected/observed outcomes, a meaningful negative result and the unverified external boundaries. Mark unavailable tests not-run.
