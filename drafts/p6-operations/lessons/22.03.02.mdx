# Multi-tier caching

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

An app has browser, CDN, process and Redis caches.

## Step 1 — Mental model

Each cache tier has distinct ownership, scope, TTL and failure mode; name authoritative state.

## Step 2 — Guided practice

Map keys and TTL per tier; simulate origin update and process-cache miss.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Authoritative read remains correct despite tier misses.

**Negative:** A private value in shared public cache fails.

## Qualification boundary

## Applied engineering walkthrough

Multiple cache tiers trade latency and origin load against freshness and memory. Each tier needs compatible key scope, expiry and invalidation. A process cache can retain stale data after Redis changes, and private representations must not enter shared public namespaces.

### Diagnose the concrete failure

Map browser, edge, process and Redis tiers for a synthetic catalog read. Simulate a miss at each tier and an authoritative update. Trace which tier supplies the response and which invalidations remain necessary.

### Independent exercise and evidence

Design a tier-by-tier freshness contract with tenant and representation scope, fallback load and observability. Record returned versions and origin calls for matched scenarios.

**Evidence boundary:** These are practice instructions, not recorded capacity or benchmark results. Preserve the existing specification, model and unpublished status. Actual deployment measurements remain independent.
