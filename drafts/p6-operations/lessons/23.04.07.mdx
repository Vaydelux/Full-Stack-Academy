# Microservice extraction criteria

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A modular monolith has one expensive workload.

## Step 1 — Mental model

Extract a service only when independent scaling, failure isolation or ownership outweighs network/operational cost.

## Step 2 — Guided practice

Write an ADR comparing module optimization, worker extraction and service extraction using observed bottlenecks.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Applied engineering walkthrough

Service extraction is justified by concrete needs such as independent scaling, isolation, ownership or deployment cadence. It adds network contracts, observability, distributed failures and operational overhead. Optimizing a module or extracting a worker can solve a bottleneck at lower complexity.

### Diagnose the concrete failure

Compare a synthetic modular monolith with a separately scaled worker and an extracted service. Identify the expensive workload and which change addresses it without duplicating business ownership. Document the new failure boundaries for each option.

### Independent exercise and evidence

Write an ADR with measured extraction triggers, migration stages and compatibility risks. Record which measurements are available and which remain hypotheses; avoid premature decomposition.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual distributed runtime qualification remains independent.
