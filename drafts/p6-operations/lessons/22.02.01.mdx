# Profiling Node CPU and heap

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A Node server becomes CPU-bound under workload.

## Step 1 — Mental model

CPU profiling identifies hot stacks; heap snapshots describe retained objects and may contain secrets or pause the process.

## Step 2 — Guided practice

Profile a disposable CPU-heavy loop and compare before/after change under fixed workload; inspect sanitized heap data separately.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Hot function is measurable and improvement is repeatable.

**Negative:** A single unrepresentative timing or real private heap dump fails review.

Inspect the complementary `requestProfile` model in `examples/p6-operations/labs.mjs` and extend its assertions where relevant. The command below does not execute the external tools discussed in this topic.

## Qualification boundary

Synthetic latency sample analysis only; actual CPU/heap profiles, Fastify comparison, query plans and HTTP behavior need real runtimes.

## Applied engineering walkthrough

CPU profiles identify where sampled execution time is spent; heap snapshots describe retained objects and references. A high allocation rate is not automatically a leak. Compare profiles under equivalent workloads and observe retained memory after repeated operations and appropriate garbage collection.

### Diagnose the concrete failure

Profile a bounded synthetic CPU-heavy handler using Node's supported tools. Inspect its hottest function, make one isolated improvement and repeat the workload. Use synthetic objects for heap inspection; never collect real private payloads.

### Independent exercise and evidence

Design a reproducible profiling receipt with runtime version, sample duration, workload, CPU and memory observations. Record measured changes and independent correctness checks.

**Evidence boundary:** These are practice instructions, not recorded benchmark results. Preserve the existing specification, model and unpublished status. Actual API and database measurements remain independent.
