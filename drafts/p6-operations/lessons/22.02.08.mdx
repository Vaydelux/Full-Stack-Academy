# Lab reduce p95 latency

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A service must reduce p95 without hiding errors.

## Step 1 — Mental model

Measure queue time, execution and total per request; percentiles are not additive across distributions.

## Step 2 — Guided practice

Run requestProfile on matched synthetic pairs; then benchmark a real disposable API before and after one change.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Total p95 computed from per-request sums; errors reported separately.

**Negative:** Adding queue p95 and work p95 or dropping failures is invalid.

Inspect the complementary `requestProfile` model in `examples/p6-operations/labs.mjs` and extend its assertions where relevant. The command below does not execute the external tools discussed in this topic.

```bash
node --test --test-name-pattern="22[.]02" examples/p6-operations/labs.test.mjs
```

## Qualification boundary

Synthetic latency sample analysis only; actual CPU/heap profiles, Fastify comparison, query plans and HTTP behavior need real runtimes.

## Applied engineering walkthrough

End-to-end latency is the sum of components for each request. Percentiles are computed on the resulting per-request totals, not by adding percentiles of independently distributed components. Retain errors and timeouts in the defined reporting population to avoid hiding degraded service.

### Diagnose the concrete failure

Run requestProfile using paired queue and execution durations and inspect total p95. Compare with a misleading sum of component p95 values. Benchmark one controlled change in a disposable API and record failures separately.

### Independent exercise and evidence

Prepare a measurement record containing paired observations, estimator, workload, baseline and changed results. Require correctness and error-rate gates before accepting latency improvements.

**Evidence boundary:** These are practice instructions, not recorded benchmark results. Preserve the existing specification, model and unpublished status. Actual API and database measurements remain independent.
