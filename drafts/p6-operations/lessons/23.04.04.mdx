# Message brokers NATS Kafka

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A team chooses NATS or Kafka for event transport.

## Step 1 — Mental model

Brokers differ in durability, retention, ordering scope and consumption models; compare configured guarantees, not brands.

## Step 2 — Guided practice

Define workload retention, replay, ordering and failure recovery requirements; test on isolated real broker if available.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Chosen configuration meets the stated guarantees with evidence.

## Applied engineering walkthrough

NATS Core, JetStream and Kafka have different persistence, replay and acknowledgement mechanisms. Ordering depends on the stream or partition and consumer configuration, rather than being universally global. Select a broker using actual workload requirements and operational capacity.

### Diagnose the concrete failure

Write a synthetic workload requiring retained events, keyed ordering and restart recovery. Compare relevant broker modes, then plan an isolated test with duplicate delivery and consumer restart. Do not infer durable replay from a basic publish-subscribe demonstration.

### Independent exercise and evidence

Prepare a broker decision matrix covering retention, replay, ordering scope, backpressure, delivery guarantees and ownership. Record exact tested configuration and observed outcomes if the runtime is available.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual distributed runtime qualification remains independent.
