# Dependency inversion

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

Domain logic imports a concrete ORM client.

## Step 1 — Mental model

Dependency inversion makes higher-level policy depend on an abstraction it owns; infrastructure implements it.

## Step 2 — Guided practice

Use boundaryViolations to forbid domain-to-ORM and allow usecase-to-port; implement a fake port.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Negative:** Concrete ORM dependency in domain fails.

## Applied engineering walkthrough

Dependency inversion makes high-level business policies independent of low-level implementation details. A port expresses a capability needed by the application, while the composition root supplies its implementation. A TypeScript interface alone does not enforce source dependency direction or correct runtime wiring.

### Diagnose the concrete failure

Run boundaryViolations with an allowed use-case-to-port edge and a prohibited domain-to-ORM import. Verify the reported violation, then replace the dependency with the intended port. Exercise the domain using a synthetic fake.

### Independent exercise and evidence

Design an inventory repository port with explicit failure behavior and a composition-root binding. Record dependency direction and fake versus real adapter evidence separately.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual source dependency and runtime qualification remain independent.
