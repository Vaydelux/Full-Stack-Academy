# Lab performance budget

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A team needs a repeatable frontend performance gate.

## Step 1 — Mental model

Set explicit metric and transfer budgets with controlled conditions; distinguish lab and field evidence.

## Step 2 — Guided practice

Run webBudget, add a one-byte regression and one missing metric; then plan browser runs on fixed fixtures.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** All required metrics within budget passes the model.

**Negative:** Missing or exceeded metrics fail; synthetic values are not browser proof.

Inspect the complementary `webBudget` model in `examples/p6-operations/labs.mjs` and extend its assertions where relevant. The command below does not execute the external tools discussed in this topic.

```bash
node --test --test-name-pattern="22[.]01" examples/p6-operations/labs.test.mjs
```

## Qualification boundary

Synthetic measured-value budget only; actual Core Web Vitals, browser profiles and real-user metrics are unexecuted.

## Applied engineering walkthrough

A performance budget is a versioned acceptance contract. Each required metric has a unit, threshold and measurement method, and missing values must fail rather than default to zero. A model tests gate decisions but does not collect browser evidence.

### Diagnose the concrete failure

Run webBudget with a complete within-budget fixture, increase bytes by one above the limit and remove one required metric. Check both negative cases. Plan matched real browser trials against a stable baseline.

### Independent exercise and evidence

Write a budget receipt containing commit, environment, workload, metrics and pass/fail decisions. Include functional and accessibility regressions as independent release gates.

**Evidence boundary:** These are practice instructions, not recorded benchmark results. Preserve the existing specification, model and unpublished status. Actual browser measurement and qualification remain independent.

## Knowledge check

1. Which invariant or operational measurement determines success?
2. What failure case disproves the unsafe design?
3. Which evidence remains missing before this can be applied to a production service?

**Assessment:** Submit input, expected/observed outcomes, a meaningful negative result and the unverified external boundaries. Mark unavailable tests not-run.
