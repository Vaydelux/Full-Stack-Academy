# Ports and adapters

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A use case must support HTTP and CLI entry points.

## Step 1 — Mental model

Ports define required/provided capabilities; adapters translate outside protocols into use-case inputs.

## Step 2 — Guided practice

Design submit-order port and two adapters; exercise same invariant through both.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Both adapters use the same application contract.

**Negative:** Duplicated business rule or adapter bypass fails.

## Applied engineering walkthrough

Ports represent application capabilities, and adapters translate transport or infrastructure contracts to those capabilities. Inbound HTTP and CLI adapters should invoke the same application rule rather than duplicate it. Transport validation and domain invariants remain distinct.

### Diagnose the concrete failure

Define a synthetic order command and invoke the same application operation through two proposed adapters. Compare accepted and denied outcomes for identical business input. Confirm a malformed transport request fails before domain execution.

### Independent exercise and evidence

Design a second inbound adapter for a background job with trusted actor context. Record the shared contract and transport-specific validation, keeping actual adapter integration separate.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual source dependency and runtime qualification remain independent.
