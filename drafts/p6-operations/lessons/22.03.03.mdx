# Cache consistency

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

An order update races with cache invalidation.

## Step 1 — Mental model

Cache-aside can expose stale data; version checks and invalidation after commit reduce races, not eliminate every stale read.

## Step 2 — Guided practice

Design versioned cached row with versions 2 and 3; simulate delayed invalidation and stale refill.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Version 2 cannot replace known version 3.

**Negative:** Late stale write restoring outdated state fails.

## Applied engineering walkthrough

Cache consistency depends on ordering between committed writes, invalidation and asynchronous refill. Version-aware writes prevent a known older version from replacing a newer one, but version comparisons must be atomic at the relevant boundary. TTL only limits some stale-state windows.

### Diagnose the concrete failure

Use a controlled sequence where version three is committed and an earlier loader returns version two later. Verify the intended fencing design rejects the old value. Test delayed invalidation and cache outage independently.

### Independent exercise and evidence

Design an invalidation/outbox strategy with monotonic revisions and bounded recovery. Record authoritative and cached revisions, completion order and allowed staleness; qualify real distributed races separately.
