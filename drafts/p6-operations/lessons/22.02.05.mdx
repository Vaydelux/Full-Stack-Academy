# HTTP caching ETags

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

Clients repeatedly fetch an unchanged resource.

## Step 1 — Mental model

ETag validators allow conditional requests; cache identity includes representation and auth policy.

## Step 2 — Guided practice

Use a local HTTP fixture with an ETag; send If-None-Match and then mutate resource.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Unchanged response returns 304 and changed representation returns 200.

**Negative:** A private response cached across users or stale validator fails.

## Applied engineering walkthrough

An ETag identifies a representation version under an explicit validator contract. For a matching conditional GET, a 304 response carries no representation body; changed data should produce a new validator. Cache-Control and Vary govern reuse, and private data must not become shared across users.

### Diagnose the concrete failure

Use an isolated HTTP fixture to read a resource and capture its ETag. Send If-None-Match, verify 304 and an empty body, mutate the resource and verify 200 with a new representation. Test private scope separately.

### Independent exercise and evidence

Design cache headers and validators for public catalog and authenticated task endpoints. Record status, validator changes and cache isolation; do not reuse a write precondition test as GET evidence.

**Evidence boundary:** These are practice instructions, not recorded benchmark results. Preserve the existing specification, model and unpublished status. Actual API and database measurements remain independent.
