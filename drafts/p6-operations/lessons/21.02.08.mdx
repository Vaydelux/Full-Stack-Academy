# Lab fault injection

> Unpublished instructor manuscript. Local model tests are supplemental, not external runtime qualification.

## Learning outcomes

Explain the relevant engineering tradeoff, define a measurable experiment and recognize the boundary of the available evidence.

## Context

A team rehearses a dependency failure.

## Step 1 — Mental model

Fault injection begins with a hypothesis, bounded blast radius, abort condition and recovery measurement.

## Step 2 — Guided practice

Inject deterministic failures into an isolated handler; calculate budget, remove fault, and compare recovery samples.

Use synthetic data and a disposable authorized environment. Record the expected result before the experiment.

## Step 3 — Acceptance

**Positive:** Measured failure and recovery match the defined target.

**Negative:** Unbounded fault injection or missing recovery evidence fails.

Inspect the complementary `errorBudget` model in `examples/p6-operations/labs.mjs` and extend its assertions where relevant. The command below does not execute the external tools discussed in this topic.

```bash
node --test --test-name-pattern="21[.]02" examples/p6-operations/labs.test.mjs
```

## Qualification boundary

Synthetic error-budget arithmetic only; real probes, alerts, concurrency and fault recovery require actual isolated services.

## Applied engineering walkthrough

A fault experiment states a hypothesis, scope, impact limits and recovery condition before injecting failure. Synthetic budget arithmetic is useful but cannot demonstrate real resilience. Measure baseline, failure and recovery using comparable observations.

### Diagnose the concrete failure

In an isolated handler, inject a bounded deterministic fault sequence and collect success and failure counts. Remove the fault, repeat the workload and compare recovery to the stated target. Record retries and stop conditions.

### Independent exercise and evidence

Prepare a fault rehearsal record with exact environment, affected dependency, baseline, observed failure and recovery evidence. Mark untested external services not-run.

**Evidence boundary:** These are practice instructions, not recorded results. Preserve the existing specification, model and unpublished status. Actual resilience and runtime qualification remain independent.

## Knowledge check

1. Which invariant or operational measurement determines success?
2. What failure case disproves the unsafe design?
3. Which evidence remains missing before this can be applied to a production service?

**Assessment:** Submit input, expected/observed outcomes, a meaningful negative result and the unverified external boundaries. Mark unavailable tests not-run.
