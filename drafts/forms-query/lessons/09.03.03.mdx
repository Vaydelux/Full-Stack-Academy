## The problem we're solving

A newly created task shows a green success toast, but it does not appear in any filtered list because the POST mutation was not followed by a cache invalidation.

**Broken behavior in the starter:** The starter sends a POST without invalidating task-list queries and has no idempotency contract.

## Build the mental model

Queries describe remote reads; mutations perform writes. Invalidate the relevant query namespace when writes succeed, then let refetch reconcile client state with server truth.

**Predict before coding:** After a valid 201 POST, the task should appear in the refreshed todo list even when that list is separately cached from done/doing views.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. No compatible npm dependency lock or browser qualification has been completed, so this draft cannot be marked published.

<LessonStep number={2} title="Implement the correct TanStack Query behavior" file="drafts/forms-query/labs/mutation-invalidation/solution.tsx" expected="After a valid 201 POST, the task should appear in the refreshed todo list even when that list is separately cached from done/doing views.">

```tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';
export function CreateTask(){
 const client=useQueryClient();
 const create=useMutation({
  mutationFn:async({title,key}:{title:string;key:string})=>{
   const response=await fetch('/api/tasks',{method:'POST',headers:{
    'content-type':'application/json','idempotency-key':key
   },body:JSON.stringify({title,priority:'normal'})});
   if(!response.ok)throw new Error('HTTP '+response.status);
   return response.json();
  },
  retry:false,
  onSuccess:async()=>{await client.invalidateQueries({queryKey:['tasks']});},
 });
 return <button type="button" disabled={create.isPending}
  onClick={()=>create.mutate({title:'Practice cache invalidation',key:crypto.randomUUID()})}>
  {create.isPending?'Saving…':'Create task'}
 </button>;
}
```

**What changed:** Queries describe remote reads; mutations perform writes. Invalidate the relevant query namespace when writes succeed, then let refetch reconcile client state with server truth.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter sends a POST without invalidating task-list queries and has no idempotency contract.
2. **Diagnose:** Trace the query key, cancellation boundary, remote response, cache update and invalidation.
3. **Repair:** Use useMutation for writes, attach one logical idempotency key, and invalidate all affected query views after confirmed success.
4. **Regression:** Create with a valid key; verify one 201, then a GET refreshes the matching list. A 422 must never produce an invalidation-based success state.
5. **Security and operations:** A retry that regenerates the idempotency key may produce duplicate tasks. Avoid retrying unauthorized or validation failures automatically.
