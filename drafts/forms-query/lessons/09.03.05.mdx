## The problem we're solving

A list appends pages using numeric offset. Another task is created between reads, shifting positions and causing duplicated or skipped rows; the server already offers opaque revision-bound cursors.

**Broken behavior in the starter:** The starter guesses numeric offsets and never uses nextCursor or signal cancellation.

## Build the mental model

An infinite query stores a sequence of pages plus page parameters. Use the API's opaque nextCursor; never reconstruct it or mix pages from different filters or revisions.

**Predict before coding:** Load More appends exactly the next page. After a 409 stale-cursor response, restart the list rather than appending incompatible results.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. The nested React npm lockfile and local Chrome/SSR tests were reported as passing on November 20, 2026. Publication, canonical academy lab registration and human accessibility review remain separate outstanding gates.

<LessonStep number={2} title="Implement the correct TanStack Query behavior" file="drafts/forms-query/labs/infinite-queries/solution.tsx" expected="Load More appends exactly the next page. After a 409 stale-cursor response, restart the list rather than appending incompatible results.">

```tsx
import { useInfiniteQuery, useQueryClient } from '@tanstack/react-query';
type Page={items:{id:string;title:string}[];nextCursor:string|null};
export function Pager(){
 const client=useQueryClient();
 const key=['tasks',{status:'todo',mode:'infinite'}] as const;
 const pages=useInfiniteQuery({
  queryKey:key,
  initialPageParam:null as string|null,
  queryFn:async({pageParam,signal})=>{
   const params=new URLSearchParams({status:'todo',limit:'10'});
   if(pageParam)params.set('cursor',pageParam);
   const response=await fetch('/api/tasks?'+params,{signal});
   if(!response.ok)throw new Error('HTTP '+response.status);
   return response.json() as Promise<Page>;
  },
  getNextPageParam:last=>last.nextCursor,
  maxPages:10,
  retry:(count,error)=>count<1&&!/^HTTP 4\d\d$/.test(String(error.message)),
 });
 if(pages.isPending)return <p role="status">Loading pages…</p>;
 if(pages.isError)return <div role="alert">Pagination failed.
  <button type="button" onClick={()=>{void client.resetQueries({queryKey:key,exact:true});}}>Restart pages</button></div>;
 return <div><ul>{pages.data.pages.flatMap(p=>p.items).map(t=><li key={t.id}>{t.title}</li>)}</ul>
  <button type="button" disabled={!pages.hasNextPage||pages.isFetchingNextPage} onClick={()=>{void pages.fetchNextPage();}}>Load more</button></div>;
}
```

**What changed:** An infinite query stores a sequence of pages plus page parameters. Use the API's opaque nextCursor; never reconstruct it or mix pages from different filters or revisions.

</LessonStep>
