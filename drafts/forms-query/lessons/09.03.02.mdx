## The problem we're solving

A learner sets staleTime to infinity and expects a fresh server list after a new task was created in another tab. Another sets gcTime to zero expecting it to prevent stale reads, but it only causes cache eviction.

**Broken behavior in the starter:** The starter sets infinite freshness and zero cache lifetime, conflating staleness and garbage collection.

## Build the mental model

staleTime determines when cached data is considered stale; gcTime determines how long an unused query remains cached. Neither makes server data immutable.

**Predict before coding:** A ten-second staleTime may prevent an immediate refetch; after the freshness window, refocus or remount can revalidate. gcTime starts after a query becomes unused.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. <LessonStep number={2} title="Implement the correct TanStack Query behavior" file="drafts/forms-query/labs/stale-garbage/solution.tsx" expected="A ten-second staleTime may prevent an immediate refetch; after the freshness window, refocus or remount can revalidate. gcTime starts after a query becomes unused.">

```tsx
import { useQuery } from '@tanstack/react-query';
export function Tasks(){
 const query=useQuery({
  queryKey:['tasks',{limit:10}],
  queryFn:async({signal})=>{
   const response=await fetch('/api/tasks?limit=10',{signal});
   if(!response.ok)throw new Error('HTTP '+response.status);
   return response.json() as Promise<{items:{id:string}[]}>;
  },
  staleTime:10_000,
  gcTime:5*60_000,
  refetchOnWindowFocus:true,
 });
 if(query.isPending)return <p>Loading…</p>;
 if(query.isError)return <p role="alert">Server tasks unavailable.</p>;
 return <output>{query.data.items.length} task(s)</output>;
}
```

**What changed:** staleTime determines when cached data is considered stale; gcTime determines how long an unused query remains cached. Neither makes server data immutable.

</LessonStep>

## Production decision guide: freshness and residency are different clocks

`staleTime` describes how long a cached response is considered fresh. `gcTime` describes how long an *inactive* query can remain in cache before collection. An active query does not disappear merely because an inactive garbage-collection timer would have elapsed. A stale response may be displayed immediately while a background refetch takes place, depending on the query configuration.

| Setting or event | What it controls | Typical misconception |
| --- | --- | --- |
| Short `staleTime` | When data becomes eligible for refetch | Stale means data was removed |
| Longer `gcTime` | How long unused entries persist | GC makes active queries refresh |
| Window refocus | Can refetch stale active data | Focus always causes network traffic |
| New observer on fresh data | May reuse cached value | Every mount must fetch again |

**Independent exercise:** Read twice immediately, refocus at two seconds and again after eleven seconds. Explain which reads should display cached data and when a request is expected. Unmount the query and predict whether its cache survives the configured inactive interval.

**Risk boundary:** Cached data is not proof that a user remains authorized. A 401/403 or logout flow must invalidate sensitive cached views and avoid leaking the previous user's records into another session. Choose timeouts based on data volatility, not merely perceived speed.

## Applied debugging clinic

Mount a list with a known staleTime and gcTime. Record when cached data is visible, when it becomes stale, when a remount refetches, and when the inactive cache is eligible for collection. Keep active and inactive intervals separate; a stale active query is not garbage collected solely because it is stale.

**Evidence to record:** query identity, request outcome, cache state before and after the action, and the recovery decision. Separate observed network behavior from what the UI displays. Re-run the original failing interaction after the repair.
