## The problem we're solving

A learner sets staleTime to infinity and expects a fresh server list after a new task was created in another tab. Another sets gcTime to zero expecting it to prevent stale reads, but it only causes cache eviction.

**Broken behavior in the starter:** The starter sets infinite freshness and zero cache lifetime, conflating staleness and garbage collection.

## Build the mental model

staleTime determines when cached data is considered stale; gcTime determines how long an unused query remains cached. Neither makes server data immutable.

**Predict before coding:** A ten-second staleTime may prevent an immediate refetch; after the freshness window, refocus or remount can revalidate. gcTime starts after a query becomes unused.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. No compatible npm dependency lock or browser qualification has been completed, so this draft cannot be marked published.

<LessonStep number={2} title="Implement the correct TanStack Query behavior" file="drafts/forms-query/labs/stale-garbage/solution.tsx" expected="A ten-second staleTime may prevent an immediate refetch; after the freshness window, refocus or remount can revalidate. gcTime starts after a query becomes unused.">

```tsx
import { useQuery } from '@tanstack/react-query';
export function Tasks(){
 const query=useQuery({
  queryKey:['tasks',{limit:10}],
  queryFn:async({signal})=>{
   const response=await fetch('/api/tasks?limit=10',{signal});
   if(!response.ok)throw new Error('HTTP '+response.status);
   return response.json() as Promise<{items:{id:string}[]}>;
  },
  staleTime:10_000,
  gcTime:5*60_000,
  refetchOnWindowFocus:true,
 });
 if(query.isPending)return <p>Loading…</p>;
 if(query.isError)return <p role="alert">Server tasks unavailable.</p>;
 return <output>{query.data.items.length} task(s)</output>;
}
```

**What changed:** staleTime determines when cached data is considered stale; gcTime determines how long an unused query remains cached. Neither makes server data immutable.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter sets infinite freshness and zero cache lifetime, conflating staleness and garbage collection.
2. **Diagnose:** Trace the query key, cancellation boundary, remote response, cache update and invalidation.
3. **Repair:** Separate staleTime freshness from gcTime eviction of unused cache entries, and predict focus/refetch behavior.
4. **Regression:** Read immediately twice, refocus at 2 seconds, then refocus after 11 seconds. Explain which reads should reuse cached data and when inactive queries are garbage-collected.
5. **Security and operations:** Never assume cache freshness is authorization. A 401/403 must be handled at the server boundary even if a previous cached object existed.
