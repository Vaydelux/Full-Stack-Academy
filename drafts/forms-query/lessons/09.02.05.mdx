## The problem we're solving

A task POST succeeds but the network response is lost. The learner clicks Retry and the app creates another random idempotency key, producing two identical tasks.

**What breaks in the learner starter:** The starter generates a new idempotency key for every retry and has no in-flight lock.

## Build the mental model

A logical operation consists of validated payload plus an idempotency key. Lock while pending; retain both across retries; clear only after confirmed success.

**Predict before coding:** Two clicks and a response-loss retry must produce one logical task, while a later new task gets a new key.

<LessonStep number={2} title="Apply the instructor repair" file="drafts/forms-query/labs/async-submission/solution.tsx" expected="Two clicks and a response-loss retry must produce one logical task, while a later new task gets a new key.">

```tsx
import { useRef, useState } from 'react';
import { useForm } from 'react-hook-form';
class HTTPStatus extends Error { readonly status:number; constructor(status:number){super('HTTP '+status);this.status=status;} }
type Operation={key:string;payload:{title:string;priority:'normal'}};
export default function RetryForm(){
 const {register,handleSubmit,formState:{isSubmitting}}=
  useForm<{title:string}>({defaultValues:{title:'Practice task'}});
 const busy=useRef(false);
 const [attempt,setAttempt]=useState<Operation|null>(null);
 const [state,setState]=useState('Ready');
 async function execute(op:Operation){
  if(busy.current)return;
  busy.current=true; setAttempt(op); setState('Sending');
  try{
   const r=await fetch('/api/tasks',{method:'POST',
    headers:{'content-type':'application/json','idempotency-key':op.key},body:JSON.stringify(op.payload)});
   if(!r.ok)throw new HTTPStatus(r.status);
   setAttempt(null);setState('Saved');
  }catch(error){
   if(error instanceof HTTPStatus && error.status<500 && error.status!==408 && error.status!==429){
    setAttempt(null);setState('Request rejected; correct input before trying again');
   }else setState('Not confirmed; retry using the same key');
  }
  finally{busy.current=false;}
 }
 return <form onSubmit={event=>{void handleSubmit(async ({title})=>{
   if(attempt)return; // Unknown outcome must be resolved before another create.
   await execute({key:crypto.randomUUID(),payload:{title,priority:'normal'}});
 })(event);}}>
  <label htmlFor="title">Title</label>
  <input id="title" {...register('title',{required:true,minLength:3,maxLength:100})}/>
  <button type="submit" disabled={isSubmitting||state==='Sending'||!!attempt}>Create task</button>
  <button type="button" disabled={state==='Sending'||!attempt}
   onClick={()=>{if(attempt)void execute(attempt)}}>Retry same request</button>
  <p role="status">{state}</p>
 </form>;
}
```

**Why:** A logical operation consists of validated payload plus an idempotency key. Lock while pending; retain both across retries; clear only after confirmed success.

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter generates a new idempotency key for every retry and has no in-flight lock.
2. **Diagnose:** Locate who owns the current value, where it is transformed, and which effect or async boundary can invalidate assumptions.
3. **Repair:** Prevent duplicate side effects and reuse one idempotency key for retries of the same logical request.
4. **Regression:** Simulate an accepted 201 with a lost response. Retry must preserve both body and key. Double-click while pending and verify no second fetch starts.
5. **Operational boundary:** An in-memory idempotency key protects only one process lifetime. Real billing/financial mutations require durable server-side deduplication.

## Production decision guide: separate a retry from a new command

An ambiguous response is not proof that the server did nothing. A create can be committed before the browser loses the response. A retry of the **same logical command** must retain the original request body and idempotency key; changing only the key can create a duplicate. A genuinely new task needs a fresh logical key. A local in-flight guard prevents ordinary double clicks, but not requests from another tab or device.

| Observation | Client policy | Backend responsibility |
| --- | --- | --- |
| Two clicks while pending | Send one request | Deduplicate concurrently |
| Accepted create, response lost | Retry the same body and key | Return the prior outcome |
| User edits after uncertain result | Do not reuse key with a different body | Reject conflicting reuse |
| Different intentional task | Use a new key | Commit independently |

**Independent exercise:** Simulate a successful 201 that never reaches the browser, then replay. Count actual server effects, not just client calls. Change the retry key and explain precisely when duplication becomes possible.

**Real-system caveat:** Aborting a fetch does not guarantee the server aborted the operation. For important financial, order or account mutations, deduplication must be durable, correctly scoped and expire under a deliberate retention policy. The educational loopback API is not a payment ledger.
