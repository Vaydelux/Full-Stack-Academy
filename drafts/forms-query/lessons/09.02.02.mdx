## The problem we're solving

An accessible star-rating widget accepts value and onChange but not an input ref. A developer spreads register into it and assumes React Hook Form can read the selected value.

**What breaks in the learner starter:** The custom control never receives the form-owned value or onChange handler.

## Build the mental model

Use register when a native control provides ref/name/onChange. For a controlled third-party component, Controller bridges field.value and field.onChange.

**Predict before coding:** The naive widget never reports its selected rating to handleSubmit; Controller makes the custom control participate in the form.

<LessonStep number={2} title="Apply the instructor repair" file="drafts/forms-query/labs/register-controller/solution.tsx" expected="The naive widget never reports its selected rating to handleSubmit; Controller makes the custom control participate in the form.">

```tsx
import { Controller, useForm } from 'react-hook-form';
function Rating({ value, onChange }: {value:number;onChange:(n:number)=>void}) {
 return <button type="button" aria-label="Increase rating" onClick={()=>onChange(value===5?1:value+1)}>Rating: {value}</button>;
}
export default function ReviewForm(){
 const { register, control, handleSubmit }=useForm<{title:string;rating:number}>({defaultValues:{title:'',rating:1}});
 return <form onSubmit={handleSubmit(console.log)}>
  <label htmlFor="review-title">Review title</label>
  <input id="review-title" {...register('title',{required:true})} />
  <Controller name="rating" control={control} render={({field})=>
    <Rating value={field.value} onChange={field.onChange} />} />
  <button type="submit">Save</button>
 </form>;
}
```

**Why:** Use register when a native control provides ref/name/onChange. For a controlled third-party component, Controller bridges field.value and field.onChange.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The custom control never receives the form-owned value or onChange handler.
2. **Diagnose:** Locate who owns the current value, where it is transformed, and which effect or async boundary can invalidate assumptions.
3. **Repair:** Use register for a native input and Controller for a non-native controlled picker without creating duplicate form state.
4. **Regression:** Click or keyboard-activate the rating button twice, then submit; the handler must receive rating 3 rather than 1. Verify the title is also registered.
5. **Operational boundary:** A rating picker still needs a semantic accessible name and keyboard focus; wrapping an inaccessible custom control in Controller does not make it accessible.

## Production decision guide: adapt custom controls without duplicating form state

`register` suits native inputs with refs and standard input events. A custom rating widget may require a controlled `value` and `onChange` API. `Controller` connects that API to RHF; its `field` includes the value, change/blur handlers, name and ref. Using only the displayed rating while forgetting `field.onChange` lets the widget appear to work while submission stays at its initial value.

| Symptom | Likely cause | Check |
| --- | --- | --- |
| Rating changes on screen but submits 1 | Widget has independent state | Assert `handleSubmit` data |
| Form never becomes dirty | The picker is disconnected | Inspect defaults and onChange |
| Keyboard users cannot select a rating | Click-only widget | Tab, Space and Enter |
| Error focus never reaches the picker | Ref not forwarded to focusable target | Trigger an invalid selection |

**Independent exercise:** Fill the registered title, keyboard-activate the rating twice, and predict the submitted title/rating pair. Then deliberately disconnect the widget's change handler and identify the first incorrect observable value.

**Accessibility is a separate responsibility.** A `Controller` adapter does not automatically create a button role, label, visible focus or keyboard support. Prefer native controls where practical. Give controlled components complete defaults so dirty-state comparisons have a meaningful baseline.

## Applied debugging clinic

In a custom priority selector, choose high, tab away, then submit. Check the payload and touched state. If the visual selection is correct but the payload is wrong, inspect the callback mapping; if focusing an invalid field fails, inspect whether the widget exposes a focusable ref.

**Evidence to record:** the initial state, action, observed result, expected result and smallest repair. Explain whether the defect belongs to the form, rendered widget, or HTTP boundary. Re-run the original failing interaction after the repair.
