## The problem we're solving

A shopping-list form lets a learner remove the middle row. With index-based React keys, entered values jump to another row because React reuses the wrong DOM input.

**What breaks in the learner starter:** The starter uses key={index} and allows unlimited rows; reordering or deleting can shift user edits.

## Build the mental model

useFieldArray tracks a stable generated field ID. Use field.id for React keys; the numeric index is only for field registration paths.

**Predict before coding:** After removing a middle row, the remaining input content must stay attached to the correct item.

**Scope:** This staged article uses genuine React Hook Form v7 interfaces and React 19 patterns. The source is not yet compiled with installed RHF packages or browser-tested. The companion Node loopback Task API is educational, unauthenticated and in-memory.

```tsx
export default function StepsForm(){
 const {control,register,handleSubmit}=useForm<Fields>({defaultValues:{steps:[{text:'A'},{text:'B'}]}});
 const {fields,append,remove}=useFieldArray({control,name:'steps'});
 return <form onSubmit={handleSubmit(console.log)}>
  {fields.map((field,index)=><div key={field.id}>
   <label htmlFor={'step-'+field.id}>Step {index+1}</label>
   <input id={'step-'+field.id} {...register(`steps.${index}.text`,{required:true,maxLength:80})} />
   <button type="button" onClick={()=>remove(index)}>Remove</button>
  </div>)}
  <button type="button" disabled={fields.length>=8} onClick={()=>append({text:''})}>Add step</button>
  <button type="submit">Save</button>
 </form>;
}
```

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter uses key={index} and allows unlimited rows; reordering or deleting can shift user edits.
2. **Diagnose:** Locate who owns the current value, where it is transformed, and which effect or async boundary can invalidate assumptions.
3. **Repair:** Preserve field-array identity with fields[].id, controlled append/remove, and bounded dynamic inputs.
4. **Regression:** Type unique values in three rows; remove the middle row. The remaining values must match their original logical items. Adding past eight rows must be disabled.
5. **Operational boundary:** Never accept arbitrary numbers of dynamic rows on the server; cap collection lengths and validate each nested item.

## Production decision guide: row identity is not the same as row index

Field arrays expose both the row's current nested-field index and a stable generated `field.id`. Use the current index to register the path and the generated ID as React's list key. If you use `key={index}`, deleting a middle row can reuse a component instance for the wrong logical item, making displayed values or nested widget state appear to jump.

| Action | Expected invariant | Regression |
| --- | --- | --- |
| Append | Existing rows retain their content | Previous entry clears |
| Remove middle row | First and last values stay with their items | Wrong text survives |
| Reorder | Values follow logical rows | Widget state follows old position |
| Add beyond eight rows | UI refuses append | Unbounded row creation |

**Independent exercise:** Enter three distinct labels, remove the middle one, and compare the remaining rendered inputs with the RHF submission payload. Locate any `key={index}` and reason about React reconciliation before changing the remove logic.

**Security boundary:** A disabled Add button is not an API limit. The server must cap the collection length and validate every nested value because a direct HTTP client can bypass browser controls. For accessible rows, keep labels and errors associated with the correct field after deletion.
