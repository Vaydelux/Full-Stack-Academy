## The problem we're solving

A form clears its inputs at the start of every submit, then a 503 response arrives. The learner must retype the entire task and loses the failed request context.

**What breaks in the learner starter:** The starter resets before the HTTP response is confirmed, destroying user input on failure.

## Build the mental model

Reset defines a new baseline and changes dirty state. Only reset after a confirmed successful mutation; preserve draft values after errors.

**Predict before coding:** After a 500 response, isDirty stays true and the typed title remains; after a 201 success, the form resets to its initial defaults.

**Scope:** This staged article uses genuine React Hook Form v7 interfaces and React 19 patterns.
```tsx
import { useForm } from 'react-hook-form';
import { useState } from 'react';
export default function SettingsForm(){
 const {register,handleSubmit,reset,formState:{isDirty,isSubmitting}}=useForm<{title:string}>({defaultValues:{title:''}});
 const [message,setMessage]=useState('');
 return <form onSubmit={handleSubmit(async data=>{
  try{
   const response=await fetch('/api/tasks',{method:'POST',
    headers:{'content-type':'application/json','idempotency-key':crypto.randomUUID()},
    body:JSON.stringify({title:data.title,priority:'normal'})});
   if(!response.ok)throw new Error('HTTP '+response.status);
   reset({title:''});setMessage('Saved');
  }catch{setMessage('Save failed; your draft is preserved');}
 })}>
  <label htmlFor="title">Title</label><input id="title" {...register('title',{required:true,minLength:3})}/>
  <button disabled={isSubmitting||!isDirty}>Save</button>
  <output aria-live="polite">{message}</output>
 </form>;
}
```

**Why:** Reset defines a new baseline and changes dirty state. Only reset after a confirmed successful mutation; preserve draft values after errors.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter resets before the HTTP response is confirmed, destroying user input on failure.
2. **Diagnose:** Locate who owns the current value, where it is transformed, and which effect or async boundary can invalidate assumptions.
3. **Repair:** Understand isDirty, dirtyFields, defaultValues, reset(), and preserving drafts after a failed request.
4. **Regression:** Enter a nonempty title, force server 503, and verify the field remains dirty. Repeat with 201 and confirm reset clears it.
5. **Operational boundary:** Do not store private form drafts or server error bodies into telemetry by default; client state may contain sensitive data.

## Production decision guide: reset only after a confirmation

`isDirty` compares current values against RHF defaults; it is not a database-persistence signal. `dirtyFields` describes per-field edits, not what an API accepted. Calling `reset()` before the result arrives can destroy the only surviving user draft if the request fails or the response is lost.

| Transition | Expected draft | Reset policy |
| --- | --- | --- |
| Initial edit | Keep typed value | No reset |
| Request pending | Keep value, prevent duplicates | No reset |
| Server returns 503 | Keep value for retry | No reset |
| Server confirms 201 | Display confirmation | Reset to intended baseline |

**Independent exercise:** Save a valid title with a forced 503, inspect `isDirty` and confirm the text remains editable. Repeat with a 201 and confirm the reset. Explain why a loading spinner is not a saved acknowledgement.

**Advanced boundary:** If the server normalizes the saved record, an edit form should reset against the *confirmed server value* rather than an arbitrary initial value. New remote data arriving during a dirty edit needs an explicit conflict policy. Do not send private draft content into analytics or error telemetry by default.
