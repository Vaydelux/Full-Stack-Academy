## Problem and observable invariant

**Unique race protections.** Uniqueness belongs in the database. Two concurrent requests can both pass an application-level preflight check before either inserts.

**Failure scenario:** The starter permits duplicate tenant/SKU pairs and leaves a race even if the API checks for duplicates first.

Imagine a multi-tenant SaaS application receiving two overlapping requests. The browser can be refreshed or closed between API calls, and another worker can operate on the same database rows. Correctness must be expressed in terms of the records that PostgreSQL allows to commit, not a successful HTTP response or a pleasant UI state.

The acceptance contract in this module deliberately distinguishes two kinds of evidence: a **single-connection semantic SQL test**, which the included runner can verify, and a **true concurrent-session test**, which requires coordinated independent transactions. Never infer the latter from the former.

## Correctness, concurrency and failure modes

Uniqueness belongs in the database. Two concurrent requests can both pass an application-level preflight check before either inserts.

The starter permits duplicate tenant/SKU pairs and leaves a race even if the API checks for duplicates first.

A uniqueness constraint prevents duplicate committed keys; it does not make an unrelated read-modify-write sequence atomic. The actual two-client race still needs a concurrency test and error handling for SQLSTATE 23505.

A useful production verification matrix varies input identity, tenant, the number of concurrent writers, repeated request keys and observed SQLSTATE outcomes. When a conflict occurs, the correct application behavior is usually to report it or retry the *whole* safe operation from a new snapshot—not to silently overwrite the last writer's state.

## Applied SQL walkthrough

A unique constraint is a database-enforced invariant across rows. A read-then-insert check alone races when two transactions see the same missing SKU. The fixture defines uniqueness over tenant and SKU; a duplicate pair is forbidden, but the same SKU in another tenant is permitted. A constraint enforces uniqueness regardless of which application instance writes.

### Predict and diagnose the result

Attempt a valid insert, a duplicate pair and an equivalent SKU under a different tenant. Record the unique_violation SQLSTATE 23505 for the duplicate. Then design a real two-session test: both read the absent pair, one inserts and commits, and the other must not produce a second committed row.
