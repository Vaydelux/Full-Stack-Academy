## The problem we're solving

**Lab query workbook.** The starter counts finished work and includes disabled users or other tenants in the owner report.

Consider a small project-management database. Users belong to tenants; projects have owners; tasks belong to projects. A report may look plausible while producing the wrong rows, exposing sensitive information, or dropping empty groups. You will begin with an intentionally incorrect SQL exercise, predict its observable failure, and then repair it.

## Mental model and vocabulary

A realistic query combines joins, tenant/user boundaries, filtering, grouping, and deterministic output, then proves both expected rows and excluded rows.

Trace cardinality from users to projects to tasks. Consider a user with no projects, a project with no tasks, a NULL estimate and a task in another tenant. Verify empty groups and security exclusions in addition to happy-path totals.

**Predict first:** Before running the red starter, describe which tenant, ID, column, or count will be incorrect. Name the row you expect to see or not see. The goal is an invariant you can assert in a real PostgreSQL session, not mere SQL syntax acceptance.

**Scope:** PostgreSQL SQL semantics using a disposable session fixture; this is a staged, not-yet-published article. The examples target PostgreSQL 17 or later but have **not** been executed against a real PostgreSQL server in this environment. The shared fixture is teaching data, not a production authorization system.

<LessonStep number={2} title="Repair the relational contract" file="drafts/postgresql/labs/query-workbook/solution.sql" expected="A realistic query combines joins, tenant/user boundaries, filtering, grouping, and deterministic output, then proves both expected rows and excluded rows.">

```sql
CREATE TEMP VIEW lesson_result AS
SELECT u.id AS user_id, u.display_name,
 COUNT(t.id) FILTER (WHERE t.status = 'todo') AS open_tasks
FROM academy_users u
LEFT JOIN academy_projects p
 ON p.owner_id = u.id AND p.tenant_id = u.tenant_id
LEFT JOIN academy_tasks t
 ON t.project_id = p.id AND t.tenant_id = u.tenant_id
WHERE u.tenant_id = 'alpha' AND u.active = true
GROUP BY u.id, u.display_name;
```

**Why the repair works:** A realistic query combines joins, tenant/user boundaries, filtering, grouping, and deterministic output, then proves both expected rows and excluded rows. Review the SQL predicate or constraint that excludes invalid rows and preserves required ones. If a client dynamically constructs SQL, bind parameters rather than interpolating untrusted data; these checked-in statements are intentionally static fixtures.

</LessonStep>
