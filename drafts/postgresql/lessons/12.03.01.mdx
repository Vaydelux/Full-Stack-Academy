## Problem and observable invariant

**ACID and isolation levels.** A transfer is one logical operation. The invariant is that the combined balance does not change when value moves between accounts.

**Failure scenario:** The starter debits one wallet but forgets the corresponding credit. Both statements would be separate side effects without a transaction.

Imagine a multi-tenant SaaS application receiving two overlapping requests. The browser can be refreshed or closed between API calls, and another worker can operate on the same database rows. Correctness must be expressed in terms of the records that PostgreSQL allows to commit, not a successful HTTP response or a pleasant UI state.

The acceptance contract in this module deliberately distinguishes two kinds of evidence: a **single-connection semantic SQL test**, which the included runner can verify, and a **true concurrent-session test**, which requires coordinated independent transactions. Never infer the latter from the former.

## Correctness, concurrency and failure modes

A transfer is one logical operation. The invariant is that the combined balance does not change when value moves between accounts.

The starter debits one wallet but forgets the corresponding credit. Both statements would be separate side effects without a transaction.

Repeatable Read and Serializable describe visibility across concurrent transactions; a single-session balance assertion cannot prove either isolation level. Run a separate two-session experiment before treating this lesson as concurrency-qualified.

A useful production verification matrix varies input identity, tenant, the number of concurrent writers, repeated request keys and observed SQLSTATE outcomes. When a conflict occurs, the correct application behavior is usually to report it or retry the *whole* safe operation from a new snapshot—not to silently overwrite the last writer's state.

## Applied SQL walkthrough

Atomicity means a transaction commits all its changes or none; consistency means the chosen invariants hold at commit; isolation controls concurrent visibility; durability concerns survival of acknowledged commits under the configured durability guarantees. Here the outer runner supplies the transaction. The two UPDATE statements conserve the initial total of twelve units: A becomes six and B becomes six. That alone is insufficient to establish isolation or a complete transfer contract.

### Predict and diagnose the result

Compare the expected balances 6 and 6 with the starter's 6 and 2. Verify both individual values as well as their sum; a sum alone could conceal a transfer in the wrong direction. Use a savepoint in an isolated session to simulate a failed credit and roll back the debit. A real implementation must check affected rows and sufficient funds.

### Independent exercise and evidence

On a separate disposable persistent table visible to two connections, compare repeated reads in Read Committed and Repeatable Read while another session commits an update. Record isolation level, read values and commit outcome. For Serializable, design a competing invariant check and capture any serialization failure; retry the whole transaction, not an individual statement.
