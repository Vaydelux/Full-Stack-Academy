## Performance question to investigate

**EXPLAIN ANALYZE.** EXPLAIN estimates a plan; EXPLAIN ANALYZE executes a statement and records actual rows, time, and instrumentation. The cost units are planner estimates, not milliseconds.

**Broken assumption:** The starter only requests an estimated plan. It cannot demonstrate actual execution, rows, and buffer activity.

The purpose of performance engineering is not to collect more indexes or force a particular query-plan node. It is to establish the correctness of the result, define a representative workload, observe the measured behavior, then decide whether one carefully scoped change produces a sustainable benefit.

This lesson uses a small synthetic multi-tenant task feed. Results can be inspected without a real account, production traffic or secrets. **It is a draft manuscript, not published course content.**

## Mental model

EXPLAIN estimates a plan; EXPLAIN ANALYZE executes a statement and records actual rows, time, and instrumentation. The cost units are planner estimates, not milliseconds.

EXPLAIN ANALYZE executes statements. Only use SELECT against disposable data here; be cautious with DML. On a tiny teaching table PostgreSQL may correctly choose a sequential scan, so no exact plan node is a grading contract.

Keep logical query correctness, physical access paths, and application-perceived latency as separate concerns. The planner may choose a sequential scan on a tiny table even when an appropriate index exists. It is incorrect to fail a lesson just because the exact node does not match a screenshot.

## Production trade-offs

EXPLAIN estimates a plan; EXPLAIN ANALYZE executes a statement and records actual rows, time, and instrumentation. The cost units are planner estimates, not milliseconds.

Record database version, dataset cardinality, actual row count, buffers and latency for three runs. Explain estimated versus actual rows. Do not assert a performance win without a matched workload and measured baseline.

EXPLAIN ANALYZE executes statements. Only use SELECT against disposable data here; be cautious with DML. On a tiny teaching table PostgreSQL may correctly choose a sequential scan, so no exact plan node is a grading contract.

When query execution moves into a real Next.js/NestJS application, measure request concurrency and database calls as well as SQL time. Remember that schema changes alter future write costs, vacuum work and storage. An index may improve a selective read but slow bulk inserts; a pooled connection may conserve memory but alter transaction/session semantics.

## Challenge and review

Imagine the same query executed from 12 API replicas against one shared database. Describe the expected p95 latency, memory pressure, index maintenance cost, and database connection budget. Which metrics would falsify your optimization? What tenant isolation and input validation would be needed before exposing the query as an API?
