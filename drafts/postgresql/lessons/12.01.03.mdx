## The problem we're solving

**JOINs.** The starter joins the project to a user with the same numeric ID, not its owner_id; it also has no tenant scope.

Consider a small project-management database. Users belong to tenants; projects have owners; tasks belong to projects. A report may look plausible while producing the wrong rows, exposing sensitive information, or dropping empty groups. You will begin with an intentionally incorrect SQL exercise, predict its observable failure, and then repair it.

## Mental model and vocabulary

A join combines related entities through their key relationships. The join cardinality determines whether rows disappear or multiply.

A JOIN on similarly named IDs is not evidence of a relationship. Read the foreign-key declaration and choose INNER JOIN versus LEFT JOIN intentionally. A database key alone does not enforce row-level authorization.

<LessonStep number={2} title="Repair the relational contract" file="drafts/postgresql/labs/relational-joins/solution.sql" expected="A join combines related entities through their key relationships. The join cardinality determines whether rows disappear or multiply.">

```sql
CREATE TEMP VIEW lesson_result AS
SELECT p.id AS project_id, u.display_name AS owner, p.title AS project
FROM academy_projects p
JOIN academy_users u
  ON u.id = p.owner_id AND u.tenant_id = p.tenant_id
WHERE p.tenant_id = 'alpha';
```

**Why the repair works:** A join combines related entities through their key relationships. The join cardinality determines whether rows disappear or multiply. Review the SQL predicate or constraint that excludes invalid rows and preserves required ones. ## Edge cases and trust boundaries

Incorrect ON predicates can silently return no rows—or connect a record to the wrong person.

For production systems, distinguish this basic query exercise from actual role privileges, row-level security, constraints across tenant boundaries, input validation, indexes, transaction isolation, and migration safety. Those topics appear in later canonical PostgreSQL and Supabase modules. The teaching fixture deliberately uses static tenant IDs and does not implement real authentication.

## Applied SQL walkthrough

A join matches rows by a relationship, not by coincidentally equal values. Here project.owner_id references user.id; matching tenant_id as well expresses the intended tenant boundary. An inner join drops unmatched rows, and a one-to-many relationship may multiply rows. In the fixture, alpha projects 10, 11 and 12 map to Ana, Bo and Ana respectively. The project with no tasks still has an owner.

### Predict and diagnose the result

Inspect the join result as project ID and owner pairs. Verify each relationship against the original tables. Compare with a join on project ID and user ID; the numeric domains differ and that predicate cannot express ownership. Count rows per project to detect duplicate matches rather than checking only that the query runs.

### Independent exercise and evidence

Sketch a project list including an optional owner display name for a hypothetical nullable ownership model. Explain how LEFT JOIN changes the result and how a WHERE predicate on the right table can remove unmatched rows. Record expected ownership pairs and the excluded beta project 20.
