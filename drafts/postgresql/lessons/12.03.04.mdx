## Problem and observable invariant

**Optimistic concurrency.** Optimistic updates compare an expected version in the WHERE clause. A stale writer updates zero rows instead of overwriting a newer result.

**Failure scenario:** The starter performs a second stale write unconditionally, turning a 1-unit debit into a 4-unit debit.

Imagine a multi-tenant SaaS application receiving two overlapping requests. The browser can be refreshed or closed between API calls, and another worker can operate on the same database rows. Correctness must be expressed in terms of the records that PostgreSQL allows to commit, not a successful HTTP response or a pleasant UI state.

The acceptance contract in this module deliberately distinguishes two kinds of evidence: a **single-connection semantic SQL test**, which the included runner can verify, and a **true concurrent-session test**, which requires coordinated independent transactions. Never infer the latter from the former.

## Mental model and vocabulary

Optimistic updates compare an expected version in the WHERE clause. A stale writer updates zero rows instead of overwriting a newer result.

Real APIs must read the updated row count and return a conflict/retry decision when it is zero; silent zero-row updates are not sufficient. Re-reading state before a retry may change the business meaning.

This is a working example of an *invariant*: a property that should continue to hold if the request is retried, a second process starts, the database is under load, or the same function is called from another API route. Describe the invariant in plain language and as a database result before writing code.

## Correctness, concurrency and failure modes

Optimistic updates compare an expected version in the WHERE clause. A stale writer updates zero rows instead of overwriting a newer result.

The starter performs a second stale write unconditionally, turning a 1-unit debit into a 4-unit debit.

Real APIs must read the updated row count and return a conflict/retry decision when it is zero; silent zero-row updates are not sufficient. Re-reading state before a retry may change the business meaning.

A useful production verification matrix varies input identity, tenant, the number of concurrent writers, repeated request keys and observed SQLSTATE outcomes. When a conflict occurs, the correct application behavior is usually to report it or retry the *whole* safe operation from a new snapshot—not to silently overwrite the last writer's state.
