## Problem and observable invariant

**Idempotency records.** An idempotency key maps a request identity to one stable outcome. A repeated request must not overwrite the original stored result.

**Failure scenario:** The starter's ON CONFLICT DO UPDATE overwrites the first response with a second, conflicting outcome.

Imagine a multi-tenant SaaS application receiving two overlapping requests. The browser can be refreshed or closed between API calls, and another worker can operate on the same database rows. Correctness must be expressed in terms of the records that PostgreSQL allows to commit, not a successful HTTP response or a pleasant UI state.

The acceptance contract in this module deliberately distinguishes two kinds of evidence: a **single-connection semantic SQL test**, which the included runner can verify, and a **true concurrent-session test**, which requires coordinated independent transactions. Never infer the latter from the former.

## Mental model and vocabulary

An idempotency key maps a request identity to one stable outcome. A repeated request must not overwrite the original stored result.

Production idempotency also needs a request-payload hash, expiry policy, in-flight locking, durable business result and atomic relationship to side effects. ON CONFLICT alone does not make external payments exactly once.

This is a working example of an *invariant*: a property that should continue to hold if the request is retried, a second process starts, the database is under load, or the same function is called from another API route. Describe the invariant in plain language and as a database result before writing code.

## Correctness, concurrency and failure modes

An idempotency key maps a request identity to one stable outcome. A repeated request must not overwrite the original stored result.

The starter's ON CONFLICT DO UPDATE overwrites the first response with a second, conflicting outcome.

Production idempotency also needs a request-payload hash, expiry policy, in-flight locking, durable business result and atomic relationship to side effects. ON CONFLICT alone does not make external payments exactly once.

A useful production verification matrix varies input identity, tenant, the number of concurrent writers, repeated request keys and observed SQLSTATE outcomes. When a conflict occurs, the correct application behavior is usually to report it or retry the *whole* safe operation from a new snapshot—not to silently overwrite the last writer's state.

## Applied SQL walkthrough

An idempotency record identifies a logical operation within a tenant. The unique tenant/key pair prevents duplicate records. ON CONFLICT DO NOTHING preserves the first result in this fixture: key charge-1 keeps result 100 rather than becoming 999. It does not automatically execute a business operation exactly once or detect a changed payload. A production receipt should include a request fingerprint and a well-defined replay contract.

### Predict and diagnose the result

Inspect the result row after both inserts and verify there is one record with the original result. On a separate shared table, submit the same key concurrently with independent connections; observe unique-index arbitration and read the winning committed result. Test reuse with a different payload and define a conflict outcome rather than silently treating it as a valid replay.

### Independent exercise and evidence

Design an operation that writes its business change and receipt in one transaction. Simulate losing the response after commit, then retry with the original key. Specify retention and failure recovery; external side effects need their own idempotency or outbox contract. Record receipt count, operation count and replay behavior.
