## Operational problem

**Lab recover sample database.** Recovery qualification must be repeatable: backup creation, clean restore target, schema inspection, data reconciliation, application smoke test and documented RTO/RPO.

**Common failure:** The starter can display live rows but has no evidence that any backup was created or that the rows would survive a database loss.

Database operations differ from syntax tutorials: observing a configuration setting, successfully creating a backup file, and actually recovering an application are three distinct kinds of evidence. A successful command cannot prove availability, restoration, consistency, or acceptable recovery time without a controlled independent drill.

## Mental model and risk

Recovery qualification must be repeatable: backup creation, clean restore target, schema inspection, data reconciliation, application smoke test and documented RTO/RPO.

Never use production credentials or destructive `--clean` against an existing environment. The runbook is deliberately manual and cannot be auto-certified by a source scan or a backup filename.

A production-grade runbook needs a named responsible operator, target environment, prerequisite privileges, allowable downtime, credentials/secret-handling instructions, rollback/abort conditions and verifiable success evidence. Keep database tests isolated from the real application's data and users.

## Applied SQL walkthrough

Recovery is complete only when an independent target contains the expected data and the application can use it under the intended permissions. The provided query measures restored row count and a deterministic checksum over two selected fields. Compare it with evidence captured before the simulated incident. Logical restoration is not point-in-time recovery, and a successful drill on a tiny sample does not establish production RTO.

### Predict and diagnose the result

Use the persistent local sample specified in the runbook and restore to the dedicated recovery database. Confirm target identity before any cleanup. Compare baseline and restored counts, checksum, representative constraints and a read-only application query. Record any missing roles or extensions and do not reuse a target that contains unrelated data.

### Independent exercise and evidence

Prepare a handoff record with incident hypothesis, selected backup, target identity, restore start/end times, measured loss and functional verification. Include a no-go decision if consistency fails and the process for safely cleaning up only the disposable target. A separate realistic rehearsal is required before claiming operational recovery objectives.

**Qualification boundary:** These are operational practice instructions, not a completed recovery or security audit. Use only explicitly authorized disposable infrastructure. Preserve the existing starter, solution and acceptance contract.

**Integrity distinction:** The SQL `md5(string_agg(...))` snippet is only a quick educational row-comparison fingerprint. MD5 is not collision-resistant and cannot authenticate a backup. For a serious restore drill, use a cryptographic file checksum such as SHA-256, verify schema and role ownership, compare independently generated application invariants, and retain sanitized signed evidence where the threat model requires it.

## Practice extension

Write an operational runbook that can be followed by a second developer who has never seen your environment. Specify the real host selector, approved test database name, least-privilege role, safety checks, expected output, cleanup, and an audit of what did or did not succeed.

For backup/restore tasks, attach only sanitized non-sensitive evidence. Explain the distinction between a backup, a restore drill, and point-in-time recovery; none of those should be marked qualified from a source-only check. For permission work, test a denied operation as deliberately as a successful read.
