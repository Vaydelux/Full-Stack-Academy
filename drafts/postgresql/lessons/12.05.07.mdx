## Operational problem

**Restore drills.** A backup is useful only if a separate restore is successful and its content and permissions are verified. Record timing, checksum, ownership, schema version and application compatibility.

**Common failure:** The starter records only row count from the original database and never tests recovery into an isolated target.

Database operations differ from syntax tutorials: observing a configuration setting, successfully creating a backup file, and actually recovering an application are three distinct kinds of evidence. A successful command cannot prove availability, restoration, consistency, or acceptable recovery time without a controlled independent drill.

The temporary fixture used for source examples is intentionally not a valid pg_dump restore artifact. A real restore drill requires two dedicated, non-production databases and manual authorization; the source scanner cannot certify it.

Keep database tests isolated from the real application's data and users.

## Applied SQL walkthrough

A restore drill tests whether a backup can become a usable database in a new environment. The sample count and ordered checksum compare selected fixture fields; they do not cover every schema object, row value, privilege or extension. The aggregate may return NULL on empty data, and the checksum is a teaching consistency check rather than a cryptographic authenticity guarantee.

### Predict and diagnose the result

Capture baseline counts and checksums from a persistent disposable sample table, not the temporary fixture that disappears when its session ends. Follow the existing runbook for a logical dump and a fresh restore target. Verify object definitions, constraints and representative queries as well as the baseline fields. Record restore errors and elapsed time.

### Independent exercise and evidence

Plan a rehearsal with a deliberately incomplete backup or an unavailable required extension in an isolated environment. Define an abort condition and how to obtain a valid replacement backup. Record tool and database versions, backup identity, restore duration and application-level smoke results before declaring recovery successful.

**Integrity distinction:** The SQL `md5(string_agg(...))` snippet is only a quick educational row-comparison fingerprint. MD5 is not collision-resistant and cannot authenticate a backup. For a serious restore drill, use a cryptographic file checksum such as SHA-256, verify schema and role ownership, compare independently generated application invariants, and retain sanitized signed evidence where the threat model requires it.

## Practice extension

Write an operational runbook that can be followed by a second developer who has never seen your environment. Specify the real host selector, approved test database name, least-privilege role, safety checks, expected output, cleanup, and an audit of what did or did not succeed.

For backup/restore tasks, attach only sanitized non-sensitive evidence. Explain the distinction between a backup, a restore drill, and point-in-time recovery; none of those should be marked qualified from a source-only check. For permission work, test a denied operation as deliberately as a successful read.
