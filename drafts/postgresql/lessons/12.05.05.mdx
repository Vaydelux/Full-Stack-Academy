## Operational problem

**Roles and least privilege.** Separate migration, runtime, read-only and backup roles. Grant only the minimum object privileges necessary for each operation and avoid long-lived superuser application credentials.

**Common failure:** The starter prints a role name without checking whether the login is a superuser or can create roles/databases.

Database operations differ from syntax tutorials: observing a configuration setting, successfully creating a backup file, and actually recovering an application are three distinct kinds of evidence. A successful command cannot prove availability, restoration, consistency, or acceptable recovery time without a controlled independent drill.

## Mental model and risk

Separate migration, runtime, read-only and backup roles. Grant only the minimum object privileges necessary for each operation and avoid long-lived superuser application credentials.

SELECT from pg_roles is read-only metadata inspection, not a privilege grant or a complete access audit. Creating test roles and exercising denial paths requires an isolated DBA-controlled lab.

A production-grade runbook needs a named responsible operator, target environment, prerequisite privileges, allowable downtime, credentials/secret-handling instructions, rollback/abort conditions and verifiable success evidence. Keep database tests isolated from the real application's data and users.

## Applied SQL walkthrough

Least privilege grants each runtime identity only the operations it needs. A login role need not own tables, create databases or create other roles. Role flags alone are insufficient: inherited memberships, object grants, schema USAGE and row policies also determine effective access. Use a separate migration identity and never give a routine API unrestricted administrative permissions.

### Predict and diagnose the result

Inspect the current role flags using the provided SELECT. In an isolated database, verify actual grants and run a positive test for permitted table operations and a negative test for a forbidden object or administrative operation. Record the effective role and insufficient_privilege SQLSTATE 42501 when appropriate; a superuser test cannot demonstrate ordinary runtime denial.

### Independent exercise and evidence

Design runtime, migration and read-only reporting roles with a permission matrix covering schema, table, sequence and administrative actions. Add a negative cross-schema read and a positive authorized write to the test plan. Record actual grants and failures without exposing credentials or modifying production roles.

## Practice extension

Write an operational runbook that can be followed by a second developer who has never seen your environment. Specify the real host selector, approved test database name, least-privilege role, safety checks, expected output, cleanup, and an audit of what did or did not succeed.

For backup/restore tasks, attach only sanitized non-sensitive evidence. Explain the distinction between a backup, a restore drill, and point-in-time recovery; none of those should be marked qualified from a source-only check. For permission work, test a denied operation as deliberately as a successful read.
