## The real modeling problem

**Many-to-many relationships.** A collaborator can be on several projects. A membership table keyed only by tenant and member prevents joining a second project.

A web framework can validate a request, but it cannot make an inconsistent relational design safe after several independent writers, scheduled jobs, or migrations start modifying the same data. In this lesson you will identify the invariant, observe a *real* negative SQL case, repair the schema or query, and write down the boundary that the database does **not** guarantee.

## Mental model

A junction table identifies one association between two entities. Its primary key must cover the full relationship, or valid memberships will be rejected.

The primary key includes tenant, member and project, and both references carry the same tenant to prevent cross-organization associations.

**Predict before running SQL:** Which row, relationship, constraint, or audit event will be incorrect? Identify a specific permitted case and a specific forbidden case. A SQL command that returns without a syntax error is not proof that it represents the business domain.

 member_id integer NOT NULL,

);

## Architectural trade-offs

A junction table identifies one association between two entities. Its primary key must cover the full relationship, or valid memberships will be rejected.

A many-to-many table can accumulate duplicate or unauthorized roles if the unique key or permission boundary is missing. Composite foreign keys validate identities, not actor permissions.

The right choice can change with workload size, tenant access patterns, migration risk and operational constraints. Optimize a schema only after correctness and measured query behavior. A trigger, index, or foreign key is not evidence of complete application authorization.
