## The problem we're solving

**Foreign keys and constraints.** The starter's task-notes table accepts an orphan task reference and a whitespace-only note.

Consider a small project-management database. Users belong to tenants; projects have owners; tasks belong to projects. A report may look plausible while producing the wrong rows, exposing sensitive information, or dropping empty groups. You will begin with an intentionally incorrect SQL exercise, predict its observable failure, and then repair it.

## Mental model and vocabulary

PRIMARY KEY, FOREIGN KEY and CHECK are data invariants, not optional form hints. Constraints reject invalid writes even when the application has a bug.

An FK prevents orphan IDs but does not guarantee the same tenant; cross-tenant composite keys and authorization policies are covered later. CHECK constraints accept UNKNOWN, so pair constraints with NOT NULL deliberately.

**Predict first:** Before running the red starter, describe which tenant, ID, column, or count will be incorrect. Name the row you expect to see or not see. The goal is an invariant you can assert in a real PostgreSQL session, not mere SQL syntax acceptance.

**Scope:** PostgreSQL SQL semantics using a disposable session fixture; this is a staged, not-yet-published article. The examples target PostgreSQL 17 or later but have **not** been executed against a real PostgreSQL server in this environment. The shared fixture is teaching data, not a production authorization system.

<LessonStep number={2} title="Repair the relational contract" file="drafts/postgresql/labs/foreign-keys-constraints/solution.sql" expected="PRIMARY KEY, FOREIGN KEY and CHECK are data invariants, not optional form hints. Constraints reject invalid writes even when the application has a bug.">

```sql
CREATE TEMP TABLE lesson_notes (
 id integer PRIMARY KEY,
 task_id integer NOT NULL REFERENCES academy_tasks(id),
 body text NOT NULL CHECK (length(btrim(body)) >= 3)
);
```

**Why the repair works:** PRIMARY KEY, FOREIGN KEY and CHECK are data invariants, not optional form hints. Constraints reject invalid writes even when the application has a bug. Review the SQL predicate or constraint that excludes invalid rows and preserves required ones. If a client dynamically constructs SQL, bind parameters rather than interpolating untrusted data; these checked-in statements are intentionally static fixtures.

</LessonStep>

Draw the relevant row set: **users → projects → tasks**. Identify whether this operation projects columns, filters rows, combines relations, aggregates groups, or enforces a physical constraint. A data-layer restriction should not be replaced by a frontend filter; the browser cannot enforce another client's access to storage.

## Edge cases and trust boundaries

Neither UI validation nor TypeScript types prevent direct SQL clients from inserting invalid rows.

For production systems, distinguish this basic query exercise from actual role privileges, row-level security, constraints across tenant boundaries, input validation, indexes, transaction isolation, and migration safety. Those topics appear in later canonical PostgreSQL and Supabase modules. The teaching fixture deliberately uses static tenant IDs and does not implement real authentication.
