## Operational problem

**Backups and PITR concepts.** Point-in-time recovery requires a valid base backup plus continuous, usable WAL archives and a well-defined recovery target. A setting alone does not prove a restorable backup.

**Common failure:** The starter looks at two settings and assumes a backup exists; it omits WAL archiving evidence, restore target, offsite retention and a completed test restore.

Database operations differ from syntax tutorials: observing a configuration setting, successfully creating a backup file, and actually recovering an application are three distinct kinds of evidence. A successful command cannot prove availability, restoration, consistency, or acceptable recovery time without a controlled independent drill.

## Applied SQL walkthrough

A logical dump exports database objects and data at a consistent snapshot; a physical base backup and continuous WAL archive can support point-in-time recovery. These are different recovery mechanisms. The displayed configuration settings indicate prerequisites but cannot establish that archives are complete, accessible or restorable. A recovery point objective defines tolerable data loss; a recovery time objective defines tolerable outage duration.

### Predict and diagnose the result

Inspect archive_mode and wal_level in the authorized disposable instance, and treat configuration output as readiness information only. Plan a base backup, archive continuity check and restore into a separate instance to a selected timestamp. Record backup identity, time zone and target. Redact archive_command and connection details if they expose secrets.

### Independent exercise and evidence

Draft a recovery plan for a hypothetical accidental deletion: specify the last acceptable recovery point, who approves the restore, the isolated target and the checks before any application cutover. Compare expected and observed recovery duration during a real drill; do not claim PITR from a successful configuration query.

## Practice extension

Write an operational runbook that can be followed by a second developer who has never seen your environment. Specify the real host selector, approved test database name, least-privilege role, safety checks, expected output, cleanup, and an audit of what did or did not succeed.

For backup/restore tasks, attach only sanitized non-sensitive evidence. Explain the distinction between a backup, a restore drill, and point-in-time recovery; none of those should be marked qualified from a source-only check. For permission work, test a denied operation as deliberately as a successful read.
