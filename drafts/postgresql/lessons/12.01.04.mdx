## The problem we're solving

**GROUP BY and aggregates.** The starter counts the joined row, losing the difference between an empty project and a project with one task.

Consider a small project-management database. Users belong to tenants; projects have owners; tasks belong to projects. A report may look plausible while producing the wrong rows, exposing sensitive information, or dropping empty groups. You will begin with an intentionally incorrect SQL exercise, predict its observable failure, and then repair it.

<LessonStep number={2} title="Repair the relational contract" file="drafts/postgresql/labs/grouping-aggregates/solution.sql" expected="Aggregate functions summarize groups; LEFT JOIN plus COUNT(child.id) preserves a group with zero related rows. COUNT(*) counts outer rows, not existing children.">

```sql
CREATE TEMP VIEW lesson_result AS
SELECT p.id AS project_id,
       COUNT(t.id) AS task_count,
       COALESCE(SUM(t.estimate_hours), 0) AS planned_hours
FROM academy_projects p
LEFT JOIN academy_tasks t
 ON t.project_id = p.id AND t.tenant_id = p.tenant_id
WHERE p.tenant_id = 'alpha'
GROUP BY p.id;
```

**Why the repair works:** Aggregate functions summarize groups; LEFT JOIN plus COUNT(child.id) preserves a group with zero related rows. COUNT(*) counts outer rows, not existing children. Review the SQL predicate or constraint that excludes invalid rows and preserves required ones. If a client dynamically constructs SQL, bind parameters rather than interpolating untrusted data; these checked-in statements are intentionally static fixtures.

</LessonStep>

## Applied SQL walkthrough

An outer join preserves the parent even when no matching child exists. COUNT(t.id) counts non-NULL child keys, while COUNT(*) counts the outer row too. SUM ignores unknown estimates and returns NULL when no non-NULL values exist; COALESCE converts that result to zero for this reporting contract. The difference between unknown work and zero work may matter in real planning reports.

### Predict and diagnose the result

Compute the fixture results before execution: project 10 has three tasks totaling nine hours; project 11 has two tasks totaling two known hours; project 12 has zero tasks and zero planned hours. Check each group independently. Moving a task predicate into WHERE can remove empty projects; keep child filtering in the join or conditional aggregate when parents must remain.
