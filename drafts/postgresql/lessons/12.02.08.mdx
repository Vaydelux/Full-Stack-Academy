## The real modeling problem

**Bug Hunt missing tenant filter.** A project dashboard filters tasks by status but not by workspace. It returns beta's unfinished task to alpha, despite producing a syntactically valid table.

A web framework can validate a request, but it cannot make an inconsistent relational design safe after several independent writers, scheduled jobs, or migrations start modifying the same data. In this lesson you will identify the invariant, observe a *real* negative SQL case, repair the schema or query, and write down the boundary that the database does **not** guarantee.

## Mental model

A correct SQL query can be an authorization vulnerability if it omits the tenant boundary. The result set needs an explicit positive and negative tenant assertion.

The tenant predicate reduces the result set before data is returned. The tests insist on known allowed rows and explicit exclusion of cross-tenant rows.

**Predict before running SQL:** Which row, relationship, constraint, or audit event will be incorrect? Identify a specific permitted case and a specific forbidden case. A SQL command that returns without a syntax error is not proof that it represents the business domain.

## Architectural trade-offs

A correct SQL query can be an authorization vulnerability if it omits the tenant boundary. The result set needs an explicit positive and negative tenant assertion.

A hardcoded tenant in a fixture does not enforce authorization in a web app. Production code must bind a verified request tenant, enforce object-level authorization, and preferably add database RLS with independently tested roles.

The right choice can change with workload size, tenant access patterns, migration risk and operational constraints. Optimize a schema only after correctness and measured query behavior. A trigger, index, or foreign key is not evidence of complete application authorization.

## Applied SQL walkthrough

Tenant filtering must happen before rows cross the data-access boundary. A status predicate alone selects matching tasks across organizations. The fixture uses a hardcoded tenant to teach query correctness; a production query must bind tenant identity from verified context, not accept an arbitrary client-supplied tenant. Row-level security can provide an additional boundary when tested with actual application roles.
