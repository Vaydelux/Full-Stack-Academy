## The real modeling problem

**Normalization and denormalization.** A signup form allows a user to add multiple contact emails. The first design stores comma-separated addresses in one column. Searching, deduplicating, and constraining an individual address becomes unreliable.

A web framework can validate a request, but it cannot make an inconsistent relational design safe after several independent writers, scheduled jobs, or migrations start modifying the same data. In this lesson you will identify the invariant, observe a *real* negative SQL case, repair the schema or query, and write down the boundary that the database does **not** guarantee.

## Mental model

A normalized model stores each repeating fact in its own relation. Contacts and email addresses have different cardinalities: one contact can own zero, one, or many addresses.

The child table has one address per row, a foreign key to its owner, and a compound primary key that rejects a duplicate address for the same person.

**Predict before running SQL:** Which row, relationship, constraint, or audit event will be incorrect? Identify a specific permitted case and a specific forbidden case. A SQL command that returns without a syntax error is not proof that it represents the business domain.

<LessonStep number={2} title="Implement the corrected relationship or constraint" file="drafts/postgresql/labs/normalization-boundaries/solution.sql" expected="The child table has one address per row, a foreign key to its owner, and a compound primary key that rejects a duplicate address for the same person.">

```sql
CREATE TEMP TABLE lesson_contacts (
 id integer PRIMARY KEY,
 display_name text NOT NULL

CREATE TEMP TABLE lesson_contact_addresses (
 contact_id integer NOT NULL REFERENCES lesson_contacts(id),
 address text NOT NULL,
 PRIMARY KEY (contact_id, address)
);
```

**Reasoning:** The child table has one address per row, a foreign key to its owner, and a compound primary key that rejects a duplicate address for the same person.

## Architectural trade-offs

A normalized model stores each repeating fact in its own relation. Contacts and email addresses have different cardinalities: one contact can own zero, one, or many addresses.

Normalization is a logical data-integrity decision, not a performance guarantee. Denormalized read models must have an explicit refresh and reconciliation strategy.

The right choice can change with workload size, tenant access patterns, migration risk and operational constraints. Optimize a schema only after correctness and measured query behavior. A trigger, index, or foreign key is not evidence of complete application authorization.
