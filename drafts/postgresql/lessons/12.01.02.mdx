## The problem we're solving

**SELECT WHERE ORDER BY.** The starter sorts all tasks, including a different tenant and completed work, instead of finding alpha's open tasks.

Consider a small project-management database. Users belong to tenants; projects have owners; tasks belong to projects. A report may look plausible while producing the wrong rows, exposing sensitive information, or dropping empty groups. You will begin with an intentionally incorrect SQL exercise, predict its observable failure, and then repair it.

## Mental model and vocabulary

<LessonStep number={2} title="Repair the relational contract" file="drafts/postgresql/labs/select-filter-order/solution.sql" expected="WHERE reduces the candidate rows; ORDER BY establishes deterministic order, especially important for paging and test assertions.">

```sql
CREATE TEMP VIEW lesson_result AS
SELECT id, title, estimate_hours
FROM academy_tasks
WHERE tenant_id = 'alpha' AND status = 'todo'
ORDER BY id ASC;
```

**Why the repair works:** WHERE reduces the candidate rows; ORDER BY establishes deterministic order, especially important for paging and test assertions. Review the SQL predicate or constraint that excludes invalid rows and preserves required ones. If a client dynamically constructs SQL, bind parameters rather than interpolating untrusted data; these checked-in statements are intentionally static fixtures.

</LessonStep>

## Edge cases and trust boundaries

Without a tenant and status predicate, even correctly sorted rows can disclose unrelated tasks.

For production systems, distinguish this basic query exercise from actual role privileges, row-level security, constraints across tenant boundaries, input validation, indexes, transaction isolation, and migration safety. Those topics appear in later canonical PostgreSQL and Supabase modules. The teaching fixture deliberately uses static tenant IDs and does not implement real authentication.
