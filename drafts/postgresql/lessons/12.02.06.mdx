## The real modeling problem

**Check and unique constraints.** The inventory accepts a negative quantity and treats 'widget' and 'WIDGET' as different SKUs. Both violate the intended domain contract.

A web framework can validate a request, but it cannot make an inconsistent relational design safe after several independent writers, scheduled jobs, or migrations start modifying the same data. In this lesson you will identify the invariant, observe a *real* negative SQL case, repair the schema or query, and write down the boundary that the database does **not** guarantee.

## Mental model

A CHECK constraint validates each row's invariant. An expression unique index can enforce case-insensitive uniqueness within one tenant.

The nonnegative quantity CHECK rejects impossible inventory and the unique expression index normalizes the SKU comparison by lowercasing before enforcing tenant-scoped uniqueness.

**Predict before running SQL:** Which row, relationship, constraint, or audit event will be incorrect? Identify a specific permitted case and a specific forbidden case. A SQL command that returns without a syntax error is not proof that it represents the business domain.

<LessonStep number={2} title="Implement the corrected relationship or constraint" file="drafts/postgresql/labs/scoped-check-unique/solution.sql" expected="The nonnegative quantity CHECK rejects impossible inventory and the unique expression index normalizes the SKU comparison by lowercasing before enforcing tenant-scoped uniqueness.">

```sql
CREATE TEMP TABLE lesson_inventory (
 id integer PRIMARY KEY,
 tenant_id text NOT NULL,
 sku text NOT NULL CHECK (length(btrim(sku)) >= 2),
 quantity integer NOT NULL CHECK (quantity >= 0)
);
CREATE UNIQUE INDEX lesson_inventory_tenant_sku_unique
 ON lesson_inventory (tenant_id, lower(sku));
```

**Reasoning:** The nonnegative quantity CHECK rejects impossible inventory and the unique expression index normalizes the SKU comparison by lowercasing before enforcing tenant-scoped uniqueness.

In a production system, migration changes must preserve existing data and support concurrent writers. This solution models one invariant using disposable temporary tables so the learner can prove correctness without modifying an existing application schema.

</LessonStep>

## Architectural trade-offs

A CHECK constraint validates each row's invariant. An expression unique index can enforce case-insensitive uniqueness within one tenant.

CHECK treats NULL as unknown; NOT NULL must be explicit. Case-folding behavior may vary with collation and Unicode; define a normalized SKU policy before using this as a production identifier.

The right choice can change with workload size, tenant access patterns, migration risk and operational constraints. Optimize a schema only after correctness and measured query behavior. A trigger, index, or foreign key is not evidence of complete application authorization.
