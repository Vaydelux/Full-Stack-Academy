## Operational problem

**Environment isolation.** Environment identity must come from the actual connection, not hardcoded configuration claims. Test databases need independent credentials, names, permissions, and retention policies.

**Common failure:** The starter labels every connection as production/admin regardless of the actual database or active role.

Database operations differ from syntax tutorials: observing a configuration setting, successfully creating a backup file, and actually recovering an application are three distinct kinds of evidence. A successful command cannot prove availability, restoration, consistency, or acceptable recovery time without a controlled independent drill.

## Mental model and risk

Environment identity must come from the actual connection, not hardcoded configuration claims. Test databases need independent credentials, names, permissions, and retention policies.

This is a connection-identity sanity test, not proof of network isolation, secrets separation, firewall policy or absence of cross-environment credentials. Independently inspect infrastructure settings.

A production-grade runbook needs a named responsible operator, target environment, prerequisite privileges, allowable downtime, credentials/secret-handling instructions, rollback/abort conditions and verifiable success evidence. Keep database tests isolated from the real application's data and users.

## Applied SQL walkthrough

Environment identity is a safety boundary, not just a filename or environment variable. A database name can be reused across servers, so verify the host, database, connected role and deployment context together. The sample view reads actual connection identity. The existing runner requires explicit opt-in and local test naming; these checks reduce accidental targeting but are not proof of a complete isolation policy.

### Predict and diagnose the result

Before running any lab, compare the expected connection identity with current_database and current_user. Use a dedicated test role and ensure the intended disposable server is selected. Try invalid configuration values using the runner validation functions without connecting to a remote server. Do not print passwords or complete connection URLs.

## Practice extension

Write an operational runbook that can be followed by a second developer who has never seen your environment. Specify the real host selector, approved test database name, least-privilege role, safety checks, expected output, cleanup, and an audit of what did or did not succeed.

For backup/restore tasks, attach only sanitized non-sensitive evidence. Explain the distinction between a backup, a restore drill, and point-in-time recovery; none of those should be marked qualified from a source-only check. For permission work, test a denied operation as deliberately as a successful read.
