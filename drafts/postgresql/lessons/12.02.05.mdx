## The real modeling problem

**Soft delete and history.** A team archives the label 'Urgent' and creates a replacement. A global uniqueness constraint blocks the replacement, and no history record explains what happened.

A web framework can validate a request, but it cannot make an inconsistent relational design safe after several independent writers, scheduled jobs, or migrations start modifying the same data. In this lesson you will identify the invariant, observe a *real* negative SQL case, repair the schema or query, and write down the boundary that the database does **not** guarantee.

## Mental model

Soft deletion separates active records from historical records. A partial uniqueness rule can permit reusing an archived label while preventing duplicates among active labels.

The partial unique index applies only to active labels, while the trigger records the archive transition in a separate table for review.

**Predict before running SQL:** Which row, relationship, constraint, or audit event will be incorrect? Identify a specific permitted case and a specific forbidden case. A SQL command that returns without a syntax error is not proof that it represents the business domain.

<LessonStep number={2} title="Implement the corrected relationship or constraint" file="drafts/postgresql/labs/soft-delete-history/solution.sql" expected="The partial unique index applies only to active labels, while the trigger records the archive transition in a separate table for review.">

```sql
CREATE TEMP TABLE lesson_labels (
 id integer PRIMARY KEY,
 tenant_id text NOT NULL,
 label text NOT NULL,
 deleted_at timestamptz
);
CREATE UNIQUE INDEX lesson_active_labels_unique
 ON lesson_labels (tenant_id, lower(label)) WHERE deleted_at IS NULL;
CREATE TEMP TABLE lesson_label_history (
 id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 label_id integer NOT NULL REFERENCES lesson_labels(id),
 tenant_id text NOT NULL,
 action text NOT NULL,
 occurred_at timestamptz NOT NULL DEFAULT now()
);
CREATE FUNCTION pg_temp.record_label_archive() RETURNS trigger
LANGUAGE plpgsql AS $fn$
BEGIN
 IF OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL THEN
  INSERT INTO lesson_label_history(label_id,tenant_id,action)
  VALUES(NEW.id,NEW.tenant_id,'archived');
 END IF;
 RETURN NEW;
END $fn$;
CREATE TRIGGER label_archive_event
AFTER UPDATE OF deleted_at ON lesson_labels
FOR EACH ROW EXECUTE FUNCTION pg_temp.record_label_archive();
```

**Reasoning:** The partial unique index applies only to active labels, while the trigger records the archive transition in a separate table for review.

In a production system, migration changes must preserve existing data and support concurrent writers. This solution models one invariant using disposable temporary tables so the learner can prove correctness without modifying an existing application schema.

</LessonStep>

## Architectural trade-offs

Soft deletion separates active records from historical records. A partial uniqueness rule can permit reusing an archived label while preventing duplicates among active labels.

Soft delete is not a substitute for retention policy, access revocation, legal erasure or a cryptographically protected audit trail. The example logs only the transition and is not a complete event-sourcing system.

The right choice can change with workload size, tenant access patterns, migration risk and operational constraints. Optimize a schema only after correctness and measured query behavior. A trigger, index, or foreign key is not evidence of complete application authorization.
