## The problem we're solving

A Next.js page fetches tasks on the server and again on the client with different query keys, causing duplicate requests, flicker, and a hydration mismatch.

**Broken behavior in the starter:** The starter creates QueryClient but fails to prefetch and hydrate into the client component with a matching key.

## Build the mental model

The server creates a request-scoped QueryClient, prefetches a query, then passes only safe dehydrated state through HydrationBoundary. Client query keys and data shapes must match.

**Predict before coding:** The first client render uses the prefetched cache; a later refetch occurs only when freshness policy requires it.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. export default async function Page(){
 const client=new QueryClient();
 await client.prefetchQuery({
  queryKey:['tasks',{status:'todo',limit:10}],
  queryFn:async()=>{
   const r=await fetch('http://127.0.0.1:3337/api/tasks?status=todo&limit=10',{cache:'no-store'});
   if(!r.ok)throw new Error('Local teaching API unavailable');
   return r.json();
  },
 });
 return <Providers><HydrationBoundary state={dehydrate(client)}><TaskList/></HydrationBoundary></Providers>;
}

## Production decision guide: SSR hydration preserves identity, not secrecy

Server prefetch and client hydration work when both sides describe the *same query key and data contract*. In Next.js a Server Component can prefetch safe data, `dehydrate` the cache and pass it through `HydrationBoundary` to a client tree with a matching `QueryClientProvider`. If the client asks for a different key, it may fetch again and ignore the prefetched record.

| Server/client mismatch | Observable result | Correction |
| --- | --- | --- |
| Different keys | Client refetch or missing initial data | Share a stable key factory |
| Wrong provider boundary | Cache is not visible to hooks | Mount provider around hydrated consumers |
| Per-request data in a global cache | Cross-request leakage risk | Create isolated request-scoped clients |
| Secret in dehydrated state | Sensitive value embedded in HTML | Prefetch only safely exposable data |

**Independent exercise:** Inspect the dehydrated payload, compare server/client keys byte for byte and confirm the page hydrates without an unnecessary duplicate query. Intentionally change the key and explain the extra fetch. Audit the serialized HTML for tokens or another user's tasks.

**Trust boundary:** SSR HTML is observable to the recipient. Do not dehydrate service keys, session credentials or other users' private records. A successful hydration test proves cache wiring, not authentication, access control or authorization.
