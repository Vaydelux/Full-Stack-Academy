## The problem we're solving

A task disappears as soon as Delete is clicked. The server rejects the request, but the UI keeps it removed, contradicting authoritative server state.

**Broken behavior in the starter:** The starter removes the row in cache but never saves or restores the previous snapshot after an HTTP error.

## Build the mental model

An optimistic update is speculative. cancelQueries protects the snapshot from in-flight reads, onMutate saves the previous value, onError restores it, and onSettled invalidates.

**Predict before coding:** During a failed DELETE, the row disappears briefly and then reappears. A successful delete stays removed after refetch.

**Version and deployment scope:** TanStack Query v5, React 19, TypeScript 5. The Task API is a locally bound, in-memory, unauthenticated fixture. Earlier committed notes report locked local Chrome/SSR tests on November 20, 2026; they have not been rerun for this candidate. <LessonStep number={2} title="Implement the correct TanStack Query behavior" file="drafts/forms-query/labs/optimistic-rollback/solution.tsx" expected="During a failed DELETE, the row disappears briefly and then reappears. A successful delete stays removed after refetch.">

```tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';
type TaskPage={items:{id:string;title:string}[]};
export function DeleteButton({id}:{id:string}){
 const client=useQueryClient();
 const key=['tasks',{status:'all',limit:10}] as const;
 const del=useMutation({
  mutationFn:async()=>{
   const response=await fetch('/api/tasks/'+encodeURIComponent(id),{method:'DELETE'});
   if(!response.ok)throw new Error('HTTP '+response.status);
  },
  onMutate:async()=>{
   await client.cancelQueries({queryKey:key});
   const before=client.getQueryData<TaskPage>(key);
   client.setQueryData<TaskPage>(key,current=>current?{...current,items:current.items.filter(t=>t.id!==id)}:current);
   return {before};
  },
  onError:(_error,_variables,ctx)=>{if(ctx?.before)client.setQueryData(key,ctx.before);},
  onSettled:()=>client.invalidateQueries({queryKey:['tasks']}),
 });
 return <button type="button" disabled={del.isPending} onClick={()=>del.mutate()}>
  {del.isPending?'Removing…':'Delete'}
 </button>;
}
```

**What changed:** An optimistic update is speculative. cancelQueries protects the snapshot from in-flight reads, onMutate saves the previous value, onError restores it, and onSettled invalidates.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** The starter removes the row in cache but never saves or restores the previous snapshot after an HTTP error.
2. **Diagnose:** Trace the query key, cancellation boundary, remote response, cache update and invalidation.
3. **Repair:** Snapshot affected query data before an optimistic delete, roll back on failure, and reconcile after the mutation settles.
4. **Regression:** Force DELETE 404 or transport failure. The cached row must be restored. Success must invalidate server data. Disable concurrent deletes or implement version-aware compensation.
5. **Security and operations:** Snapshot rollback only remains correct when conflicting updates are serialized or reconciled; overlapping optimistic mutations need a more careful policy.

## Production decision guide: rollback is a concurrency problem

An optimistic update makes the interface react before the server confirms an operation. A correct delete flow cancels or coordinates relevant reads, snapshots the affected query values, removes the row temporarily and restores the snapshot on failure. On settlement, invalidate or reconcile against authoritative server state. This simple model is sound only when overlapping mutations cannot overwrite each other's snapshots.

| Event | Optimistic cache action | Verification |
| --- | --- | --- |
| Delete begins | Snapshot then remove row | UI updates promptly |
| Server returns 404 or fails | Restore previous rows | Original row returns |
| Delete succeeds | Reconcile with server | Row stays removed |
| Two deletes overlap | Serialize or use version-aware compensation | One rollback cannot erase another success |

**Independent exercise:** Force a failing delete after the row disappears. Assert that its title, status and list position recover. Then make the delete succeed and verify a fresh server read. Repeat with two near-simultaneous operations and explain why the naive single-snapshot approach could restore stale data.

**Security boundary:** Client cache rollback is a presentation safeguard. It cannot undo a committed server write, authorize a deletion or resolve multi-user conflicts without a backend revision/ETag or equivalent authoritative protocol.

## Applied debugging clinic

Start deletion A, then deletion B, before A returns. Force A to fail and B to succeed. Predict how restoring an entire snapshot can resurrect B. Compare targeted rollback or serialized conflicting writes, then invalidate to reconcile with the server. This is an extension exercise; the existing starter need not support concurrent writes.

**Evidence to record:** query identity, request outcome, cache state before and after the action, and the recovery decision. Separate observed network behavior from what the UI displays. Re-run the original failing interaction after the repair.
