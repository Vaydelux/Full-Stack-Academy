## The problem we're solving

A title preview reads a separate useState variable, while the submit handler reads React Hook Form's registered field. Typing changes one value and submitting sends another.

**What breaks in the learner starter:** Separate useState preview and RHF input values drift after reset or programmatic update.

## Build the mental model

React Hook Form owns registered values. useWatch observes form state without introducing another writable duplicate source.

**Predict before coding:** Typing must update both preview and submitted payload from the same registered field value. Reset should clear both.

<LessonStep number={2} title="Apply the instructor repair" file="drafts/forms-query/labs/form-state-bug-hunt/solution.tsx" expected="Typing must update both preview and submitted payload from the same registered field value. Reset should clear both.">

```tsx
import { useForm, useWatch } from 'react-hook-form';
export default function PreviewForm(){
 const {register,handleSubmit,control,reset,setValue}=useForm<{title:string}>({defaultValues:{title:''}});
 const preview=useWatch({control,name:'title',defaultValue:''});
 return <form onSubmit={handleSubmit(console.log)}>
  <label htmlFor="preview-title">Title</label><input id="preview-title" {...register('title',{required:true})}/>
  <p aria-live="polite">Preview: {preview}</p>
  <button type="button" onClick={()=>setValue('title','Suggested title',{shouldDirty:true})}>Use suggested title</button>
  <button type="button" onClick={()=>reset({title:''})}>Reset</button>
  <button type="submit">Save</button>
 </form>;
}
```

**Why:** React Hook Form owns registered values. useWatch observes form state without introducing another writable duplicate source.

</LessonStep>

## Bug Hunt: reproduce, diagnose and repair

1. **Reproduce:** Separate useState preview and RHF input values drift after reset or programmatic update.
2. **Diagnose:** Locate who owns the current value, where it is transformed, and which effect or async boundary can invalidate assumptions.
3. **Repair:** Find and remove duplicated form state, stale previews, and uncontrolled-to-controlled mismatches.
4. **Regression:** Type, reset and programmatically update the field; preview and submitted payload must be consistent, with no independent useState shadow.
5. **Operational boundary:** Treat displayed form previews as user content; React text interpolation escapes text, while innerHTML would introduce an XSS risk.

## Production decision guide: derive previews from the form

A preview is a view of the current title, not an independent source of editable state. When the registered RHF input owns the title, use `useWatch` (or an appropriate `watch` subscription) to render it, and `setValue` to apply a suggestion to that same field. An extra `useState` copy can drift after reset, programmatic updates or rerenders.

| Action | Single source of truth | Typical bug |
| --- | --- | --- |
| Type title | Registered field value | Preview uses stale component state |
| Apply suggestion | One `setValue` update | Submission sends older title |
| Reset form | RHF default baseline | Shadow preview remains |
| Submit | `handleSubmit` data | Confirmation differs from sent value |

**Independent exercise:** Type a title, activate the suggested title, submit, then reset. After each action, record expected input and preview values. Explicitly distinguish the current draft from the last submitted result; these values can legitimately have different lifetimes.

**Security boundary:** User-provided preview text belongs in React text interpolation, not HTML injection. Unified state fixes consistency bugs; it does not establish that a server accepted a record. Revalidate submitted values at the HTTP boundary.
